## 一、依赖关系

```
方向4 渠道管理 API ──┬──> 方向1 真实/模拟 provider 入站（需要绑定与身份数据）
                    └──> 方向3 等待消息提升（需要绑定反查员工与租户）
方向1 provider sender ──> 方向2 outbox 调度（没有 sender 就不能开调度，
                                        否则每条投递会被误标为永久失败）
方向3 提升 ──┐
方向2 调度 ──┴──> 共用 Run 终态钩子（RunExecutionService.settle）
方向6 慢客户端/多实例 ──> 横切：outbox 认领、提升占位、瞬时事件可见性
方向5 P4 ──> 相对独立，但与方向6 的"多实例父子状态"有交集
```

实施批次（前一批通过再进下一批）：

| 批次 | 内容 | 理由 |
| --- | --- | --- |
| A | 方向 3 提升机制 → 方向 2 outbox 调度 → 方向 4 管理 API | 无外部依赖，且是方向 1 的数据与触发前提 |
| B | 方向 1 模拟 provider（sender + 回调 + 验签 + 放行规则）→ 端到端验证 | 依赖 A 的绑定数据与调度 |
| C | 方向 5 P4 受控团队 → 方向 6 慢客户端加固与多实例幂等用例 | 相对独立，放最后 |

## 二、逐方向边界、依赖与验收标准

### 方向 4：渠道管理侧 API

**边界**：只做平台侧绑定数据的管理（账号绑定、身份绑定）；**不做** provider 侧的 OAuth/授权交互（那属于真实 provider 接入，本轮以模拟 provider 代替）。凭据只以引用（`credentialRef`）形式存取，**任何接口都不回传明文凭据**。

**依赖**：无（独立）。

**交付物**：
- `POST/GET/PATCH /api/admin/v1/channels/accounts`：创建、列出、详查、启停或改默认员工与会话粒度
- `PUT/DELETE /api/admin/v1/channels/accounts/{bindingId}/identities/{externalUserId}`：绑定、解绑外部用户与平台用户
- `GET /api/admin/v1/channels/runtime`：查看框架渠道注册表的实际装载情况（渠道、默认 Agent、会话粒度、启用绑定数）
- 平台服务 `ChannelAdministrationService` + 仓储端口；审计留痕落在控制层
  （平台层按既有约定不依赖日志实现，管理操作的记录在 API 层完成）

### 实现方式：复用 AgentScope 既有能力，不另造渠道管理

渠道运行的注册表与生命周期直接复用框架组件，平台只提供"持久化绑定 → 框架配置"这一层投影：

| 框架组件 | 平台侧用法 |
| --- | --- |
| `ChannelManager` | 渠道注册表与生命周期（`register` / `unregister` / `startAll` / `isStarted`），取代原先"手工 new 一个渠道且从不注册"的状态 |
| `ChannelConfig` + `ChannelBinding.forAccount` | 渠道配置与路由的规范载体：每条启用绑定投影为一条账号级路由（外部账号 → `employee-<id>`） |
| `DmScope` | 会话粒度的框架表示；平台侧用 `SessionScope` 枚举同构声明，由装配层映射，避免框架类型渗进领域模型 |
| `Channel.applyRoutingConfig` | 配置热更新钩子：同一渠道增加绑定时不重建实例，只在渠道拒绝配置时才换实例兜底 |

装配规则与取舍：

1. **一个 `provider` 对应一个渠道实例**，`channelId` 即 provider；没有任何启用绑定的渠道会被卸载（`unregister` 顺带 `stop`）。
2. **启动即装配一次，运行期由管理写入触发**：新增绑定装载渠道、禁用绑定卸载渠道、其余情况热更新配置。
3. **同一渠道内混合会话粒度取最严的一条**：放宽会让不同对端共用一个会话（框架默认 `DmScope.MAIN` 正是如此），收紧只影响会话数量，因此失败方向必须是收紧。
4. **不让 Gateway 直接驱动 Agent**：执行仍由平台 Run 调度器负责，否则会出现两套 Run 状态机，而排队、取消、审批与事件持久化都挂在平台那一套上。
5. **`ChannelManager.startAll()` 无幂等判断**，装配层每次刷新都会调用它，因此渠道自身的 `start` 必须幂等（`PlatformChannel` 内部记账），避免重复启动刷成日志噪音。


**验收标准**：
1. 非管理员访问返回 403（`/api/admin/**` 已强制 `PLATFORM_ADMIN`）。
2. 创建绑定后再入站即可受理；`enabled=false` 后入站立即被拒。
3. 解绑后该外部用户入站立即被拒（`REVOKED` 不参与解析）。
4. 列表与详情只返回 `credentialRef`，不含任何明文凭据。
5. 重复绑定同一 (provider, externalAccountKey) 被拒绝，而不是产生第二条记录。

### 方向 3：等待中消息的提升机制（缺陷 B 遗留）

**边界**：只解决"会话忙时登记的等待消息"如何在该会话空闲后变成 Run。**不做**跨会话的优先级调度，也不做用户可见的队列位置展示。

**依赖**：方向 4 的绑定与身份数据（提升时要按原消息的用户与员工建 Run）；运行终态钩子（与方向 2 同源）。

**交付物**：
- 端口 `ChannelTurnPromoter.promoteWaitingTurn(SessionId)`（platform/channel）
- JDBC 实现：`SELECT … WHERE session_id=? AND run_id IS NULL ORDER BY accepted_at, provider_event_id LIMIT 1 FOR UPDATE` → 复用 `SessionApplicationService.createRun`（`clientRequestId = provider_event_id`，天然幂等）→ 回填 `run_id`
- `RunExecutionService` 在终态落定后调用（与 `ChannelReplyEnqueuer` 同一位置）

**验收标准**：
1. 会话忙时入站的消息，在该会话当前 Run 进入终态后**自动变成 Run**，无需人工干预。
2. 提升**只发生一次**：并发或重复触发都不会产生第二个 Run（`FOR UPDATE` + 回填条件双保险）。
3. 无等待消息时提升为无操作，不产生任何写入。
4. 提升失败（例如员工已下架）不影响已落定的 Run 终态。

### 方向 2：outbox 任务调度与接线

**边界**：只做"定时认领 + 交给 sender + 记结果"的驱动与装配；**不做** sender 内部的 provider 协议。**不开**无 sender 的调度。

**依赖**：方向 1 的 sender（否则不启用调度）。

**交付物**：
- `ChannelDeliveryWorker` 装配为 bean（`Map<provider, ChannelOutboundSender>`）
- `ChannelDeliveryDispatcher`：`@Scheduled` + `@ConditionalOnProperty(haizhuo.brain.channel-worker.enabled)`，形态与 `RunWorker` 一致（本类不含业务逻辑）
- 配置项：`haizhuo.brain.channel-worker.enabled`、`poll-delay-ms`、`batch-size`

**验收标准**：
1. 开启调度后，`PENDING` 投递被自动发送并落 `DELIVERED`。
2. 未装配 sender 的 provider 不会被自动调度误标永久失败（该开关默认关闭）。
3. 两个实例并发运行时，同一条投递**只被发送一次**（状态翻转互斥）。
4. 可重试失败下一轮重投；`UNCERTAIN` 与 `PERMANENT_FAILURE` 不再被认领。

### 方向 1：真实 IM provider 的消息发送链路

**边界**：本轮以**本地模拟 provider** 打通链路：出站 sender + 入站回调 + 验签 + 去重 + 回执。**不改**平台受理与其他业务语义；换真实 IM 时只新增 sender 与验签器两个实现。

**依赖**：方向 4 的绑定数据、方向 2 的调度。

**交付物**：
- `SimulatedProviderChannelOutboundSender`：按绑定解析端点，HTTP 投递；未配置端点时记录并返回 `DELIVERED`（便于本地验证）；支持注入失败以验证重试与不确定分类
- 入站回调 `POST /api/v1/channels/{provider}/webhook`：HMAC-SHA256 验签 → 构造 `VerifiedChannelMessage` → `ChannelIngressService.accept` → 返回受理结果
- 安全规则：显式放行该路径（当前 `denyAll` 兜底会拦住它），**验签失败一律 401 且不写任何数据**
- 凭据经 `CredentialResolver` 解析，不落日志

**验收标准**：
1. 验签失败 → 401，且收件箱、会话、Run 均无新增。
2. 验签成功 → 受理并建 Run；同一 `providerEventId` 重投只受理一次。
3. Run 终态后答复自动进入 outbox 并由 sender 投出（端到端可见 `DELIVERED`）。
4. 投递失败按可重试/永久/不确定三态正确分类，不确定不自动重发。

### 方向 5：P4 受控团队

**边界**：复用框架 `exposeSubagent` / `SubagentRegistry` / `RemoteEventType`；平台只收敛**可委派角色**与**最小工具集**，并建立父子关联与进度投影。**不**开放动态子代理、**不**让渠道侧看到 Worker 内部消息。

**受控默认角色集**（已确认）：
| 角色 | 允许的能力 | 明确禁止 |
| --- | --- | --- |
| `research` | 检索类只读工具 | 任何写操作、任何审批类工具 |
| `document` | 文档处理类只读工具 | 任何写操作、任何外部副作用 |

**依赖**：已发布定义（角色声明随定义版本冻结）。

**交付物**：
- `HarnessAgentFactory` 注入 `subagent(SubagentDeclaration)`：子代理工具集 = 父级工具集 ∩ 角色白名单，且剔除写操作
- 平台侧：`SUBAGENT_EXPOSED` 事件 → 父子 Run 关联与进度投影（复用既有事件与投影链路）
- 父 Run 取消/失败时撤销暴露（`revokeByParentSession`）

**验收标准**：
1. 子 Agent 无法调用父级未授权或写操作工具（越权请求被拒且留痕）。
2. 并发子任务的产出不串会话（结果归属各自父 Run）。
3. 父 Run 取消或失败时，已暴露子代理被撤销，不再回传。
4. 渠道侧只收到安全摘要，不含 Worker 内部消息与工具原始参数。

### 方向 6：慢客户端与多实例

**边界**：加固正确性，不改变业务语义。多实例**接受瞬时事件降级**（已确认）：瞬时增量只在订阅所在实例可见；持久事件（含终态、计划快照）仍全量一致，断线补读不受影响。

**依赖**：横切方向 2（认领互斥）、方向 3（提升占位）与 P1/P2 的流。

**交付物**：
- 慢客户端：确认并固化 backpressure 语义——durable 事件绝不因慢订阅者丢失、慢订阅者不阻塞其他订阅；补"延迟订阅者"回归用例
- 多实例：outbox 认领与等待提升的跨实例幂等用例；在文档中明确瞬时事件降级语义与前端表现（前端已依赖持久终态校准，无需改动）

**验收标准**：
1. 一个慢订阅者阻塞时，另一个订阅者仍能按时收到事件。
2. 慢订阅者恢复后能通过游标补齐全部持久事件，不出现空洞。
3. 两个实例并发认领同一条投递或同一个等待消息时，只有一个成功。
4. 多实例下瞬时事件缺失不会导致界面错乱（终态校准足够）。

## 三、关键设计决策

| 决策 | 内容 | 理由 |
| --- | --- | --- |
| 提升的原子性 | `SELECT … FOR UPDATE` 锁住最早等待记录 → 建 Run → 回填 `run_id` | 建 Run 需要先知道 runId，无法用单条 UPDATE 完成占位；行锁是唯一能保证"只提升一次"的手段 |
| 提升复用 `createRun` | `clientRequestId = provider_event_id` | 复用既有幂等重放与单会话唯一活动 Run 排队，不重写排队 |
| outbox 认领互斥 | 状态翻转 `PENDING/RETRYABLE_FAILURE → SENDING` | 单条 UPDATE 自带原子性，无需长事务锁，天然支持多实例 |
| 无 sender 不开调度 | 调度由独立开关控制，默认关闭 | 否则每条投递会被记成永久失败，污染状态 |
| 瞬时事件降级 | 不引入 Redis 广播 | 前端已用持久终态整体校准，多实例下缺失瞬时增量只影响"逐字出现"的观感，不影响正确性 |
| 管理 API 位置 | `/api/admin/v1/channels/**` | 自动继承既有的 `PLATFORM_ADMIN` 强制鉴权，无需新增安全规则 |
| 回调端点放行 | 显式 `permitAll` + 强制验签 | 当前 `anyExchange().denyAll()` 会拦住回调；放行必须与验签成对出现 |

## 四、风险与未决项

| 项 | 说明 |
| --- | --- |
| 模拟 provider 与真实 IM 的差距 | 真实 IM 有平台特有的签名算法、加解密、重试语义与限流；本轮只保证平台侧链路正确，切换时需针对 provider 复核验签与发送语义 |
| 提升的触发时机 | 目前挂在 Run 终态落定后；若 Run 终态由其他路径产生（如租约回收后重排），仍需回归确认 |
| 子代理预算与并发上限 | 受控默认角色集只收敛了工具权限，**未设**并发子任务上限与预算，需后续补充 |
| 渠道侧安全摘要的边界 | "哪些内容算安全摘要"需要与产品确认，当前按"仅进度与结论、不含工具参数"实现 |
| 多实例瞬时事件 | 接受降级，但若产品要求逐字流跨实例一致，需要重新引入共享广播 |

## 五、实施与真机验证结果

本轮实现并验证了**方向 1（模拟 provider）、方向 2（outbox 调度）、方向 3（等待提升）**，构成完整闭环。

### 已验证通过的场景（真机，MySQL + 真实模型）

| 场景 | 结果 |
| --- | --- |
| 正确签名回调 | 200 + `sessionId` + `runId`，受理并建 Run |
| 同一事件重投 | `duplicate=true` 且命中**同一** `runId`，收件箱不增 |
| 错误签名 | **401** + `CHANNEL_SIGNATURE_INVALID`，且不写任何数据 |
| 会话忙时入站 | 后两条消息**受理但 `runId` 为空**（等待中），不撞唯一约束 |
| **等待消息提升** | 45 秒内两条等待消息被**自动回填 `runId`** 并各自执行到 `SUCCEEDED`（按序逐个提升） |
| **outbox 调度投递** | 5 条答复**全部 `DELIVERED`**，`attempts=1`（一次成功、无重复发送） |

### 过程中发现并修复的问题

**回调端点需要 CSRF 豁免。** 首次部署回调全部返回 **403**：`permitAll` 只解决了鉴权，但 POST 仍被 CSRF 保护拦截——无浏览器的渠道回调不可能持有 CSRF token。修复为在 CSRF 保护 matcher 中排除该路径，使「`permitAll` + 跳过 CSRF + 控制器内强制验签」三者成对出现。

**但豁免必须"追加"而不是"替换"。** 第一版豁免把 `requireCsrfProtectionMatcher` **整体替换**成"仅排除回调路径"，丢掉了框架默认匹配器承担的另一条语义——**安全方法（GET/HEAD/OPTIONS/TRACE）不参与 CSRF 校验**。后果是匿名 GET 也要 token，而发放 token 的 `/api/v1/auth/csrf` 自身就是 GET，形成死锁式 403；又因为 CSRF 过滤排在授权之前，本应 401 的匿名请求全部被抢先改成 403。正确写法是在默认语义之上用 AND 组合追加：

```java
.requireCsrfProtectionMatcher(new AndServerWebExchangeMatcher(
        CsrfWebFilter.DEFAULT_CSRF_MATCHER,     // 保留"安全方法不校验"等默认语义
        channelCallbackCsrfExemption()))        // 只额外豁免渠道回调
```

这也解释了为什么单元测试没能拦住它：回调控制器测试是 Mockito 单元测试，**不经过 `SecurityWebFilterChain`**，只有全链路的 `ApplicationContextSmokeTest`（随机端口真起服务）才会暴露。该冒烟现已补上三条防回归断言（匿名 GET csrf=200、匿名 GET 受保护资源=401、无 token 的渠道回调 POST 抵达控制器而非被 CSRF 拦成 403）。这条经验已补进第三节决策表。

### 尚未修复、需要决策的发现

**禁用用户仍可通过渠道入站创建 Run。** 验证过程中临时账号处于 `DISABLED` 状态，但渠道回调依然受理成功并创建了 Run 并正常执行。原因是受理链路只校验"渠道绑定 + 身份关联 + 员工已发布"，**不校验平台用户状态**。是否应在受理时拒绝禁用用户，需要产品确认（涉及"禁用后已排队消息如何处理"的语义），因此本轮只记录不修改。
