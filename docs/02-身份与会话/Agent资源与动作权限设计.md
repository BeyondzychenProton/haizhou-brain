## 1. 结论和已确认前提

**数字员工装配了能力，只表示它可以提出相应操作；当前用户是否能执行，必须按本次动作和目标资源重新判定。** 本平台负责自己的授权；外部系统继续负责它自己的业务授权。

以下作为一期已确认的产品基线：

1. 管理员创建并启用用户；用户通过唯一手机号和密码登录。平台使用稳定的 `UserId` 归属数据和授权，手机号用于登录及对接定位。
2. 启用的普通用户默认可使用唯一的预置 `DigitalEmployee`，默认只能访问自己的 Session、Workspace、资料和成果。
3. 员工的已发布定义显式绑定 Skill、Tool、MCP 和知识资源。配置能力不自动授予用户对业务资源的权限。
4. 外部业务动作需要平台授权。外部只读动作**逐项评估**：管理员按“目标系统 + 业务动作”明确加入普通用户默认权限的才默认开放，其余单独授权；外部写操作不因员工配置而默认开放。
5. 重要操作可能需要确认。确认不能弥补权限不足；外部系统 Token 也不代替本平台的授权。
6. 公司内部使用，不引入公司或租户作为产品权限维度。既有代码中的 `TenantId` 命名后续与产品模型一起校准。
7. 知识一期分为管理员开放给员工使用的**公司公共知识源**和按 `UserId` 归属的**个人 Workspace 资料**；同一知识源内混放不同用户或部门权限的文档，不作为一期默认能力。
8. 外部业务系统的用户 Token 由凭证管理职责按 `UserId + 目标系统` 单独维护，与员工能力、Tool 和 MCP 绑定分离。

这份文档提出一种能支持一期、又能向更多数字员工和业务系统延伸的权限骨架。文中标注“建议”的细则属于设计提议，不等于代码已经实现。

没有匹配的明确授权规则时默认拒绝。员工已装配、工具自称只读、持有外部 Token 或用户点击确认，均不构成隐含授权；尚未列入管理员逐项批准清单的外部只读动作也默认拒绝。

## 2. 先把三种“允许”分开

| 边界 | 谁决定 | 回答的问题 | 不能替代什么 |
| --- | --- | --- | --- |
| 员工能力 | 员工已发布定义与 `CapabilityBinding` | 这个版本的员工可以发现和调用哪些能力？ | 不替代用户授权 |
| 平台权限 | 智慧大脑 `security` 与资源所有者规则 | 当前用户对这个动作和目标资源有无权限？ | 不替代外部系统授权 |
| 外部系统权限 | 目标系统及其认可的用户凭证 | 目标系统是否接受这次业务操作？ | 不反向授予平台权限 |

例如，员工已绑定“查询订单”和“取消订单”两个工具，张三获准使用该员工，并不意味着张三拥有 `order.cancel`。即使平台允许取消，目标系统仍可能因为订单状态、所有权或它自己的授权规则拒绝。平台必须把拒绝当成实际结果反馈。

可以用一个决策次序理解：**账号与入口有效 → 员工可用且能力已绑定 → 用户有相应动作权限 → 本次资源在允许范围内 → 满足必要确认 → 实际执行并接受目标系统的最终判断。** 其中任何一项失败，都不能由 Prompt、模型规划或换一个 Tool 名称补足。

## 3. 权限语言：Subject、Role、Scope、Resource、Action、Policy

| 概念 | 在本产品里的含义 | 一期用法 |
| --- | --- | --- |
| `Subject` | 提出请求或承担责任的主体 | 首先是已验证的真实 `UserId`；后台服务身份另行标识 |
| `Role` | 一组平台内 Permission 的集合 | 至少区分平台管理员与普通用户；不把 Role 本身当作资源范围 |
| `Scope` | 权限适用的边界 | 一期重点是“本人资源”与明确授予的外部业务范围 |
| `Resource` | 被读取、管理或操作的对象 | 例如员工定义、Session、某份成果或目标系统订单 |
| `Action` | 对该对象要做的事情 | 例如 `use`、`read`、`publish`、`cancel` |
| `Policy` | 额外的业务条件 | 账号启用、资源所有者、任务有效期、目标系统、必要确认等 |

**Role 给出“可以做什么”，Scope 与资源事实决定“可以对哪些对象做”。** 例如普通用户有“读取个人成果”的权限，但读取 `artifact:A2` 时，还须核验它属于本人；无需为每个用户复制一个角色。`Group` 可以作为后续批量分配角色的途径，现阶段不因只有一个公司就预设部门权限。

Scope 判断依赖可信的资源归属或范围事实。模型生成的资源 ID、工具返回的描述、文件路径和渠道消息里的自报身份只是请求参数，不能证明归属。外部对象的范围事实应由目标系统、平台同步的可信关系或受控适配器提供；无法可靠判定时拒绝该范围的调用。

数字员工与内部子 Agent 不应伪装成真实用户。Agent 身份可用于记录“哪个员工版本、哪个子 Agent 发起”，执行行为仍要关联真实用户、Session 和 Run。服务账号只代表平台访问外部服务的技术身份，也不能代替用户获得其个人资料访问权。

## 4. 一期需要辨认哪些资源和动作

这里的动作名表示稳定的**产品权限语义**，不要求立刻建成独立的数据库权限项。平台可以先用少量角色、所有者规则及工具授权规则实现。

| 资源类别 | 典型资源 | 典型动作 | 一期边界 |
| --- | --- | --- | --- |
| 员工与配置 | `DigitalEmployee`、已发布定义、能力绑定 | `use`、`configure`、`publish`、`disable` | 普通用户默认 `use` 预置员工；配置和发布归管理员 |
| 对话与执行 | Session、Run、待回答/确认事项 | `create`、`read`、`append`、`cancel`、`respond`、`confirm` | 普通用户只操作归属自己的对象；确认必须指向具体待确认事项 |
| 个人资料 | Workspace 文件、上传资料、个人知识引用 | `read`、`write`、`delete`、`export` | 默认按所有者核验；检索结果进入模型前同样受控 |
| 公共知识 | 管理员配置的公司公共知识源 | `search`、`read` | 绑定到员工且源已开放后，启用的普通用户可检索；不与个人资料混存 |
| 成果 | 文档、报告、产物版本 | `create`、`read`、`update`、`export`、`share` | 默认本人可用；跨会话引用不自动获得修改权；共享先不默认开放 |
| 能力配置 | Skill、Tool、MCP 服务、知识源 | `register`、`bind`、`enable` | 管理“装配什么”属于配置权限；不能把 MCP 服务整包视为业务操作权限 |
| 外部业务对象 | 订单、会议或其他目标系统资源 | `query`、`create`、`modify`、`cancel` | 按目标系统和业务动作授权；写操作需要明确规则，必要时确认 |

注意两个细节：

- “读取订单列表”在请求前可能没有具体订单 ID。平台应在发出查询前限定目标系统、业务动作、查询条件和允许范围，返回后再复核。若目标系统不能按范围查询，不能仅靠事后过滤开放宽范围列表、分页、计数或聚合接口；这些响应也可能泄露无权对象信息。目标尚未明确时不能扩大为“查询所有”。
- 外部查询不会仅因标注为“只读”就成为普通用户默认权限。管理员逐项确定可默认开放的目标系统和业务动作，目标系统再约束具体可读数据。
- 公司公共知识源必须由管理员确认其全部内容可向该员工的启用用户开放。个人资料按 `UserId` 隔离。将不同用户或部门权限内容混在同一检索源的能力留待后续设计；若以后接入，必须在检索前按可信权限元数据收窄候选，并对返回内容复核，不能只在检索后删去无权片段。
- 管理员可管理账号和员工配置，不因此默认能读取普通用户的私密对话、个人 Workspace 或成果。受控审计与代办如果以后需要，应另设权限和留痕。

## 5. Skill、Tool、MCP 与 Permission 如何建立关系

`CapabilityBinding` 是**员工定义的能力装配记录**，例如“本版本可使用工具 T 的某个修订”。平台授权则针对**用户对业务动作与资源**，两者各有职责。

| 对象 | 与权限的关系 | 设计要求 |
| --- | --- | --- |
| Skill | 方法和指引，可能引用多个工具 | 可按员工定义装配；加载 Skill 不自动授权它提及的操作 |
| Tool | 执行某种操作的入口 | 登记其可能执行的业务动作、目标资源识别方式及确认要求；执行前按实际参数判定 |
| MCP 服务 | 提供多个远端 Tool 的连接 | 新发现的子工具先进入待选择清单；经过登记、绑定与发布才成为员工能力；每种实际操作仍经过平台检查 |
| Knowledge | 公司公共知识源，以及与之分开的个人资料访问能力 | 一期公共源由管理员开放并绑定员工；个人资料始终按 `UserId` 校验；不默认支持混合文档权限 |
| 子 Agent | 内部委派的执行者 | 只能获得本次工作需要的能力与资料，权限上限不高于委派者的有效授权 |

一个 Tool 可能根据参数执行不同操作；一个业务操作也可能由多个 Tool 实现。因此授权规则不要仅绑定原始 Tool 名称。建议由能力登记说明“这个调用对应哪个业务动作、如何识别目标资源、是否需要确认”，再由统一执行入口把实际参数交给授权判断。发现或展示能力时可先过滤无权项，**工具真正执行前仍必须重新检查**，防止配置、权限或目标在等待期间改变。

尤其要覆盖 AgentScope 内置工具、Workspace 文件操作、知识检索、MCP 适配以及子 Agent 使用的工具。不能只检查平台自己新写的一部分业务 Tool，也不能仅靠 Prompt 告诉 Agent“不要调用”。

**工具接入门槛**：能力登记时必须给出稳定身份与修订、参数约束、读写影响、业务动作映射及目标资源解析方式。实际调用由平台控制的适配器解析，不能相信模型或远端 MCP 服务自报的权限标签。一次调用可能触发多个动作时，对完整影响集合授权；影响无法确定、参数越界或 schema / 语义与已审核修订不一致时拒绝。通用命令、任意 HTTP 请求、任意文件系统或网络访问不能用一个宽泛 Permission 覆盖；先限制可达范围或改为专用受控工具。装配时还须核对最终暴露给 Agent 的工具集合，不开放绕过平台检查的路径。验证方法见[AgentScope 接入验证清单](../06-开发指南/智能体框架接入验证清单.md)。

AgentScope 的工具许可与平台业务授权是两层判断。框架的允许或询问结果可用于拦截与交互，但不能覆盖平台拒绝；[框架权限文档](https://github.com/agentscope-ai/agentscope-java/blob/v2.0.3/docs/v2/en/docs/building-blocks/permission-system.md)所述的建议规则接受机制，不能转化为平台对后续同类业务调用的授权。平台须对每次实际操作重新判定；用户确认仅针对一次已获授权的具体操作。

## 6. 一次 Run 中的授权时点

| 时点 | 要核验的事实 | 失败时的产品行为 |
| --- | --- | --- |
| 请求入站 | Web 登录态或可信渠道绑定解析为 `UserId`；账号启用；Session 归属 | 拒绝进入用户上下文；消息里自报手机号不算已验证身份 |
| Run 实际开始执行 | 重检账号状态与员工使用权；锁定当时已发布定义及能力修订；附件和历史引用可访问 | 不启动无权 Run；不给模型注入无权资料；等待执行期间不提前冻结版本 |
| 能力准备 | 已发布版本的绑定有效；工具/知识源仍受控 | 过滤无权或停用能力；发现能力不增加授权 |
| 每次读资料/调用工具 | 实际 `Resource + Action`、用户角色与范围、所有者、任务约束、账号状态 | 拒绝该动作并返回明确原因；其他安全的工作可按 Run 规则继续 |
| 等待用户确认及恢复 | 确认人、Run、目标操作、资源、规范化参数与有效期；恢复时重检账号、授权、工具状态和原发布修订 | 过期或内容变化则重新确认/拒绝；确认不自动扩大权限 |
| 外部请求 | 凭证属于当前 `UserId + 目标系统`，仍有效；目标系统接受请求 | 只使依赖该系统的能力失败或等待，不伪造成功 |
| 结果保存与查看 | 产物归属、Session/Run 关联、查看人的权限 | 结果不能写入或展示到别人的个人空间 |

这条链适用于 Web 和可信消息渠道；不同渠道可能对应不同 Session，但属于同一平台用户时，访问规则仍由同一个 `UserId` 计算。对于长任务、续接和重试，不能只依赖 Run 开始时的一次判定，尤其要重检停用账号、撤销授权和外部写操作。

确认是对**已获授权的一次待执行操作**的附加条件。平台先判定权限，再保存关联真实用户、Run、动作、目标资源、规范化参数或摘要、影响说明及有效期的待确认事项。回应时核验确认人与事项归属、参数未变且事项未被消费，重检权限、资源状态、账号与工具停用后才执行。目标或参数实质变化须重新确认；重复回应不得再次提交。同一请求已发出但外部结果不确定时按 Run 恢复规则核查，不能假定外部副作用恰好发生一次。业务审批是另一项业务事实，不能混同用户确认。

“撤销立即生效”指撤销后尚未越过执行前检查的调用应被拒绝；已经发往外部系统的请求仍可能完成。平台记录在途状态和真实结果，不承诺撤销、取消或确认失效能回滚已发生的外部副作用。

## 7. 一期默认权限与授权方式

| 主体 | 默认可以做 | 默认不可以做 |
| --- | --- | --- |
| 已启用普通用户 | 使用预置员工；建立和访问自己的 Session/Run；读取、编辑自己的 Workspace 和成果；检索已绑定的公司公共知识源；回应自己的等待点 | 管理员工定义；访问他人资料；仅凭员工绑定调用尚未授权的外部业务动作 |
| 平台管理员 | 创建、启停用户；管理基础角色及员工配置、发布和能力绑定 | 因管理身份而直接读取他人的私密对话正文或个人 Workspace |
| 内部子 Agent | 在所属 Run 内使用显式交付的任务上下文和受限能力 | 自行获得新角色、打开整份 Workspace、绕开当前用户权限 |

外部业务动作按“目标系统 + 业务动作 + 适用范围”明确配置；管理员只把逐项评估通过的外部只读动作加入普通用户默认权限，其余单独授权。**一期先不要为每个 Tool 都造独立角色**；几个稳定的业务 Permission 和必要的范围规则，通常比大量随代码变化的 Tool 权限更容易管理。

首个外部系统接入前，应形成明确的默认权限清单：每项只读动作的目标系统、数据范围和是否默认开放，以及写动作所需单独授权、用户确认或业务审批。清单未覆盖的动作默认拒绝。

关于临时任务授权：本阶段先保留设计位置。若以后由用户对某个任务授予一次性操作，必须限定动作、具体资源或可收敛的范围、任务及有效期，并确保授权者本来有权委托。Agent 不能自行签发授权；任务授权也不能绕过员工能力上限或目标系统规则。一次确认则是对已获准操作的附加条件，不等于长期或任务授权。

## 8. 与外部 Token 的关系

平台在登录后可按已核验手机号为对应目标系统准备用户 Token，但**“拿到 Token”与“平台允许 Agent 执行某动作”是两个不同事实**。外部用户 Token 由独立凭证管理职责按 `UserId + 目标系统` 维护，不写入员工、Tool 或 MCP 绑定；实际调用时由对接层按已验证用户和目标系统取得，不进入 Prompt、Agent 状态或授权规则本身。

MCP 连接如需服务密钥，该密钥也由凭证管理部分提供；它不是某位用户的外部业务 Token。仅更换密钥值不修改员工能力修订；若连接目标、服务身份、授权范围或认证方式发生变化，须按配置变化审核。MCP 新工具只有在管理员选择、登记、绑定到员工草稿并发布后才进入员工能力；已有工具 schema 或行为变化产生新修订，不静默影响旧 Run。

目标系统需要认可智慧大脑的服务身份和代用户获取凭证的方式；手机号只是定位线索，不足以要求对方签发 Token。具体签发、刷新和目标系统的最终授权，要在接入各系统时协调。若 Token 获取失败，平台登录和不依赖该系统的工作仍可继续。

具体接入还须维护稳定的 `UserId + 目标系统 + 外部账号` 对应关系，并处理手机号变更、外部账号解绑或重绑、凭证撤销和过期。不能因为两个平台账号先后使用同一个手机号，就把旧用户的外部 Token 交给新用户；实际调用时复核凭证归属。

## 9. 模块职责与当前骨架的后续收敛

| 模块 | 在这份设计里的职责 |
| --- | --- |
| `api` | 处理登录、Web 请求和第三方 webhook 协议；不把请求体自称的用户身份当作认证结果 |
| `platform.channel` | 把已验真的外部渠道身份映射到稳定 `UserId`，处理绑定、路由与会话归属 |
| `platform.employee` | 管理员工、发布版本和 `CapabilityBinding`；给出可装配能力，不替用户作最终授权 |
| `security` | 账号、密码与登录状态；角色、范围、资源所有者与动作判定；确认和撤销规则；输出允许、拒绝或需要确认及原因 |
| `platform` 的 Run/资料/成果职责 | 保持 `UserId`、Session、Run 与资源归属；组织授权时点和可审计的执行事实 |
| `runtime-agentscope` | 用平台传入的身份和受限能力执行；所有实际工具路径接入统一的检查边界 |
| `infrastructure` | 保存授权事实、提供受控文件/知识访问与外部凭证适配；不自行制定产品权限 |

当前骨架已有 `AuthorizationService.decide(Subject, Resource, Action)`、`TaskGrantService`、`PolicyDecision`、`ApprovalRepository` 和 `CapabilityBinding`，但仍只是粗粒度契约，不能据此认定授权已生效。`PolicyDecision.APPROVE` 含义不明确；`ApprovalRepository` 当前只按 taskId 和 action 查询，不能证明确认针对哪个 Run、资源和参数。详细设计须明确“允许”“拒绝”“需要本次确认”，将确认事实绑定一次待执行操作并在恢复时复核、一次性消费；还须补齐可信资源归属、Run 上下文，以及所有实际工具路径的不可绕过检查。现有 `Subject.tenantId` 需按单公司模型校准。

## 10. 用这些场景验收权限骨架

1. 张三使用预置员工，请它总结李四的历史 Session：即使 Agent 知道 Session ID，资料读取也应拒绝。
2. 员工绑定了取消订单 Tool，但张三只有查询权限：可以查询授权范围内的订单，取消被拒绝；张三点击“确认”也不能使取消变成允许。
3. 张三原有取消权限，某次操作正在等待确认；管理员撤销权限后张三确认：恢复时重新判定并拒绝。
4. 同一个 MCP 服务新增了高风险 Tool：服务连接或员工旧版本存在，不自动开放新业务动作。
5. 子 Agent 获得整理订单报告的任务：只能访问交付给它且张三有权访问的资料，不继承其他用户的 Workspace。
6. 外部系统 Token 有效但平台权限不足，或者平台允许但目标系统拒绝：两种情况都要明确失败来源，不将 Token 当授权证明。
7. 普通用户从已绑定的消息渠道发起同一工作：按同一 `UserId` 判断权限；仅在消息正文写手机号无法访问该用户资料。
8. 管理员把某个外部查询动作加入普通用户默认权限，未加入的其他查询仍不可用；员工已绑定 Tool 也不改变这条规则。
9. 张三可检索已绑定的公司公共知识源；他上传的私人资料只归自己，李四不能通过同一员工或知识检索读到。
10. 张三的外部 Token 过期并刷新：员工发布版本、Tool 和 MCP 绑定保持不变；适配层从独立凭证管理职责取得更新后的 Token。
11. MCP 服务发现新工具：仅管理员可在审查后选择登记，再绑定草稿和发布；已发布员工不会自动获得该工具，普通用户也不会因此自动获得对应业务权限。
12. 通用 MCP 或 HTTP 工具无法从实际参数确定全部动作和目标：登记或调用拒绝；改工具名、修改自报 schema、转给子 Agent 均不能绕过。
13. 查询接口返回列表、总数或聚合结果，或检索源含他人私有片段：无权内容及数量信息不能进入模型；来源无法在请求前收窄范围时不向普通用户开放。
14. 张三确认取消订单 A 后，Agent 改为取消订单 B、修改数量或重复提交确认：旧确认失效或已消费，不能执行变更后的操作，也不能重复提交原操作。
15. 账号或工具在调用发出前停用：调用拒绝；已发出的外部请求按真实结果记录，不虚构为自动撤销。

## 11. 留给下一轮的产品决策

1. **外部只读动作的具体清单**：逐项评估、由管理员标记为普通用户默认权限的规则已确认；各接入系统哪些查询动作符合条件，待实际对接时确认。
2. **外部写动作的分级**：哪些需要用户本次确认，哪些还需要业务审批；确认展示的目标、影响及有效期如何表达。
3. **共享与部门范围**：什么时候引入 Group、部门 Scope 与他人资源共享；一期仍遵循个人资源默认私有。
4. **任务授权**：哪些场景确实需要一次性授权或委派；谁能签发、如何撤销，以及与原有用户权限的关系。

首条可运行链路至少验证：发布版本与能力修订固定、全部实际工具路径经过平台检查、外部查询按可信范围收敛、撤销后新调用被拒绝，以及外部系统拒绝与结果不确定时如实记录。若接入动作配置为需要确认，还必须验证确认绑定一次具体操作；[首个 Mock 会议室预定详细设计](../05-业务闭环/会议室预定首个业务闭环详细设计.md)已确认在明确单笔请求且单独授权的条件下不增加二次确认，不能推广到真实系统。无法通过相应验证的能力先不对普通用户发布。

先定这些产品规则，再设计接口、权限存储和 AgentScope 适配细节，才不会把“工具已经接入”误当成“行为已经安全授权”。
