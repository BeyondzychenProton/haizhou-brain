### 缺陷 A：计划投影在真机上永不产出（已修复）

**现象**：模型确实调用了 `plan_write` 且执行成功，但没有任何 `PLAN_SNAPSHOT` 事件。

**定位过程**：应用日志显示 `Toolkit - Registered tool 'plan_write'`（工具已注册）与 `AgentTraceMiddleware - POST_ACTING | name=plan_write, state=SUCCESS`（调用成功），说明问题不在工具装配或模型。随后在事件翻译器的未匹配分支加临时 DEBUG 日志，采集真实事件类型分布：

```
49 TOOL_CALL_DELTA        ← 有
 0 TOOL_CALL_START        ← 没有
 0 TOOL_CALL_END          ← 没有
 1 TOOL_RESULT_END        ← 实际可用的收尾信号
```

**根因**：原实现依赖 `ToolCallStartEvent` 建缓冲、`ToolCallEndEvent` 产出，而 Harness 的事件流**只发入参增量**，从不发 START/END。

**修复**：改为对所有 `ToolCallDeltaEvent` 建缓冲（入参增量可能不携带工具名），在 `ToolCallEndEvent` **或** `ToolResultEndEvent` 时按工具名结算；工具名优先取增量携带的名字，其次取结束事件的名字；即使没有入参增量，只要结束事件表明是计划工具也产出阶段事件。补充了 3 个覆盖真实事件流形态的用例（含"增量为空"与"无工具名"两种边界）。

**修复后真机复验**：`PLAN_SNAPSHOT` 正确产出，内容为从入参派生的完整计划（"# 三步执行计划 / ## 目标 / ## 步骤 …"），并在同一事务投影到会话游标。

### 缺陷 B：会话忙时渠道入站抛唯一约束异常（已修复）

**现象**：探针首次运行报 `Duplicate entry '…-1' for key 'platform_agent_run.uk_platform_agent_run_session_active'`。

**定位过程**：先以为索引与迁移不一致，逐版追查后确认**不是环境问题而是产品有意设计**：

| 迁移 | 动作 |
| --- | --- |
| V6 | 建 `active_marker` 生成列 + `uk_platform_agent_run_session_active`（唯一） |
| V8 | `DROP INDEX` 该唯一索引——注释写明"Allow several queued Runs for one Session" |
| **V10** | `DROP COLUMN` 后重建 `active_marker`（活动状态集合纳入 `WAITING_TOOL`）并**重新 `ADD UNIQUE KEY`** |

即 V10 之后平台在数据库层**强制"每个会话同一时刻只有一个活动 Run"**，`active_marker` 对活动状态取 1、终态取 NULL，因此终态 Run 可以有很多个、活动 Run 只能有一个。

**根因**：`JdbcChannelTurnStore.accept` 直接调用 `SessionApplicationService.createRun`，会话忙时撞唯一约束并抛出，违背了端口契约的明确要求——`ChannelAcceptance` 注释写着"runId 为空表示已受理，正排在当前活动 Run 之后等待"。

**修复**：受理前先判断该会话是否已有活动 Run（判定集合与 `active_marker` 生成列严格对齐），有则只写收件箱并返回 `runId=Optional.empty()`，把"等待中"如实表达出来。

**遗留**：等待中的收件箱记录目前**没有提升机制**（谁在 Run 结束后把等待消息变成 Run 尚未实现），已列入待跟进。
