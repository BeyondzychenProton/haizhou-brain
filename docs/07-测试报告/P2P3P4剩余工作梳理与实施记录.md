## 一、盘点：实际状态与文档阶段描述的差异

盘点时发现两处与"按阶段编号推测"不同的实际情况，先纠正：

1. **P3 并非零起点**：`haizhuo-brain-platform/.../platform/channel/` 下已有 9 个**端口契约**
   （`ChannelIngressService`、`ChannelTurnStore`、`ChannelDeliveryOutbox`、`ChannelOutboundSender`、
   `ChannelAccountDirectory`、`ChannelIdentityDirectory`、`VerifiedChannelMessage`、`ChannelAccountBinding`、
   `ChannelAcceptance`/`ChannelDelivery`），且契约注释已经写死了关键约束
   （"实现必须把收件箱、Session 与待执行 Run 一起提交"、"在数据库层强制 (binding,event) 唯一"、
   "每个 Session 只有一个活动 Run"、"含短期密钥的回复目标必须加密或带过期时间存储"）。
   但**没有任何实现、没有表、没有 Controller、没有框架 Channel 适配**。
2. **P2 的"Delivery outbox 与可见性规则"与 P3 的 outbox 是同一件事**，因此合并实施，不再分两次。

## 三、本轮实施内容

### P2-1 会话游标保留窗口

- `SessionEventPage`（新增）：事件 + `cursorFloor` + `cursorExpired`。
- `SessionRunStore` 新增 `oldestSessionCursor`（保留下界，0 表示从未裁剪）与 `trimSessionEvents`（按保留条数裁剪）。
- `SessionApplicationService.sessionEventPage(...)`：判定 `requested > 0 && floor > requested + 1` 才算失效——请求游标恰好位于下界前一条时仍可无缝续传。
- `GET /api/v1/sessions/{id}/events` 改为返回分页信封；前端 `syncSessionEvents` 在收到失效时清空本地时间线并从 0 全量补读。
- 裁剪实现分两步（先取边界再删除），避免依赖 MySQL 与 H2 一致支持的自引用删除子查询；并发写入只会让边界更大，因此只可能少删、不会误删。

### P2-2 `plan.snapshot`

- `HarnessAgentFactory` 打开 `.enablePlanMode()` 与 `.planFileDirectory("plans")`——计划能力直接来自框架，未自研。
- `AgentPlanUpdatedEvent`（新增）：`phase`（ENTER/WRITE/EXIT）+ `plan`。
- `AgentScopeEventTranslator`：按 `toolCallId` 缓冲计划工具的**流式入参**，在工具调用结束时解析成计划正文；`ToolCallStartEvent` 就建立缓冲，因为 `plan_enter/plan_exit` 可能完全没有入参；Run 终态统一清理残留缓冲。
- `RunExecutionStore.recordPlanSnapshot`：只校验租约与 fence、不改尝试状态，与 run 事件同一事务写入并同步会话投影。
- `RunExecutionService`：只落有正文的 WRITE；落库失败被吞掉，不影响业务终态。
- 前端：`PLAN_SNAPSHOT` 按 `${runId}-plan` 合并成一张计划卡片（同一 Run 只留最新）。

### P3 渠道底座

- **V15 迁移**：`platform_channel_account` / `_identity` / `_conversation` / `_inbox` / `_delivery`。
- `JdbcChannelTurnStore`：锁账号行串行化受理 → 查重（命中即返回 `duplicate=true`）→ 查/建会话映射 → **复用 `SessionApplicationService.createRun`**（排队与幂等由它保证）→ 写收件箱。
- `JdbcChannelDeliveryOutbox`：`enqueue` 按幂等键去重；`claimNextDelivery` 用状态翻转认领（`PENDING/RETRYABLE_FAILURE → SENDING`）；`recordOutcome` 区分已投递/可重试/永久失败/结果不确定。
- `JdbcChannelReplyEnqueuer`：由会话映射反查渠道与回复目标，幂等键 `runId:reply`。
- `ChannelDeliveryWorker`：认领 → 找 provider 发送器 → 记录结果；无发送器记永久失败，发送抛异常记结果不确定。
- `JdbcChannelAccountDirectory` / `JdbcChannelIdentityDirectory`：只读；身份只认 `LINKED` 且必须与账号同租户。
- `PlatformChannel`（bootstrap）：复用框架 `Channel` 边界，入站翻译成平台受理，出站委托给可选的直接投递消费者；**不让 Gateway 直接驱动 Agent**，避免出现两套 Run 状态机。
- `ChannelConfiguration`：装配入站受理服务；出站刻意不自动调度，避免在无发送器时把投递误标为永久失败。
