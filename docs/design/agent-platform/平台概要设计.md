## 1. 产品目标与初版范围

平台提供一个统一工作助手，基于 AgentScope Java 执行。用户在个人 Workspace 中，通过持续会话使用 Skills 或专业 Agent 完成工作。会议是第一种业务能力，系统围绕通用工作过程组织。

每个用户自动拥有一个默认的个人 Workspace，不依赖用户本地目录。用户可以直接描述需求，由统一助手选择能力；也可以主动指定 Skill 或专业 Agent。专业 Agent 按当前任务参与，完成后返回统一助手，后续仍由统一助手协调。

### 初版纳入

- 平台统一接入模型，预置 Agent、Skills 和工具。
- 上传资料、持续对话、查看执行进度和获取产物。
- 统一助手直接执行，或顺序委派专业 Agent。
- 执行中的必要追问、操作确认、取消、抢占、补充当前执行、回应系统等待及结果查询。

### 初版暂不纳入

- 跨会话自动积累的个人长期记忆。
- 用户自建 Agent 或自行维护 Skills。
- 多 Agent 并行协作。
- 多人共享 Workspace。
- 全量配置快照与完整执行回放体系。
- 用户删除资料或产物、回收站功能；归档隐藏尚未确认，不默认纳入。

## 2. 核心概念

| 概念 | 职责 |
| --- | --- |
| Model | 平台管理模型接入，供 Agent 选择使用 |
| Agent Profile | 定义角色、指令、默认模型、可用 Skills、工具和委派范围 |
| Skill | 可复用的工作指引，包含适用场景、步骤及必要参考资源 |
| Tool | 执行具体操作，例如读取资料、检索内容、生成文档 |
| Workspace | 用户个人资料、会话和产物的归属空间 |
| Session | 用户与统一助手的一段持续交互，保存工作上下文 |
| Run | 一次具体执行，管理进度、等待、完成、失败和取消 |
| Artifact | 执行生成的持久成果，例如纪要、报告或表格 |

Agent Profile 是共享的配置定义。不同用户即使使用相同 Profile，也拥有独立的会话与数据。

业务 Task 暂时作为目标和工作计划理解，可以跨多个 Run，不承担运行生命周期管理。系统不需要在每次执行前先准确判定输入属于新业务任务还是旧业务任务。

```text
用户
└── 个人 Workspace
    ├── 资料与产物
    └── Session：与统一助手持续交互
        ├── Run：一次执行
        │   ├── 使用 Agent Profile 的有效配置与模型
        │   ├── 按需加载 Skills、调用 Tools
        │   └── 必要时委派专业 Agent，返回结果
        └── 后续 Run：沿用相关上下文继续工作
```

## 3. 基于 AgentScope Java 的分工

| 部分 | 主要职责 |
| --- | --- |
| 平台管理 | 用户与 Workspace、模型接入、Agent Profile、Skills、工具登记、文件与产物 |
| 执行协调 | 接收输入、创建 Run、解析配置、组织上下文、检查权限、保存状态并向前端提供进度 |
| AgentScope Java 运行层 | 构建 Agent、执行模型与工具循环、加载能力、执行专业 Agent 子任务、输出运行事件 |

在现有工程边界上补齐平台模块，以下均为目标职责：

- 新增 `haizhuo-brain-platform`，内部划分能力配置、资源管理、会话管理和执行协调；初版不再拆成多个 Maven 模块。
- `haizhuo-brain-runtime-api` 提供平台侧运行契约。
- `haizhuo-brain-runtime-agentscope` 负责 AgentScope Java 的适配与实际执行。
- `haizhuo-brain-security` 承接权限判断与操作确认相关能力。
- `haizhuo-brain-observability` 承接执行观测，采用 Langfuse 实现；接入方式与版本待验证。
- `haizhuo-brain-infrastructure` 承接持久化与外部基础设施适配。
- `haizhuo-brain-meeting` 承载首个会议业务场景。

以上是已确认的职责承接方向，不表示相关模块已实现完整功能。具体模块依赖、数据归属及适配边界见[整体工程架构草案](平台整体工程架构.md)；类、接口与存储结构仍在详细设计时确定。

平台中的 Session、Workspace、Run 保持自己的业务含义，与 AgentScope 的会话状态、运行上下文建立映射。平台负责资源归属、配置选择和授权，运行适配层负责将有效配置转为可执行的 AgentScope 对象。

### 3.1 初版运行部署方式（已确认）

采用单体应用内执行：Run 状态持久化，通过有并发上限的内部执行器调度 AgentScope Java。初版不引入消息队列，不拆分独立执行服务。请求接收、调度和执行保持职责分离，为后续扩展保留边界。

执行并发不足时需要处理资源等待，但这与同一 Session 内普通新任务排队是不同的问题；后者暂未确认为初版功能。具体并发额度、等待容量和超时策略在详细设计时确定。

### 3.2 工具权限与操作确认（已确认）

工具定义配置所需权限及确认要求，Agent Profile 限定可用工具和范围；实际调用时结合用户权限、资源范围与有效授权执行检查。没有权限直接拒绝，不能通过用户确认突破权限。

所有 Agent 工具调用统一经过平台检查入口，`security` 提供授权与确认判断，实际业务操作由能力所属分区或模块执行。确认后仍须检查权限撤销、工具停用和授权有效性，工具获准调用也不能绕过资源归属、版本冲突等业务规则。业务澄清与操作审批分别处理，框架权限机制不能代替平台授权。

## 4. Agent 与 Skills 的组织

### 4.1 统一助手与专业 Agent

统一助手是能直接完成工作的通用助手，负责理解需求、选择能力、协调执行和交付结果。直接执行不限于简单工作，复杂工作也可通过组合 Skills 和工具完成，不因步骤多就必须委派。

专业 Agent 用于需要独立上下文、专属模型或工具范围的子任务。委派时提供明确目标、相关资料和必要上下文；完成后返回处理结果与产物引用，统一助手保持整体协调权。

用户主动指定能力时，将该选择作为当前工作的执行约束，仍由统一助手协调和交付。专业 Agent 的独立上下文不意味着获得所属 Workspace 的全部访问权限。

主 Agent 负责整体交付，专业 Agent 负责受托的局部任务。委派提供目标、必要上下文、约束和预期产物，不默认传入整个 Session；返回结果、产物引用以及未完成或无法验证的部分。主 Agent 对照原始要求检查和汇总，不把子 Agent 结束直接当作整体工作完成。专业 Agent 需要澄清或新增授权时，由主 Agent 统一面向用户提出。

### 4.2 能力划分原则

1. 新增格式、方法或标准流程，优先增加 Skill。
2. 需要独立处理子任务、隔离上下文或配置专属模型与工具范围时，再增加专业 Agent。
3. 专业 Agent 复用 Skills，避免重复维护同一套工作指引。

步骤多并不必然需要专业 Agent。必须严格执行的业务顺序和规则，由程序或确定性流程保证，不能只依赖 Skill 中的文字指令。

### 4.3 能力发现与模型选择

Skills 按需加载：先向 Agent 提供名称与适用场景，选中后加载完整指引。工具操作由运行中的 Agent 发起，工具服务负责实际执行。

Agent Profile 需要说明自身职责，以及何时适合被委派、需要什么输入、预期返回什么结果，供统一助手选择。

每个 Agent 配置默认模型。Skills 沿用执行它的 Agent 的模型，不单独设置模型。模型接入由平台统一管理。

优先发现并组合已有、已授权的能力。Skill 是可复用的方法，不是执行入口的必需条件；没有匹配 Skill 时，主 Agent 也可使用已有工具完成工作。真正需要新增工具、外部连接或权限时，进入独立的配置与授权流程，不把发现能力等同于扩充权限。

用户明确指定 Skill 后，主 Agent 可以按需补充其他 Skills 来完成原目标，但不能擅自替换指定方法、扩大范围或获得额外权限。存在实质冲突或指定能力不可用时，说明限制并按需澄清。

### 4.4 主 Agent 准备与需求理解（已确认）

本阶段以 Hermes 的上下文准备与主 Agent 循环思路为参考，运行基础仍为 AgentScope Java。职责划分为“主 Agent 准备、上下文关联、需求理解、下一步选择”，不要求拆成四个独立 Agent 或四次固定模型调用。

- 平台准备确定信息：主 Agent 配置、当前输入、会话历史、明确引用的附件与产物，以及允许使用的能力；平台保证资源身份、归属和权限。
- 主 Agent 负责语义判断：理解目标与约束、关联指代、识别信息缺口，决定直接处理、读取资料、加载 Skill、委派专业 Agent 或追问。
- 上下文按需补充，允许根据新信息修正理解；不要求执行前找齐所有资料，也不设置每次请求必须经过的独立业务意图分类阶段。

操作意图（发送、补充、取消、抢占、回应等待）继续由显式操作表达，与主 Agent 理解的业务意图区分。

### 4.5 首次上下文范围（已确认）

| 上下文 | 默认提供内容 |
| --- | --- |
| 当前请求 | 用户原始输入、明确指定的 Skill 或 Agent |
| 会话背景 | 当前 Session 的最近对话；历史较长时使用摘要保留关键目标与约束 |
| 工作对象 | 本次附件、明确引用的产物，以及近期成果的简要说明与引用 |
| 可用能力 | Skills、专业 Agent 和工具的必要描述 |

大文件正文、当前 Session 较早的完整历史及个人资料库内容，由主 Agent 按需获取，不在每次请求中注入整个 Workspace。上述按需获取不改变历史会话默认隔离的原则，也不引入跨会话自动记忆。工作对象的引用不意味着默认加载其全部正文。

主 Agent 判断资料相关，不等于获得访问授权。最近对话的范围、摘要更新与准确性、引用消歧、能力目录大小及上下文预算等策略后续继续细化；本节仅确定概要职责和输入范围。

### 4.6 显式引用与历史检索（已确认）

- 用户明确引用附件、产物或 Skill 时，平台先解析并校验引用，将对应对象的必要内容或可访问引用带入执行，不只把对象名称留给模型猜测。
- 用户引用 Skill 时加载相应工作指引；引用工作资料不代表默认加载全部正文。引用不明确、失效或无权访问时，明确反馈，不能默默替换对象。
- 参考 Hermes 的 `session_search` 思路，提供按需检索原始会话内容的能力，用于上下文压缩后回查来源、约束和历史结论。摘要不替代原始记录；原始记录的保存期限与检索实现待详细设计确定。
- 初版检索范围限定为当前 Session，不因提供历史检索而开放跨 Session 访问或自动长期记忆。

### 4.7 信息不足与澄清（已确认）

不影响核心结果、容易修改的细节，可以采用合理默认并说明；会改变目标、处理范围或影响外部操作的关键信息，先向用户澄清。缺失事实不能靠猜测补齐。例如会议纪要缺少负责人时可标注“待确认”，实际分派任务前则必须明确负责人。

参考澄清工具的交互方式，由主 Agent 提出必要问题，平台将问题组织为可回应的等待点，用户回答后继续原 Run。澄清与操作审批分别处理，回答业务问题不自动构成操作授权；等待与继续仍须按第 9.1 节验证 AgentScope Java 支持范围。

### 4.8 按需规划与执行调整（已确认）

- 简单且明确的工作直接执行；复杂、多步骤工作建立简短计划，继续执行并按实际进度更新，不强制每次先等待用户批准计划。
- 用户明确要求“先出方案，不要执行”时，仅完成必要了解与计划交付，不执行所规划的工作，等待进一步指示。
- 计划确认不替代后续操作授权。存在关键歧义、需要新授权或用户要求先确认时，才进入对应等待。
- 目标与范围不变时，可以自行调整方法和步骤，必要时简短告知；改变交付内容、扩大范围或需要新授权时，先确认。
- 某一步受阻时，继续完成不受影响的部分，保留成果并说明缺口，不擅自降低要求后宣称全部完成。

计划用于组织执行和沟通，不展示内部推理，也不要求单独的规划 Agent 或固定规划模型调用。允许调整完成工作的路径，不允许自行改写用户目标。

### 4.9 自检与统一交付（已确认）

默认由主 Agent 根据用户要求和 Skill 做必要自检后直接交付，不把用户验收设为每次 Run 结束的必经步骤。有明确要求的工作，再增加专门检查或确认；不默认增加独立验收 Agent。

- 主 Agent 检查内容是否满足目标、格式、指定方法和交付要求。
- 平台及工具提供真实执行结果，例如文件是否保存、导出是否成功，不能仅凭 Agent 的描述认定操作成功。
- Skill 可描述本类工作的交付要求、必要检查和缺失信息处理方法；专业 Agent 的结果由主 Agent 汇总检查。
- 未完成、失败或无法验证的部分明确说明，保留已完成成果；自检受执行预算约束，不无限重试或反复润色。

Run 结束与业务目标全部达成分别理解。本节不新增具体状态字段，状态表达与检查机制在详细设计时确定。

本阶段整体覆盖准备、上下文关联、需求理解、选择与执行、自检交付。这些是职责边界，不是固定流水线，不要求拆成五个 Agent 或五次模型调用。

## 5. Workspace 与执行环境

Workspace 是平台里的个人资源空间，组织用户上传的资料、保存的文件、Session 和生成的产物。

本文的 Workspace 是平台业务概念，**不等同于 AgentScope Java 的 Harness Workspace**。后者组织 Agent 指令、Skills、工具配置及工作文件，并非仅用于存放临时文件；可以由服务端本地、远程或沙箱存储承载。平台 Agent Profile 是本项目的配置定义，其内容与框架配置有交集，但不要求与个人 Workspace 一一绑定。

框架续接用的 `AgentState` 由独立的 `AgentStateStore` 保存，不是 Workspace 文件。采用 Harness 不改变本平台的资料归属、Session 隔离和产物规则，也不自动纳入跨会话记忆。官方定位、证据及与平台设计的重叠评估集中见[整体工程架构第 5.1 节](平台整体工程架构.md#51-官方-harness-workspace-的定位官方能力核查)；具体复用方案仍待验证。

已确认采用“平台管理业务规则、框架机制优先复用”的工程方向：平台保留配置发布、权限、资源归属、产物版本及 Run 生命周期；配置加载、Skills 发现、上下文压缩、等待续接和委派等优先验证复用框架能力，避免两套独立机制。平台发布配置是业务依据，框架配置文件不能成为不受控的第二来源；具体接入和存储映射仍待验证，不改变初版范围。

资料的持久保存与运行时使用范围分别管理：

| 资料 | 默认使用规则 |
| --- | --- |
| 当前会话上传的资料 | 默认用于当前 Session，用户主动存入资料库后供后续会话按需引用 |
| 个人资料库内容 | 用户主动保存的长期资料，按需选择或检索后使用 |
| 历史会话 | 默认不跨 Session 读取 |
| 执行产物 | 保存到 Workspace，关联来源 Session 和 Run |

AgentScope 通过平台提供的资源工具访问内容。系统根据用户身份、资源归属与实际授权约束访问，不把整个 Workspace 的内容自动注入模型上下文。

执行环境承载文件处理或程序运行，与个人 Workspace 分开管理。初版可以使用后端工具服务；需要执行脚本、文档转换等工作时，再采用受控的服务端环境。用户无需提供本地目录。

### 5.1 会话附件与个人资料库（已确认）

会话附件默认作为当前工作的材料，不自动进入个人资料库。用户主动“存入资料库”后，作为长期资料供后续会话按需引用。两者区分产品用途与使用范围，底层可以引用同一份文件，不要求复制；具体存储方式留待详细设计。

未存入资料库不意味着立即删除，也不意味着无限期保存。附件保存期限、临时文件清理和数据保留策略后续单独确定。

### 5.2 产物身份、版本与衍生关系（已确认）

同一成果保持稳定身份，内容修改生成新版本并保留原版；明确另做一份或生成新的衍生成果时，创建独立产物并保留来源关联。

| 用户需求 | 产物处理 |
| --- | --- |
| 精简刚才的纪要 | 同一产物的新版本 |
| 将纪要导出为 PDF | 对应内容版本的另一种文件格式，不视为内容修改 |
| 基于纪要生成行动项表格 | 独立产物，关联来源纪要版本 |
| 另外做一份适合客户的纪要 | 独立产物，保留来源关联 |

产物版本与来源 Session、Run 关联；格式文件关联其对应内容版本，不因后续修改而混淆交付依据。本节确定产品语义，不预设版本存储结构。

### 5.3 跨会话引用与修改授权（已确认）

- 新会话不自动读取其他会话；用户可以主动从个人资料库或历史产物中选择对象带入当前会话。
- 引入对象仅带入其内容或可访问引用及必要来源说明，不自动带入原会话的全部聊天和附件，不扩展当前 Session 原文检索的范围。
- 默认引用用户选择时的具体版本，来源后续更新不静默替换当前工作的依据。
- 引用只表示将对象用于当前工作，不等于授权修改原产物。明确要求“继续修改这份纪要”时，可更新原产物并生成新版本，不因跨会话而强制复制。
- 要求参考原成果生成周报等新内容时，创建独立产物并关联来源。意图不明确且可能影响原成果时，先澄清。

跨会话修改产生的新版本记录本次 Session 和 Run，仍遵守资源权限及下述并发冲突规则。

### 5.4 草稿与正式交付（已确认）

- 中间草稿、临时转换文件不全部展示为正式产物。
- 达到可交付状态后，保存为产物或新版本，再向用户提供；“正式”不表示必须经过用户验收，仍遵守第 4.9 节的默认自检交付规则。
- 执行失败或取消时保留已有正式成果；有用但未完成且已保存的内容，可作为“未完成草稿”查看，不冒充正式版本。
- 修改过程中不覆盖上一份可用版本，不因新版本生成失败导致原成果丢失。

草稿保存时机、展示方式及清理策略在详细设计时确定，不承诺任意中间状态均已持久化或可恢复。

### 5.5 并发修改冲突（已确认）

同一 Session 只有一个活跃 Run，不代表不同 Session 不会修改同一产物。各次修改基于各自开始时选定的版本；提交新版本时，如果原产物已被其他执行更新，需要识别冲突。

不静默覆盖，也不自动合并。保留双方成果，由用户选择将冲突修改另存为独立产物，或基于最新版重新修改。具体冲突交互及提交控制在详细设计时确定，不预设锁或数据库实现。

### 5.6 删除与保留范围（已确认）

初版暂不开放用户删除资料或产物，也不引入回收站。归档隐藏尚未确认，不默认作为删除的替代功能纳入。临时文件清理与数据保存期限后续单独确定；暂不开放删除不等于承诺所有数据永久保存。

## 6. Session 与 Run 生命周期

### 6.1 典型执行流程

1. 用户在 Session 中发送需求，可附带文件或指定能力。
2. 平台创建 Run，确定有效配置及可访问资源。
3. AgentScope 运行统一助手，理解需求并选择能力。
4. 统一助手直接使用 Skills、Tools，或顺序委派专业 Agent。
5. 平台持续记录执行事件，向用户展示必要进度。
6. 如需补充信息或确认操作，执行进入等待状态；用户回应后继续。
7. 完成后保存结果与产物，结束本次 Run，Session 继续保留。

### 6.2 状态与输入归属

Run 概要上区分：待执行、执行中、等待输入、等待确认、完成、失败和取消。

每个 Session 同时只允许一个活跃 Run，等待状态仍属于活跃 Run。回应系统等待的输入关联原 Run；执行完成后的追问开启新 Run，并沿用相关上下文。

以下四项交互控制纳入初版，具体实现需在详细设计阶段验证：

| 能力 | 目标行为 | 待细化边界 |
| --- | --- | --- |
| 取消 | 停止当前 Run，保留已完成动作与结果 | 取消请求与实际停止分开记录；已发生的外部操作不自动回滚 |
| 抢占 | 请求停止当前 Run，确认停止后再执行替代请求 | 旧 Run 仍可能修改资源时，不启动替代 Run；不可立即取消的操作需要明确等待状态 |
| 补充当前执行 | 新要求关联当前 Run，在可控执行边界生效 | 生效时点、输入顺序、接收确认，以及要求到达时 Run 已结束的处理 |
| 回应系统等待 | 回答或审批结果关联对应等待点，继续原 Run | 等待点标识、重复或过期回应、等待超时及资源释放方式 |

以上是平台行为要求，不代表 AgentScope Java 原生支持全部控制。普通新任务的排队尚待确认；输入意图采用下述已确认的显式操作方式。

同一业务目标可以经历多个 Run，例如生成纪要、精简纪要、提取行动项。平台分别记录每次执行，无需强制建立新的业务 Task。

等待中的 Run 仍占用 Session 的活跃位置；当前执行片段安全结束且平台等待记录与框架续接状态可靠保存后，释放执行名额。问题可以提前展示、回应可以提前保存，但不能提前恢复执行；有效回应后原 Run 重新申请名额，期间显示“等待继续”。等待点取消、失效或重复回应不得导致重复继续。

状态保存失败时暂不允许继续，对可安全重试的保存操作做有限重试；仍失败则结束本次执行尝试、关闭继续入口，保留已有内容和成果。实际执行结束且有限收尾完成后释放名额，不因保存失败无限占用资源，也不假报终态已保存。具体职责与待验证边界见[整体工程架构第 8 节](平台整体工程架构.md#8-交互控制与执行资源已确认设计实现待验证)。

#### 输入意图与网页交互（已确认）

网页通过明确的操作类型表达用户意图，服务端根据操作类型及实际运行状态处理，不依赖自由文本猜测是否抢占。

| 当前状态 | 用户操作 | 平台行为 |
| --- | --- | --- |
| 没有活跃 Run | 发送 | 创建新 Run |
| 正在执行 | 补充要求 | 输入关联当前 Run，在安全执行边界应用 |
| 正在执行 | 停止 | 请求取消，显示“正在停止”；确认执行结束后显示“已停止” |
| 正在执行 | 停止并发送 | 保存替代请求，确认旧 Run 停止后再启动新 Run |
| 等待用户回答 | 提交对应问题的回答 | 回应原 Run 的等待点，继续执行 |
| 等待操作确认 | 允许或拒绝 | 决定关联原 Run 的确认点；拒绝后的处理由具体操作规则决定 |

执行期间，普通输入框将“发送”改为“补充要求”，并提示“将用于当前工作”；“停止并发送”提供独立操作入口。

- 补充输入区分“已接收，等待应用”与“已应用”；只有运行时实际读取后才标记已应用。
- 控制操作关联具体 Run，回答和审批同时关联对应等待点。若补充到达时原 Run 已结束，保留输入并提示重新发送，不自动作用于下一次执行。
- 操作确认通过对应入口提交；自由文本“好的”等不自动解释为允许操作。
- 网页表达意图，平台校验并管理状态，AgentScope 适配层落实控制。补充生效边界及停止确认机制仍须按第 9.1 节验证。

### 6.3 状态持久化与恢复边界

页面断开与执行结束分别处理；刷新页面后可以重新查询执行状态。Session 保存持续上下文，Run 保存执行状态与必要过程记录，Artifact 保存成果及来源关联。

服务进程故障后，已持久化的结果应保留。能否从中间步骤恢复取决于 AgentScope 状态保存能力与工具特性，详细设计时核实。不得默认重放具有外部副作用的操作；恢复时需要识别已执行动作，具体幂等与检查点策略后续细化。

#### 断线、重复提交与服务重启（已确认）

| 情况 | 初版处理原则 |
| --- | --- |
| 网页断开或刷新 | 不自动取消 Run；重新进入后恢复状态与已有内容 |
| 提交后未收到响应 | 先查询该请求是否已被接收，避免直接重建 Run |
| 网络重试或重复点击 | 同一次提交只执行一次；取消、补充、抢占、回答和审批等控制操作也需防止重复处理 |
| 服务进程重启 | 区分可恢复和无法恢复的执行；无法恢复时明确展示“执行中断”，不盲目重做外部操作 |

网页断线时服务端可能仍在执行；服务进程重启后则需要重新检查执行是否能够恢复，两者不能使用同一套假定。请求去重与恢复机制不等于对外部工具副作用提供恰好一次的执行保证。请求标识、去重边界、历史内容补齐和重启后的状态收敛方案在详细设计时确定，框架恢复能力按第 9.1 节验证。

### 6.4 网页执行过程展示（已确认）

初版展示以下三类信息：

| 类型 | 展示内容 |
| --- | --- |
| 整体状态 | 等待执行、执行中、等待回答或确认、正在停止、完成、已停止、失败或执行中断 |
| 关键动作 | 正在读取材料、使用某项 Skill、委派专业 Agent、生成产物，以及对应的简要结果 |
| 控制反馈 | 补充要求是否已接收、是否已应用，取消是否真正完成 |

关键动作基于实际发生的执行事件展示，不展示模型内部推理。“已接收”与“已应用”、“正在停止”与“已停止”分别表达，不以请求提交成功替代实际执行状态。具体事件映射与推送机制留待详细设计。

#### 内容分类与过程聚合

参考 OpenCode 的消息片段、工具状态和折叠分组思路：过程可追踪，但不逐调用刷屏；重要结果和需要用户参与的事项始终清晰可见。

| 内容 | 默认呈现 |
| --- | --- |
| 助手说明与最终答复 | 对话正文，支持流式展示；工作说明不作为操作成功的证明 |
| 连续读取、检索等动作 | 聚合为简短过程组，展示状态与数量，具体动作按需展开 |
| 生成或修改的产物 | 独立成果卡片，关联具体版本，支持相应预览、下载和继续修改入口 |
| 澄清、授权及影响交付的异常 | 明确展示问题或影响与有效操作入口，不藏在折叠详情中 |

同一动作的状态变化更新原展示项，不为开始、进展、完成分别新增聊天消息。后端提供可关联身份、类型和状态的工作记录，不将全部内容混成字符串交给前端猜测。聚合展示不丢弃必要过程记录，也不改变执行顺序或授权边界。

#### 进度文案与职责分工

| 责任方 | 职责 |
| --- | --- |
| 后端平台与工具 | 提供实际动作、操作对象、执行状态、结果和必要说明 |
| 前端 | 按展示规则生成常规状态文案，完成聚合计数、更新与折叠 |
| 主 Agent | 提供面向用户的计划、工作方法说明、调整原因及最终答复 |

常规进度由真实事件驱动、前端规则呈现；需要解释的工作说明才由主 Agent 提供。不为每次工具调用额外生成聊天文字，不额外依赖模型总结常规进度。动态说明不能替代真实状态，原始工具参数和输出也不默认完整展示。

仅展示面向用户的计划、工作说明和必要理由，不直接展示模型内部推理，也不照搬从 reasoning 内容提取标题的展示路径。

#### 真实进度与等待提示

- Agent 整体工作展示当前真实阶段，不估算整体完成百分比，因为检索、计划和步骤可能调整。
- 可准确计量的具体操作可展示数量或百分比，例如已处理文件数、上传进度；不将局部进度冒充整体进度。
- 较长时间没有新结果时，在已知执行状态下保持执行中及耗时提示；重试、等待和异常依据后端状态展示，不凭前端计时猜测。

#### 阅读与操作连续性

- 用户停留在底部时，跟随流式回复和最新进度；主动向上查看历史时，不自动拉回，提供有新内容或回到最新的入口。
- 已展开的过程详情不因执行状态更新而自动收起。
- 需要回答、授权或出现影响交付的异常时，醒目提示但不强制改变阅读位置。

信息及时更新，但不打断用户当前的阅读和操作。

#### 刷新与重连后的展示恢复

- 恢复已有答复、必要过程记录、产物和后端当前真实状态，不只显示最终结果。
- 同一动作继续更新原展示项，不因重连重复出现，也不重新启动工作。
- 尚有效的回答或授权等待点恢复操作入口；已处理或失效的入口不可再次生效，服务端仍须校验。
- 展开、折叠等阅读状态尽量保留，不作为后端执行状态的依据。

重新进入后，用户能接着看、接着操作，而不是重新开始一次工作。执行恢复能力仍遵守第 6.3 节，界面恢复不意味着任意中断步骤都能重新执行。

#### 异常分级展示

- 可自动恢复的临时失败，在原过程项中显示正在重试，不新增聊天消息；仅在实际进入重试时显示。
- 已恢复的失败在详情中保留记录，默认展示最终结果，不持续突出警告。
- 影响交付或需要用户处理的失败，明确展示影响、已保留成果及可采取的下一步，不能藏在折叠内容中。
- 普通界面展示可理解的原因，不直接暴露堆栈、密钥或原始请求内容；诊断信息的访问与脱敏规则另行细化。

不让用户承担每次内部波动，但必须让用户知道影响工作结果的问题。上述是概要行为原则，事件字段、聚合规则、推送协议、重连同步方式和具体组件均留到详细设计。

### 6.5 失败与重试（已确认）

| 情况 | 初版处理原则 |
| --- | --- |
| 模型请求或只读工具临时失败 | 有限次数自动重试，仍失败则明确反馈 |
| 写入、发送等操作明确未执行 | 工具具备安全重试条件时才重试 |
| 外部操作是否成功不确定 | 先核查结果，不直接重复执行 |
| 部分工作完成后失败 | 保留已完成结果，说明失败位置和未完成内容 |
| 用户取消 | 不自动重试或重新启动 |

重试针对具体失败步骤，不默认将整个 Run 从头再执行一次。已确认完成的外部动作不能因后续步骤失败而被重复执行；无法核实外部操作结果时，应明确反馈不确定状态，不按“未执行”处理。

重试次数、超时、工具安全重试条件，以及平台与 AgentScope Java 各自承担的重试边界，在详细设计阶段确定，避免多层重试叠加导致重复执行。

### 6.6 执行限制（已确认）

- 单次模型请求和工具调用设有超时限制。
- 每个 Run 设有执行时长、调用次数或用量上限，专业 Agent 的消耗纳入所属 Run 的统计。
- 等待用户回答或审批单独计时，不长期占用执行线程。
- 达到限制后停止继续发起操作，保留已有结果，并向用户说明停止原因。

具体额度、计量口径、等待过期后的处理，以及 AgentScope Java 对超时、预算和等待资源释放的支持范围，均在详细设计阶段确认。达到限制不表示正在执行的外部操作已经立即终止，实际停止仍需遵循取消和结果核查规则。

请求链路与工程职责的集中视图见[请求执行链路与控制概要](请求执行链路与控制.md)。本文是已确认行为原则的维护入口，链路文档用于组织这些原则及后续工程验证。

## 7. 配置更新与资源一致性

参考 Pi 的默认配置、当前有效配置和历史记录分别管理的思路，平台采用以下规则：

- Agent Profile 保存平台预置的默认配置。
- Run 开始时解析当前有效配置。
- 执行过程中不主动切换到平台新发布的配置。
- 后续 Run 可以使用更新后的配置，Session 无需重建。
- 记录实际使用的 Agent、模型和 Skills 等信息。

对于按需加载的 Skills，需要保留当前 Run 所引用的资源修订内容，避免平台更新后读取到不同正文。这是资源一致性的基本要求；初版不扩展为全量配置快照与完整回放系统。资源修订保留范围和清理策略在详细设计时确定。

权限撤销、工具紧急停用及时生效，不受配置更新边界限制。

连续修改已有成果时，以已有产物和用户要求为依据。例如“精简刚才的纪要”应修改原纪要，不能仅因模板更新就自动改写整份结构。

上述 Run 边界与资源修订规则是本平台的设计选择，不宣称 Pi 原生提供了同等的全量冻结机制。

## 8. 会议能力作为首个验证场景

用户上传会议记录，提出“整理纪要并提取行动项”。

统一助手加载会议整理相关 Skills，读取材料，生成纪要和行动项，保存到个人 Workspace。用户随后要求调整，系统在同一 Session 中创建新的 Run，引用已有结果继续处理。

只有会议工作出现明确的独立委派需求时，才引入会议 Agent；该 Agent 继续复用已有 Skills。

初版交付应验证：

- 用户能在同一会话中持续完成工作并修改已有成果。
- 系统能展示使用了哪些能力、执行到哪里、产生了什么结果。
- 用户资料与会话状态保持隔离。
- 配置更新遵循 Run 边界，权限撤销及时生效。
- 等待输入、确认、取消及失败具有明确状态。

## 9. 后续详细设计事项

### 9.1 AgentScope Java 交互控制验证（实现前必须确认）

以仓库锁定版本为准，通过对应版本的文档、源码和必要验证，确认以下支持范围，不预设存在现成接口：

| 验证项 | 需要确认的问题 |
| --- | --- |
| 中途补充输入 | 能否进入正在执行的 Agent，在什么阶段生效，是否影响当前模型或工具调用 |
| 取消传播 | 是否能中断模型请求、工具调用及专业 Agent；如何确认执行已停止 |
| 等待与继续 | 用户输入或审批等待如何保存状态、释放执行资源，并恢复原 Run |
| 恢复范围 | 支持同一进程内继续，还是也支持进程重启后的状态恢复；有哪些不能恢复的操作 |
| 执行限制 | 模型与工具超时如何落实；Run 与专业 Agent 的消耗如何汇总；达到限制如何停止；等待如何释放执行资源 |

验证结果应区分“框架原生支持”“平台需要补充”“存在限制”，再确定 runtime-api 的控制契约及 AgentScope 适配方案。抢占建立在旧执行实际停止的确认机制上。

### 9.2 其他细化事项

以下不改变已确认的概要方向，但需在实现前细化：

- 平台 Session、Run 与 AgentScope Java 状态的映射及恢复能力。
- 模型、Agent Profile、Skills 和工具的发布、引用与修订保留方式。
- 文件存储、检索及产物管理的基础设施选择。
- 会话附件存入资料库的引用关系、内容版本与格式导出的关联、跨会话来源记录。
- 草稿保存与正式版本提交边界、跨 Session 修改冲突检测及用户处理流程。
- 附件、草稿及正式成果的数据保存期限与临时文件清理策略；归档隐藏是否纳入需另行确认。
- 专业 Agent 的委派输入、返回结果和上下文传递方式。
- 显式对象与 Skill 引用解析、当前 Session 原文检索、压缩摘要与原始记录的关联及保存策略。
- 澄清工具与平台等待点的映射；计划进度、自检依据和部分交付的表达方式。
- 权限校验、操作确认、执行预算及工具幂等规则。
- 前端进度事件、四项交互控制、重新连接及重复提交的行为。
- 工作记录与前端展示项的身份关联、状态更新及重连去重，过程分组与流式内容同步策略。
- 常规文案模板、可计量进度口径、阅读状态保留、异常提示及诊断信息脱敏；不在概要阶段选定推送协议或组件实现。
- 内部执行器的并发上限、资源等待容量、超时及应用重启后的状态收敛。
