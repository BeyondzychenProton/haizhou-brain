## 1. 结论

1. **平台用户身份由智慧大脑自己的用户库确认。** 管理员创建账号；用户以唯一的规范化手机号作为登录名，以密码完成平台认证。数据库主键 `UserId` 是唯一稳定的内部身份，业务数据不以手机号归属。外部系统的 Token 不用于登录智慧大脑。
2. **管理员身份由平台用户的有效角色记录确定。** 一期只定义 `PLATFORM_ADMIN` 和 `USER` 两个角色。管理接口要求当前登录用户仍启用且具有 `PLATFORM_ADMIN`；客户端传来的 `actorId`、角色字段、请求头或旧配置中的固定管理员 ID 均不可信。管理员也不自动拥有查看他人私密 Session 正文的权限。
3. **浏览器/API 使用服务端登录态。** 登录成功后生成不可预测的会话标识，写入受保护的 Cookie；Redis 保存 WebFlux 会话。会话只记录 `UserId`、登录时的账号版本等最小身份信息，不把密码、外部系统 Token 或完整权限快照放进 Cookie。后端每次受保护请求从会话解析用户，并核对数据库中的账号状态与当前角色。Redis 或身份库不可用时拒绝受保护请求。
4. **真实身份未接通前维持入口关闭。** 本文不恢复 Session/Run、管理或会议室 API，也不将原型固定用户 1001 换一个常量继续使用。此前“先不实现手机号密码登录”的范围要求在本轮仍有效；何时开始编码登录由后续开发任务决定。

这套方案沿用已确认的“平台自有用户”产品规则，不预设公司已经提供 SSO。以后若接入企业 SSO，应把其已验证身份映射到现有 `UserId`，并经过单独的账号绑定审查；不能直接用外部用户名替代平台内部主键。

## 2. 四种身份与凭据

| 对象 | 来源 | 用途 | 存放与信任边界 |
| --- | --- | --- | --- |
| 平台用户 `UserId` | 平台用户表 | Session、Run、成果、授权、审计的归属 | 仅在认证成功后由服务端建立；请求体不指定当前用户 |
| 平台角色 | 平台角色分配表 | 判断能否访问管理入口 | 每次管理操作读取有效角色；前端展示只是提示 |
| 平台登录态 | 平台认证后创建的 Redis 会话 | 证明当前 Web/API 请求属于哪个用户 | Cookie 只携带会话标识；服务端验证与撤销 |
| 外部业务系统凭据 | 目标系统认可的用户授权流程 | 访问具体外部业务系统 | 按 `UserId + 目标系统` 独立管理，不作为平台登录或管理员凭据 |

手机号用于登录、管理员联系用户及经授权的外部账号定位。手机号变更只更新登录名和外部映射核验，不改 `UserId`；旧号码重新分配后，新用户不能继承原用户的数据或外部凭据。

## 3. 用户与管理员数据模型

本节定义逻辑字段，物理 SQL 待编码前按现有数据库命名、索引与 Flyway 迁移规范落成新版本；**不修改已执行的 V1–V3**。

### 3.1 `platform_user`

| 字段 | 约束与语义 |
| --- | --- |
| `id` | 生成的稳定 `UserId`；不可从手机号推导，不允许复用 |
| `mobile_normalized` | 唯一、非空；登录和创建时使用同一规范化规则，展示时可遮蔽 |
| `password_hash` | 单向自适应编码值；不存明文、可逆密文或配置文件中的初始密码 |
| `status` | `PENDING_ACTIVATION`、`ACTIVE`、`DISABLED`；未激活或停用时拒绝普通登录与业务动作 |
| `auth_version` | 单调递增；密码重置、账号停用、角色变更时递增，使旧会话失效 |
| `must_change_password` | 首次启用或管理员重置后要求先设置新密码；此期间不能进入普通业务与管理接口 |
| `created_by`、`created_at`、`updated_at`、`row_version` | 操作者、审计时间与并发修改保护 |

一期手机号采用带国家码的规范化字符串，如 `+86...`。创建账号和登录必须走同一规范化函数；无法解析或不满足业务允许范围时拒绝，不把不同格式当成不同账号。密码编码通过 Spring Security `PasswordEncoder` 实现并保留算法标识，以便后续升级。[Spring Security 密码存储文档](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)

管理员创建普通用户时先置为 `PENDING_ACTIVATION`，平台生成一次性激活凭据，只存摘要、有效期与使用状态；由管理员通过公司认可的独立渠道交给本人。用户凭该凭据设置自己的密码后才变为 `ACTIVE`。激活凭据不作为可长期登录的密码；过期或使用后立即失效，重发使旧凭据失效。短信或邮件自动投递不属于首轮前提，具体交付渠道由运营流程确认。

一次性激活记录至少包含 `user_id`、`token_hash`、`expires_at`、`used_at`、`created_by`；明文凭据仅在创建响应中向已认证管理员显示一次，不落库、不写日志。激活接口按凭据和来源限流；创建、重发与使用均记录不含凭据正文的审计。凭据长度、有效期和交付渠道在实施时按部署环境确定。[OWASP 一次性重置凭据建议](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)

### 3.2 `platform_user_role`

主键为 `(user_id, role_code)`；记录授予人、授予时间，撤销以受控操作和审计记录体现。`role_code` 首期只允许 `PLATFORM_ADMIN`、`USER` 白名单值。角色从数据库读出，不写死“用户 1 是管理员”，也不信任客户端自报。`USER` 不含管理权限；`PLATFORM_ADMIN` 仅授予明确的管理动作。若管理员还需使用普通业务，应显式同时授予 `USER`，其私人资源仍按本人 `UserId` 隔离。

至少保留一个**启用且可登录的管理员**。停用、撤销角色或重置最后一名管理员的操作必须被拒绝，除非同一受控流程已建立替代管理员。管理权限变更写审计：操作者、目标用户、原状态、新状态、原因和时间；审计不记录密码与会话值。

### 3.3 首位管理员建立

部署后通过**仅在服务器运维端运行的一次性初始化命令**创建首位管理员；不提供匿名 HTTP 初始化接口，也不在迁移 SQL、YAML、测试数据中写默认管理员或默认密码。命令只在数据库中不存在任何管理员记录时可用，从交互式控制台读取手机号和初始密码，完成规范化与密码编码后在事务中写入用户、管理员角色和初始化审计。输入密码不作为命令行参数，避免留在进程列表和 shell 历史中。

初始化命令需要运维人员对部署环境和数据库的受控访问；命令运行后即退出，不作为常驻服务。首次登录要求修改初始密码。若已有管理员但全部失去访问权，不重新开放匿名初始化；按单独的运维恢复流程核验身份、记录审批和审计后修复。

## 4. 登录态与请求身份链路

```mermaid
flowchart LR
    A[用户提交手机号和密码] --> B[认证服务校验账号与密码]
    B --> C[建立 Redis WebSession]
    C --> D[Cookie 携带会话标识]
    D --> E[WebFlux 安全链读取会话]
    E --> F[复核账号状态和 auth_version]
    F --> G[读取当前角色并建立可信主体]
    G --> H[业务与管理授权]
```

- 登录成功后更新会话标识，避免沿用匿名会话；登出销毁服务器会话。会话采用可配置的空闲超时，首期建议 8 小时；不得仅靠浏览器关闭窗口判断失效。
- Cookie 设置 `HttpOnly`、生产 HTTPS 下 `Secure` 和适合同站点部署的 `SameSite` 属性。使用 Cookie 认证的写请求保留 CSRF 防护；若前后端跨站部署，先重新评审 Cookie、CORS 与 CSRF 方案，不直接放宽为任意来源。
- 匿名客户端先通过 `GET /api/v1/auth/csrf` 取得 CSRF 令牌，随后在登录、激活等写请求中按约定请求头提交；已登录写请求同样校验。CSRF 令牌不承担用户身份认证。
- 登录失败对“手机号不存在、密码错误、账号停用”使用相同的对外响应，记录内部分类用于审计；登录接口按账号和来源实施限流。登录与重置响应不泄露账号是否存在。[OWASP 认证建议](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)
- WebFlux 使用 `SecurityWebFilterChain` 约束路径：健康检查按运维需要公开，登录入口匿名，`/api/admin/**` 要求管理员，其余恢复开放的业务 API 要求已认证，未配置的路径默认拒绝。[Spring Security WebFlux 授权文档](https://docs.spring.io/spring-security/reference/reactive/authorization/authorize-http-requests.html)
- Redis 会话采用 Spring Session 对 WebFlux 的支持，不能照搬 Servlet `HttpSession` 的配置。当前工程只有 Redis 数据依赖，尚未加入 Spring Session，也没有真正的认证过滤链。[Spring Boot 响应式会话文档](https://docs.spring.io/spring-boot/reference/web/spring-session.html)

每个受保护请求应得到一个服务端构造的 `AuthenticatedUser(userId, roles, authVersion)`。控制器把该主体交给应用服务；不得从 JSON、URL 参数、可伪造的普通请求头取当前用户。WebFlux 中不能依赖普通线程局部变量跨异步边界传递身份，使用响应式安全上下文或显式参数。涉及 JDBC 的用户与角色查询须避免阻塞 Netty 事件循环。

## 5. 对外 API 边界

以下是后续编码的目标契约，不表示接口现在已实现：

| API | 调用者 | 结果与边界 |
| --- | --- | --- |
| `GET /api/v1/auth/csrf` | 匿名或已登录 | 提供写请求所需 CSRF 令牌；不返回用户身份 |
| `POST /api/v1/auth/activate` | 持有效一次性激活凭据者 | 设置本人初始密码并激活账号；凭据只用一次且有时限 |
| `POST /api/v1/auth/login` | 匿名 | 手机号和密码校验成功后建立会话；失败响应不泄露账号状态 |
| `POST /api/v1/auth/password/change` | 已登录或仅允许首次改密的会话 | 校验当前凭据并设置新密码，递增 `auth_version`；首次改密前不能访问其他业务 |
| `POST /api/v1/auth/logout` | 已登录 | 使当前会话失效；重复登出按统一语义处理 |
| `GET /api/v1/auth/me` | 已登录 | 返回自己的 `UserId`、遮蔽手机号、显示名及可展示角色；不返回密码、会话值 |
| `POST /api/admin/v1/users` | 平台管理员 | 创建待激活普通用户并发起一次性激活；目标角色不能由请求随意提升为管理员 |
| `PUT/DELETE /api/admin/v1/users/{id}/roles/PLATFORM_ADMIN` | 平台管理员 | 独立授权和审计；只给已激活用户授予管理员，保护最后一名有效管理员 |
| `PUT /api/admin/v1/users/{id}/status` | 平台管理员 | 启用或停用账号并递增 `auth_version`；保护最后一名有效管理员 |
| 恢复的 Agent 定义管理 API | 平台管理员 | `actorId` 来自当前身份，不接受固定配置或请求体自报 |
| 恢复的 Session/Run API | 已登录用户 | `UserId` 来自当前身份；查询单个资源仍检查归属 |

状态语义：未登录或会话无效返回 **401**；已登录但没有管理权限或资源权限返回 **403**；用户请求别人的私有资源时还应避免通过响应暴露资源存在性，具体使用 403 或 404 在资源 API 中统一。仅有管理员角色不绕过业务资源归属检查。

## 6. 账号、会话与异步 Run 的失效规则

1. 登录时验证账号启用、密码和首次改密状态；建立会话时写入当前 `auth_version`。
2. 每次受保护请求重新核对用户启用状态及 `auth_version`，管理员请求还读当前角色。密码修改、管理员重置、停用账号、管理员角色变更时递增 `auth_version`；旧会话即使仍留在 Redis，也不再被接受。
3. Redis 不可用、身份库查询失败或会话记录损坏时，受保护请求失败关闭，不临时退化为固定用户或“信任请求头”。
4. 创建 Run 时记录经过认证的 `UserId`。异步执行不依赖浏览器会话持续存在，但实际启动和每次受控工具执行仍复核账号状态、员工能力、动作权限与目标资源范围；停用用户不能发起新的外部动作。已成功发生的外部操作按真实结果记录，不伪装成回滚。
5. 多渠道身份绑定将来必须由验签或可信渠道身份映射到现有 `UserId`；消息文本自报手机号不能成为认证。外部系统 Token 的过期与平台会话过期互相独立。

## 7. 模块实施位置与顺序

| 模块 | 后续实施职责 |
| --- | --- |
| `security` | `PlatformUser`、角色与认证主体、密码验证、账号状态和授权规则；不依赖 HTTP 或 AgentScope |
| `infrastructure` | 用户/角色 JDBC 仓储、新 Flyway 迁移、Redis 会话接入和审计持久化 |
| `api` | 登录、登出、本人信息、管理员用户 API；从安全上下文取身份并做输入校验 |
| `bootstrap` | WebFlux 安全链、配置装配、离线首位管理员初始化命令 |
| `platform` | Session/Run 和 Agent 定义服务接收可信 `UserId`/管理员操作者；资源归属与动作权限检查 |
| `runtime-agentscope` | 只消费应用层传入的已验证身份，不负责登录或把模型输出当身份 |

实施顺序：**数据库与离线管理员初始化 → 登录/会话/登出 → 当前用户与管理员权限 → 恢复管理 API → 恢复普通业务 API → 接入真实会议室适配器**。每一步先写可复核的接口与迁移设计，再编码、测试、提交。恢复某个接口前，该接口的身份、角色、资源归属与审计必须一起完成；不能仅把控制器重新放回应用。

## 8. 验收场景

1. 空库启动没有默认用户或管理员；未经初始化时管理 API 保持关闭。离线初始化只成功一次，第二次拒绝且不覆盖已有管理员。
2. 用户登录后 `GET /auth/me` 的 `UserId` 来自数据库；在请求体/请求头伪造另一个 `UserId` 不改变身份。
3. 普通用户调用管理员 API 得 403；管理员调用可用，但管理操作审计中的操作者是其真实 `UserId`。
4. 两个普通用户的 Session/Run 隔离；管理员不凭角色直接读取任意用户的私密正文。
5. 停用账号、修改密码或撤销管理员角色后，既有会话无法继续执行受保护操作；Redis 或身份库不可用时拒绝。
6. 登录错误不区分账号不存在与密码错误；密码和会话标识不进入日志、Agent Prompt、审计正文或数据库明文字段。
7. 新 Run 和工具动作分别复核账号与权限；Cookie 过期不改变已经完成的真实外部操作结果。

## 9. 实施前需核对的运营事实

- 首位管理员由谁负责初始化、谁可接触服务器运维控制台、如何留存操作审批记录。
- 是否需要支持中国大陆以外手机号；若需要，手机号规范化和验证规则在建唯一索引前统一确定。
- 前端最终是否与 API 同站点部署；跨站部署会改变 Cookie、CORS 和 CSRF 的具体配置。
- 正式环境 Redis 的持久化、可用性、访问控制和会话过期策略；开发机上的独立 Redis 容器不等于生产方案。

这些事实影响实施参数，但不改变本文确定的身份来源和管理员判定原则。本文只交付设计；此前暂缓手机号密码登录的实现约束不会因为文档完成而自动解除。
