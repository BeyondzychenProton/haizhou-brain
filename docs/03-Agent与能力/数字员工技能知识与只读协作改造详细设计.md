### 1.3 对输入方案的具体校准

1. **公开 API 校准**：2.0.3 的 `HarnessAgent.Builder.asLeafSubagent()` 是包内方法，外部业务代码不能调用。薄子构建使用公开的 `disableSubagents()`、`disableDynamicSubagents()` 等配置，并验收最终工具集；不通过反射或同包补类调用内部方法。
2. **Skill 开关校准**：`disableDynamicSkills()` 选择冻结技能中间件路径；`disableDefaultWorkspaceSkills()` 只省略默认 Layer 4 来源。本地工作区 Layer 3 仍可组成技能仓库。新 profile 物化资产并显式过滤技能，不能仅删除一个开关就称为接入完成。
3. **持久文件校准**：`RemoteFilesystemSpec` 的默认隔离是 USER，并且未匹配路由的文件仍走本地后端。新 profile 必须显式 SESSION、列出所有可写路由并验证重启恢复。
4. **专家策略校准**：原生自定义 subagentFactory 注册不携带 SubagentDeclaration 到默认管理器；声明对象中的过滤、步数等需由薄子构建显式应用。Builder 的 Function<String, Agent> 回调不接收父 RuntimeContext；可信父执行作用域须通过原生 SubagentEntry/SubagentFactory(RuntimeContext) 扩展点或经过探针验证的 Run 作用域薄装配传递，不放进共享模板的可变闭包。首期默认不持久复用子 Session；expose/forceSync 由可信调用上下文覆盖。
5. **事件事务校准**：统一所有 Run 事件写入入口，补齐工具/审批事件的会话投影；不能只修 Run 完成的一个写入点。
6. **授权校准**：延续现有 TOOL/MCP 差异：本地业务动作由平台判权，可信 MCP 由终端用户身份在 Server 最终判权。子专家首期不执行这两类业务工具。

## 2. 目标、范围与首个验收场景

### 2.1 用户可看到的结果

管理员能够创建或配置员工，选择经过审核的技能与知识版本，绑定固定成员版本，校验后发布。用户新建“销售经理”会话后提交任务，主员工按需使用 customer-analysis、proposal-writing 和岗位参考资料，调用 researcher/reviewer 做只读分析，最后返回完整答案。

页面显示主员工答案、计划与独立专家卡片。刷新或断线后，持久结果与专家关键状态能恢复；渠道 Run 的完成与回复意图一致提交，消息送达状态独立跟踪。

用户也可以在同一团队 Session 先问 researcher，再问 reviewer，随后切回 researcher 继续其对话。单次请求可以指定专家直接回答，也可以交给协调者组织多个专家协作；每条答案显示实际回答角色。角色切换不清空整个 Session，也不切换已固定的团队版本。

### 2.2 发布 profile

| profile | 使用对象 | 技能 / 知识 | 原生专家 | 计划与运行文件 | 自动长期记忆 |
| --- | --- | --- | --- | --- | --- |
| LEGACY_STABLE | 已有 V1 发布包、兼容旧草稿请求 | 按旧包与旧限制 | 关闭 | 保留旧运行路径 | 关闭 |
| SINGLE_SKILLED | 新单员工与只读专家的发布定义 | 冻结发布版本 | 主员工关闭 | 原生 SESSION 文件面 | 关闭 |
| TEAM_READONLY | 新团队 Session，含协调者与可选专家 | 冻结发布版本 | 固定与动态专家、受控同步协作 | 原生 SESSION 文件面、独立角色槽 | 关闭 |
| TEAM_AUTONOMOUS_READONLY | 需要成员主动互发消息和认领任务的团队 Session | 冻结发布版本 | 一次父 Run 内的原生 Team、预先批准的成员 | 独立角色槽 + 每次 Team 的内部状态与任务板 | 关闭 |

运行策略随员工发布固定。平台部署开关只能拒绝启用未经验收的 profile，不能给旧发布包扩权。legacy_runtime=true 的存量 Session 继续旧路径；新 profile 的试运行采用新 Session。

TEAM_AUTONOMOUS_READONLY 是单独验收的目标 profile，默认关闭；其 Session 仍能直接选择专家或使用受控协作。自治成员之间的消息不是用户新请求，不各自创建业务 Run。首期自治 Team 成员集合在本次 Team 开始前冻结；§8.6 的动态专家仍可用于受控 spawn/send，不向活跃 Team 动态加人。

首期不改 Gateway 的排队、路由和取消所有权。Web 与已有渠道继续创建平台 Run，Worker 调用 Harness；原生专家执行在这个调用内完成。

### 3.1 Session、角色、运行槽与 Run

业务 Session 是一个用户的对话容器；新团队 Session 固定一个不可变团队发布包。包中包含协调者与专家的版本、资产和策略。管理员发布新版不会在原 Session 中替换任何角色的版本。

**角色身份与根/子执行位置分开**。用户直接选 researcher 时，researcher 是本次 Run 的根执行者；协调者委派 researcher 时，它是该 Run 的子执行者。相同专家名称不能决定它是否有权完成业务 Run。

~~~mermaid
flowchart TD
    S[同一个业务 Session<br/>固定团队版本、用户历史和属主]
    S --> A[协调者运行槽<br/>独立 AgentState / 文件]
    S --> B[researcher 运行槽<br/>独立 AgentState / 文件]
    S --> C[reviewer 运行槽<br/>独立 AgentState / 文件]
    S --> R[每次 Run 固定目标角色<br/>同一 Session 一个活动根 Run]
    R --> D[本次根 Harness 调用]
    D --> E[原生专家协作<br/>任务子会话与结果传递]
~~~

拟新增 platform_session_agent_slot：slotId、sessionId、roleId、employeeId、definitionVersionId、runtimeSessionId、状态及创建时间；(sessionId, roleId) 唯一，runtimeSessionId 全局唯一。协调者可继续使用业务 Session ID，其他角色使用服务器生成并持久保存的原生 ID。AgentState 正文仍由 AgentScope StateStore 保存，槽位表只保存可信寻址关系。

各槽的 AgentState 保留该专家在本 Session 中的对话上下文；跨 Session 的长期 Memory 仍按首期策略关闭。角色槽无需另存一份专家内部聊天记忆。

普通单员工仍保持当前直接身份规则。TEAM Session 增加显式身份模式与验证，不使用 bridgeSnapshotHash 非空来绕过旧构造断言，也不借旧 Binding/Bridge 机制复制或迁移专家记忆。所有角色共用业务属主校验，原生键各自隔离。

### 3.2 同一 Session 内切换专家

正常切换流程：

1. 用户选择 researcher，发送 R1；服务端从固定团队清单确认其可供用户直接选择，冻结目标角色、版本、运行槽和权限。
2. Worker 调用 researcher 槽，原生恢复其 AgentState；R1 完成与结果写入同一业务 Session。
3. 用户选择 reviewer，发送 R2；调用 reviewer 槽，读取它自己的 AgentState。
4. 用户切回 researcher，发送 R3；恢复 R1 所在 researcher 槽，并按请求引用传入 R2 的安全结果或共同任务资料。

未使用过的槽可以初始化；已经执行/等待恢复的槽缺状态时仍按 §13 失败或核查，不静默新建。

界面当前选择只决定**新请求**。R1 已在执行时选择 reviewer，不改 R1 的模板、上下文、审批归属或输出身份；R2 沿用平台 Session 队列，R1 完成后才执行。需要打断时显式取消 R1，确认收尾后执行下一条；不能热替换正在执行的 Agent。

同 clientRequestId 的目标角色、输入、结果引用都进入请求摘要；修改目标重发必须返回幂等冲突，不能取得旧目标结果或把旧请求重定向。

### 3.3 多 Agent 的协作方式

| 方式 | 具体例子 | 控制与交付 |
| --- | --- | --- |
| 串行 | researcher 分析 → reviewer 审查分析 → 根 Agent 汇总 | 原生根循环逐次委派，显式传入前一结果 |
| 并行 | 两个专家独立研究不同维度 | 原生同轮工具并行；平台限制预算，根 Agent 收齐必要结果后汇总 |
| 复核修订 | 方案作者产出 → reviewer 指出问题 → 作者修订 → 再复核 | 根 Agent 使用原生 agent_send 跟进本任务内已生成专家，保留其子上下文 |
| 专家主导 | 用户直接选 researcher，且团队策略允许它调用 reviewer | researcher 是根，reviewer 是只读子执行；根角色和委派规则分别校验 |
| 无需委派 | 用户直接问 reviewer 一个问题 | 一个 Run、一个根调用；专家直接答案展示为该轮正式回答 |

团队发布策略定义 userSelectableRoles、defaultRoleId、allowedDelegations（fromRoleId/toRoleId）与最大协作规模。可供用户选择不代表可以自行委派所有角色；某角色能作为根协调，作为子执行时仍收窄为只读叶子。

成员作为根时使用其冻结定义的迭代上限，并受团队批准上限收窄；成为根不自动得到协调者的业务工具、Plan 写或文件写权限。mode=direct 收窄掉委派入口，mode=collaborative 只开放该根角色已批准的委派边。缺省普通单员工为 direct，团队协调者为 collaborative，用户指定专家而未填 mode 时为 direct。

协作决定和等待由原生 Harness 循环、agent_spawn/agent_send 承担。平台记录版本、权限、预算和关联，不实现固定 A→B→C 的第二套执行引擎。复核次数受总委派/跟进次数与主迭代限制约束；达到边界明确收尾，不能无限互评。

**agent_send 需纳入 C 的原生验收**。它只能由本次根调用向当前 Run 已受理的专家 agent_key 发起；核对根运行槽、Run/attempt/fence、成员及原生关联。不能仅凭模型给出的 label、roleId 或任意 sessionId 寻址。每次 follow-up 计入 Run 总调用预算，复用同一 delegationId，并保存独立 invocationId/toolUseId，避免把第二轮结果吞成第一轮的重复事件。

同任务 follow-up 保留原生已生成专家上下文；跨任务的子 Session 自动复用仍关闭。直接对话槽与任务子槽用途不同：委派默认接收本任务明确给出的资料，不自动读写专家的直接对话记忆。后续若要求两者共享状态，必须重新证明并发、权限与恢复一致性。

### 3.4 共享资料与私有上下文

| 内容 | 是否共享 / 方式 |
| --- | --- |
| 用户本次任务、明确引用的先前答案/文件 | 按属主和可见性校验后，作为当前调用输入传递 |
| 用户可见的专家结论、审查意见、已确认事实 | 通过 resultId/消息引用共享；带来源、版本、任务与有效范围 |
| 全体专家的全部聊天历史 | 不自动复制到每个 Agent；只传本任务选定或用户明确引用的安全资料 |
| 原生内部记忆、压缩摘要、思考链、工具/审批状态 | 保存在所属 AgentState；不复制到其他角色 |
| 私有工具凭据、业务访问权限 | 不由切换或协作授予；每次执行重新遵守用户与角色的权限交集 |

切回专家时，它能够恢复自己的先前对话；若需要了解其他专家新增的结果，应明确携带相关 resultId 或由本次根 Agent 选择可共享材料。持久 Session 历史是展示和受控资料引用来源，不据此重建各 Agent 的内部记忆。

输入契约增加 referencedResultIds，首期只接受同 Session 且用户有权读取的结果；服务端解析为带来源的任务资料，去重并限制长度。模型生成内容保持资料身份，不能被提升为系统指令。快照的单一会话游标覆盖所有角色，页面能显示完整用户可见进程，底层运行状态仍各自隔离。

### 3.5 原生 Team 与开放式互相协作

本地 2.0.3 源码已有 TeamsMiddleware、TeamTool、LocalTeamClient、MessageBus 和 WakeupDispatcher。任务板、任务 CAS、成员邮箱和闲置成员激活沿用这些原生组件；平台薄接线负责可信身份、父 Run 所有权、版本和调用预算。[N09]、[N10]、[N11]、[N12]

目标流程见 §8.7。首期在一个有效父 Run 内由唯一 Worker 持有活团队，内部成员可互相传递资料、认领任务和通知 Team lead。用户下一次直接选择专家，仍走 §3.2 的稳定角色槽；自治任务使用独立的 Team 内部会话，不与专家直接对话记忆混写。

源码已确认：唤醒注册是进程内机制；LocalTeamClient 的消息序号保存在实例内存；该实现不支持动态 spawnMember 和计划审批等控制面动作。持久 BaseStore 因此只能证明任务板/消息可存储，不能证明同一团队跨进程自动接续。§13.5 给出首期处置，不把这些限制留成没有方案的“待验证”。跨节点自动接续仍需 §19 的后续门槛。[N09]、[N10]、[N13]

### 3.6 Session、Run、Task、实例与调用的统一含义

本次 Task 指一次业务 Run 内的工作项。§3.3 的“同任务 follow-up / 跨任务复用”分别指同一业务 Run 内跟进 / 跨业务 Run 复用；同一 Run 内需要调整职责时仍须使用明确的工作项引用。用户下一条新请求通过平台受理新 Run，内部成员消息和追问不自动创建业务 Run。

| 对象 | 身份与关系 | 状态所有者 |
| --- | --- | --- |
| 业务 Session | 可信用户的持续对话容器，1:N Run；固定团队包，含独立直接角色槽 | 平台；同 Session 的活动根 Run 与排队规则沿用现有受理 |
| 业务 Run | 一次受理请求，固定根执行者、RunSpec、预算与最终交付；可包含多个工作项 | 平台；子结果和成员轮次不能完成根 Run |
| Task / 工作项 | 要完成的工作，定义目标、输入、依赖和验收；一个工作项可有多轮调用或多个协作者 | 原生 Plan/Team 存储拥有其原生任务状态；普通同步委派保留输入、结果和检查事实，不另建任务队列 |
| Agent 实例 / delegation | 本 Run 的执行者与专家上下文；固定或通用实例可在同 Run 内承接受控跟进 | AgentScope 管理实例和 AgentState；平台保存归属、规格与寻址关联 |
| Invocation | 对实例的一次执行；首次 spawn、每次 send、每次 Team 唤醒轮次分别记录 | 原生生命周期为执行依据，平台记录预算与状态投影 |
| 原生 sessionId | AgentState 的寻址键；直接角色槽、委派子实例、Team 成员分别绑定 | AgentScope 状态存储；平台仅保管可信映射 |

~~~mermaid
flowchart TD
    S[业务 Session：固定团队包与独立角色槽] --> R1[Run 1：一个根执行者]
    S --> R2[Run 2：用户后续请求]
    R1 --> W[多个 Task / 工作项]
    R1 --> A[多个 Agent 实例]
    W --> I[工作项与实例的调用关联]
    A --> I
    I --> O[每轮结果与交付检查]
    O --> F[根汇总；平台结算 Run]
~~~

工作项采用服务端生成、Run 内稳定的 workItemRef；原生任务引用另存 origin、nativeTaskId、nativeTaskVersion，以及存在时的 Team 身份/generation。同步 spawn 未产生原生 taskId 时为 null；同一 general-purpose 类型的多个实例、同一实例的多轮调用都不能合并成一个任务 ID。

workItemRef 是受理、资料与结果的关联标识，没有授权或排队含义。首期不新增可由 Worker 扫描认领的 platform_task 表；目标/依赖选择由原生根循环或 Team lead 决定，Task 投影不能反向驱动第二套调度。独立跨 Run 的长期业务任务不在这次 Task 定义中；后续请求只能明确引用有权读取的已持久资料。

### 3.7 未来多 Agent 群聊的兼容性约束

用户要求考虑未来多个 Agent 加入同一群聊的可能性，当前仅约定以下架构边界。它们是现有设计的约束，不是群聊模式的详细方案或已经具备的能力。

| 兼容点 | 当前设计须保持的边界 |
| --- | --- |
| 对话与任务生命周期 | 持续业务对话和一次 Run/Team 执行分别识别；当前 Team 随 Run 收尾是任务实例策略，不把“Run 完成”定义成关闭业务对话或删除专家身份 |
| 参与者与执行角色 | Agent 定义、实际实例、业务角色和 ROOT/CHILD 位置分别表达；Team lead 是本次任务的协调角色，不把它固定为所有业务消息的唯一发言身份 |
| 成员与执行快照 | 当前固定 roster 是本次 Team 的批准执行快照，不把它等同于未来群聊的参与者名单；成员变化不得无声改写已受理 Run 的版本和权限 |
| 多来源消息 | 保留实际发送者、目标、原生消息引用和任务关联；消息归并按来源与调用区分，不依赖唯一 runId-assistant 气泡；群中发言与 Run 最终结果的含义分别保留 |
| 可见性与上下文 | 参与同一业务对话不自动共享全部 AgentState、内部消息或业务权限；保留私有状态、批准资料引用与受控展示边界；当前 USER/INTERNAL 不构成群成员授权或广播规则 |
| 渠道与可信寻址 | 外部群标识、业务 Session、原生成员 Session 与本次 Team 标识通过可信关联衔接，不在通用契约中规定它们必须相等；消息中的 Agent 名称或群标识不能充当可信用户身份 |

当前 platform_run_team_execution/member_binding 继续表达一次 Run 内的执行关联；未来需要群聊参与关系时可以在业务会话层扩展。首期的单 owner、只读、固定成员和单个活动根 Run 等规则仍按本稿执行；这些是当前运行策略，群聊是否沿用须在未来明确需求后评审。

## 4. 岗位资产与管理模型

### 4.1 复用现有能力身份，补齐非工具内容

现有 `CapabilityType` 已有 SKILL/KNOWLEDGE，草稿和版本的能力绑定也已能保存代码与修订。沿用这些身份，补充资产内容和按类型校验。

当前 `capability_revision` 强制 tool_name、implementation_key、business_action 非空。新增迁移允许这三个字段对 SKILL/KNOWLEDGE 为 null；TOOL/MCP 的服务校验继续要求完整工具字段。input_schema_json 对非工具保存 `{}`，不伪造工具名、执行器或业务动作。

拟新增：

| 表 | 核心字段 / 约束 | 用途 |
| --- | --- | --- |
| capability_asset_revision | capability_revision_id PK/FK、kind、manifest_json、asset_hash、审核人/时间 | 已审核且不可变的 SKILL/KNOWLEDGE 文件包 |
| capability_asset_file | capability_revision_id + relative_path PK、media_type、content、sha256、byte_size | 首期 UTF-8 Markdown / 文本参考资料 |
| capability_asset_draft | asset_code、draft_revision、kind、files_json、updated_by/at | 管理员编辑和预览，尚不能进入发布包 |

资产修订复用现有 capability_definition 的启停状态与 capability_revision 的稳定数值 ID。资产审核写入修订、文件和审计须同事务；审核后的正文不可覆写，修改产生新修订。

首期文件正文保存于数据库，发布包保存冻结引用和哈希。Worker 在构建快照前读取精确资产修订并校验，将不可变文件内容交给物化器；模板工厂不查询“最新资产”或草稿。

### 4.2 文件组织与格式

~~~text
AGENTS.md
skills/
  customer-analysis/
    SKILL.md
    references/customer-fields.md
  proposal-writing/
    SKILL.md
knowledge/
  KNOWLEDGE.md
  references/product-catalog.md
members/
  researcher/<memberBundleHash>/...
  reviewer/<memberBundleHash>/...
~~~

Skill 用框架原生 SKILL.md 格式，校验 front matter、name、description 与引用文件；名字与目录一致，重复名字在发布前拒绝。Knowledge 以 KNOWLEDGE.md 为入口，索引引用必须指向同一个已冻结文件包，且不得依赖 Worker 磁盘上的额外资料。

成员目录仅是父发布物中的只读定义布局；每个子 Harness 使用自身成员定义根，不把父目录当作子运行工作区。

### 4.3 资产校验

- 路径采用规范化的 POSIX 相对路径；拒绝绝对路径、盘符、UNC、`..`、符号链接和大小写折叠冲突；同时拒绝 Windows 保留名、尾随点/空格与非法字符。
- 首期接受 UTF-8 文本。脚本、可执行文件、归档展开和任意远程下载属于后续沙箱接入，不进入本轮资产管理 API。
- 建议单文件不超过 256 KiB、单修订不超过 2 MiB / 100 个文件、一个员工包含成员的总资产不超过 10 MiB；超过时显式校验失败。
- 计算原始 UTF-8 字节的 SHA-256；清单按相对路径排序。引用不存在、哈希不符或部分文件丢失时拒绝构建。
- 资产选择仍指向指定修订；禁用资产是紧急收窄，新 Run 在受理时拒绝使用，现有上下文中已经读到的内容不能承诺被“撤回”。

### 4.4 知识访问范围

当前员工目录按默认租户列出可用员工，尚无完整的“用户可使用哪些员工”授权模型。首期资产限定为平台批准的共享岗位资料，并在管理页说明共享范围；本轮不以现有用户工具 Grant 假装实现知识权限。

用户私有文件、客户机密资料与跨组织知识须通过现有受授权的父工具取得，或在后续增加真实岗位访问策略后接入。资料由父员工最小化后交给专家，不存入共享定义资产。正文可见权限、页面属主和模型读取权限必须一致。

## 5. 草稿、发布包与版本冻结

### 5.1 草稿结构

沿用 AgentDefinitionDraft 与现有 `capabilities`，扩展 `configuration`。TOOL/MCP 继续作为业务工具绑定，SKILL/KNOWLEDGE 作为岗位资产绑定；成员使用独立、显式的角色引用。

  "capabilities": [
    {"capabilityCode": "skill.customer-analysis", "revision": "3"},

新 profile 允许没有业务工具绑定的分析员工；仍要求完整指令与模型。旧校验的“至少选一个工具”需要按 profile 修订，前后端一致处理。

### 5.2 发布物字段

| 现有载体 | V2 扩展 |
| --- | --- |
| workspace_manifest_json | schemaVersion=2、规范化 workspaceAssets、资产修订 ID、相对路径、字节哈希与大小 |
| subagent_manifest_json | 固定角色、成员 employeeId/definitionVersionId/bundleHash、成员模型和工作区引用、只读策略 |
| policy_json | profile、实际工具类别与开关、迭代/预算/同步策略、文件隔离、策略格式版本 |
| tool_catalog_json | 仍只含 TOOL/MCP；资产不进入外部工具 Schema |
| RuntimeDefinitionSnapshot | 增加 schemaVersion、employeeId/tenant 标识、不可变资产、成员快照、团队规则和已解析策略 |
| agent_definition_draft/version | configuration_json，支持草稿编辑、发布比较与审计 |
| agent_definition_member | 父 definitionVersionId + roleId 唯一，成员版本 FK、成员 bundleHash、策略 JSON |

新增成员关系表供查询“哪些父版本引用了此成员”、禁用检查与版本预览。它保存发布依赖，不能承载子执行队列或任务状态。

### 5.3 发布事务与幂等

1. 读取并校验草稿修订、模型与 profile，解析所有指定资产和成员版本。
2. 校验角色为规范化的小写标识、角色唯一、成员同租户且已发布、资产已审核、文件无冲突；直接选择/委派规则只引用清单内角色，coordinator 为父定义的保留角色。
3. 首期成员只接受 LEGACY_STABLE / SINGLE_SKILLED 的分析定义；实际子配置一律收窄到只读。检查自引用和已发布成员依赖循环。
4. 在发布事务内重新锁定草稿并核对 expectedDraftRevision；创建不可变定义版本、冻结配置、成员关系、能力绑定与运行时包，更新员工当前发布指针并写审计。
5. 同一 publish requestId 返回原版本及原 bundle，不重新编译或重新解析“最新成员”。编译、持久化或审计失败时全部回滚。

发布前预览只给预览 token / 内容摘要；正式发布须再校验同一草稿及引用。模型调用和外部网络不放进发布数据库事务。

### 5.4 内容哈希与缓存

`workspaceContentHash` 覆盖所有主/成员资产清单和文件字节哈希；`bundleHash` 覆盖员工模型、指令、工具目录、资产、成员版本/包哈希与实际运行策略。显示名变化若影响原生配置，也进入哈希。

`HarnessTemplateKey` 从冻结内容计算：bundleHash、实际策略哈希、模型配置、工具目录、全部资产与成员包。删除固定 `haizhuo-p0` 策略常量对新 profile 的决定作用。凭据、userId、Session/Run、当前工具视图与活跃预算不进入共享模板键。

团队根角色、direct/collaborative 与子叶子具有不同的有效静态策略。模板键须包含团队包、目标角色、执行位置和解析后的策略哈希，不能只用同一个 memberBundleHash 复用不同权限的模板；运行槽 ID 仍是本次上下文，不能固化在共享模板中。

旧 V1 包不重算、不覆写。读取时归一化为 LEGACY_STABLE，旧字段与旧状态键保持原义。发布新 V2 是新的不可变定义版本。

### 5.5 Session 固定行为

创建 Session 固定父 definitionVersionId；团队 Session 中这个版本就是协调者及所有角色的团队包，已固定成员、资产和直接选择/委派规则。父、成员或资产再次发布不改变既有 Session。升级团队版本、加入发布清单外员工仍通过新建 Session 完成；在当前团队清单内选择专家按 §3.2 保持同一 Session。

AgentRun 与 HarnessRunSpec 现有 employeeId/definitionVersionId 继续表达业务 Session 的归属与固定包，不覆写为目标成员版本。新增 executorRoleId/executorEmployeeId/executorDefinitionVersionId/runtimeSlotId 与实际执行配置引用；Worker 分别读取“团队来源”和“本次实际执行者”。成员作为根执行时也不得绕过 Session 固定包取其当前最新发布。

AgentExecutionRequest/RuntimeContextFactory 目前要求新调用的原生 ID 等于业务 Session ID。[C26]、[C27] TEAM 需新增可信 RuntimeExecutionScope/显式身份模式，区分 SINGLE_DIRECT、TEAM_ROLE 与 LEGACY；TEAM_ROLE 根据服务器槽位映射验证归属后设置原生 sessionId，Langfuse、Run 控制与对外事件继续关联业务 Session。不得靠改 employeeId 而复用同一个原生状态键切换专家。

运行时只解析 RunSpec 指定的包。管理员停用成员/资产是拒绝后续受理和委派的紧急开关，不允许自动替换为另一个版本。已接受但尚未执行的委派在调用边界重查可用性；正在执行的计算走取消或明确失败路径。

### 5.6 子实例、工作项与结果的版本快照

在子调用受理边界生成不可变的执行规格引用，保存到 §9 的调用关联；模型提供的配置只作为请求，服务端解析有效值：

| 类型 | 必须固定的内容 |
| --- | --- |
| 固定专家 | 根 RunSpec/团队包、专家发布版本/bundleHash、模型与批准资产、实际 CHILD 策略哈希 |
| general-purpose | 原生工厂类型与框架版本、父实际执行者规格、复制后的有效子配置/策略哈希、批准技能知识；不伪造独立员工发布版本 |
| 动态生成专家 | 定义来源 RUNTIME_GENERATED、创建 Session/Run、声明身份与哈希、批准模型/资产与有效子策略；不重新读取可变同名文件覆盖旧实例 |
| 工作项输入 | workItemRef、assignmentRevision、规范化契约哈希、精确 inputRefs/依赖结果及内容哈希、验收规则哈希 |
| 结果与复核 | resultId、完整内容哈希、来源调用、对应输入/规格哈希；复核明确记录 reviewedResultRef 和被复核内容哈希 |

assignmentRevision 是工作项输入契约修订，原生 TeamTask.version 是并发/状态版本，定义发布版本和结果内容版本另有来源；这几种版本不可互换。目标发生实质变化时生成新工作项；补充同目标的资料或修订方案时创建新的输入修订，各次调用保留旧快照。

父/子版本与资产更新不影响已受理调用；同一实例继续采用创建时的有效静态规格。成员/能力/资源停用和用户撤权仍在实际执行前重查，只能收窄或拒绝；版本冻结不能绕过实时授权。若新工作项需要扩大能力或更换模型，不能热替换现有实例，而应走批准范围内的新建与明确关联。

方案 P1 的复核只对应 P1 哈希；修订形成 P2 后生成新的复核输入。Team 的旧任务保持其原生终态，新复核走原生新任务或另一次受控工作项调用，不手工把 completed 改回 pending。上述字段是目标快照契约，尚未加入现有 RunSpec/数据库。

## 6. 原生工作区、物化与 JDBC 文件面

### 6.1 物化算法

DefinitionWorkspaceMaterializer 接收已经解析的不可变资产快照，依次：

1. 解析相对路径，验证最终路径落在 `<definitionWorkspaceDir>/<bundleHash>` 内。
2. 在同一文件系统的临时目录写全部文件及完整 manifest；重新读取字节校验哈希。
3. 校验主/成员入口、Skill 引用和知识索引完整，再发布目录；尽量使用原子 rename。同一哈希并发构建只接受完整赢家，不覆盖已有完整目录。
4. 用完成标记及 manifest 全部校验结果识别缓存命中；不能仅凭 AGENTS.md 存在复用。已存在但内容损坏的目录停止使用并重新物化；保留可诊断记录。
5. 失败临时目录与正式完整目录分开。启动/维护可清理确认未被引用的临时目录；不删除活模板引用的定义目录。

定义目录可从数据库资产重建，不包含用户运行文件。Windows 上的原子 rename、只读权限和并发赢家处理需真实文件系统验证。

### 6.2 存储装配

保留现有 JdbcAgentStateStore。新增原生 `JdbcStore.builder(dataSource).dialect(new MysqlDialect()).initializeSchema(false)`，组合 `DistributedStore`，传入主/子 Harness 与 `RemoteFilesystemSpec`。

原生 KV 表由新增 Flyway 按 2.0.3 MysqlDialect 建立；默认表名、索引、version 字段和更新语义在实施探针中逐一匹配。禁止用自动建表掩盖漏迁移，不自建第二套文件存储协议。

§6–8 的新能力构建缺少 JDBC 文件面时应失败，不能悄悄降级到本地文件后端。LEGACY_STABLE 保留旧配置，其缺少 Workspace 持久化的限制继续明示。

### 6.3 精确隔离与寻址

| 数据 | 主员工键 | 专家键 / 约束 |
| --- | --- | --- |
| AgentState | 单员工/协调者为可信 userId + 业务 SessionId；直接专家为可信 userId + 固定角色槽原生 ID | 委派使用原生创建的任务子 Session ID；不自动复用直接专家槽 |
| legacy AgentState | 原旧 harnessSessionKey | 首期新团队不在旧会话打开 |
| runtime agentId | 可信租户 + 员工 + definitionVersionId | 父版本、roleId、成员定义版本组成稳定标识 |
| 发布定义路径 | bundleHash 内容寻址 | 独立成员定义根和成员 bundleHash |
| 远程文件面 | 显式 IsolationScope.SESSION | 显式 SESSION，使用原生子 Session |

2.0.3 的 SESSION 远程命名空间是 `["agents", agentId, "sessions", sessionId, routeSegment]`，不额外包含 userId。Session ID 必须全局唯一；缺失身份时在执行前拒绝，不使用框架的 `default` 回退。

`HaizhuoNamespaceFactory` 只影响传给它的后端；RemoteFilesystemSpec 自己生成远程路由的命名空间。不能以已有 workspaceRuntimeKey 推断实际远程隔离已经成立。

### 6.4 路由与可写范围

| 文件范围 | 读取来源 | 写入策略 |
| --- | --- | --- |
| AGENTS.md、skills/、knowledge/、成员定义 | 只读发布资产；原生 overlay lower | 禁止模型与远端 overlay 覆盖、删除或重命名 |
| plans/ | 原生 SESSION 远程路由 | 主员工原生 Plan 工具可写；专家关闭 Plan 写工具 |
| agents/<agentId>/tasks/ 等框架记录 | 原生远程路由或框架仓储 | 框架维护；模型首期不直接编辑任务记录 |
| outputs/ | 显式 addSharedPrefix 后的 SESSION 远程路由 | 主员工可生成受控文本产物；专家禁止 |
| 其他路径、主机绝对路径 | 不向模型开放 | 拒绝访问，避免落入默认 LocalFilesystem |

RemoteFilesystemSpec 的 overlay upper 本身可以覆盖 lower；目录在操作系统上只读不能阻止远端覆盖。首先用原生 PermissionContextState/规则限制模型工具，再用薄路径护栏保护发布资产及允许根。框架自动更新文件若能绕过工具规则，则在公开 AbstractFilesystem 扩展点增加只限制路径的装饰，底层读写仍委托原生实现。

缓存命中前检测发布路径的远端覆盖；发现污染时拒绝执行并记录管理诊断，不能以被覆盖正文继续运行。定义完整性、路径穿越、远端同名覆盖与跨 Session 列举均是启用门槛。

仅把 RemoteFilesystemSpec 接线，不能证明任意运行文件都跨节点持久化。验收须关闭并重建 Harness/Store，切换本地物化目录，逐项读取计划、outputs 和框架任务记录。

## 7. 原生 Skill 与知识加载

新 profile 显式配置冻结技能来源、SkillFilter.only(已发布技能名)、只读知识入口，并继续关闭动态技能管理、Shell、tools.json 自动装配和 @ 路径展开。

主员工在系统提示中只得到技能名称/简介与知识入口，不预先把所有参考正文塞入提示。技能正文由原生 HarnessSkillMiddleware / SkillLoadTool 按需加载；2.0.3 的工具名为 `load_skill_through_path`，其模型可见与执行权限一起放行。知识由原生 read_file/grep_files/glob_files 在批准路径读取。

文件基线始终是发布包中的版本；模型不能从本机全局 Skill 仓库、其他岗位目录或动态下载获得未发布能力。新构建须核对 composeSkillRepositories 的实际来源和顺序，通过 SkillFilter 及路径护栏保证同名外部来源不会遮盖发布内容。

`disableDefaultWorkspaceSkills()` 在新 profile 中移除，以便采用显式的工作区来源配置；这项调整与资产物化、白名单和完整性验证一起交付。`disableDynamicSkills()` 保留，使用 2.0.3 的 frozen 中间件路径。不开放 skill_manage/propose_skill。

真实模型验收要有可辨认的 Skill 指令/知识事实，并观察原生加载行为；回答“看起来像用了技能”不足以证明指定版本确实被加载。确定性模型测试先验证装配与调用路径，真实任务再验质量。

## 8. 固定只读专家的原生接入

### 8.1 注册与子构建

固定专家使用原生 factory/registry 注册路线，以冻结成员清单为来源；`builder.subagentFactory(roleId, description, factory)` 可用于不依赖父执行作用域的构建和契约探针。正式委派需传递父 RuntimeContext 时，使用原生 SubagentEntry/SubagentFactory 扩展点与原生管理器，或经探针验证的 Run 作用域薄装配；具体接线在 SPEC-00/09 验证，不另写子调度器。动态专家按 §8.6 从当前 Session 的受控声明加载。同一固定角色不再同时加入 builder.subagent 或自动扫描的 subagents/*.md，动态声明不能覆盖已发布成员。

Builder callback 只接收角色名，不能捕获“当前用户”或把发布时的身份塞进共享模板。原生 parent-aware factory 接收的父上下文须核对可信 delegationScope，薄子构建函数消费不可变成员定义和进程组件，明确设置：

- 指定成员版本的模型、指令、技能、知识、独立定义根和稳定 runtime agentId。
- 同一原生 AgentStateStore、DistributedStore 与显式 SESSION RemoteFilesystemSpec。
- 只读工具集与冻结 SkillFilter；不注册父员工 SchemaOnly 业务工具。
- steps 上限；disableSubagents、disableDynamicSubagents、disableShellTool、disableMemoryHooks/Tools、disableTranscript、disableToolsConfig、disableAtPathExpansion。
- 子角色作用域、路径限制、父 Run 取消与预算关联中间件；不消费父 Run 的运行中引导。

专家的只读是“不能做业务副作用、不能由模型改文件”；框架保存 AgentState 和自身内部记录仍需要存储写入。

`asLeafSubagent()` 不属于本版本对业务开放的 API。使用公开禁用配置之后，还必须枚举最终 Toolkit，证明 agent_spawn、agent_send、动态创建、写文件与 Shell 没有可执行入口。

### 8.2 角色策略如何生效

自定义 factory 的原生 SubagentEntry.declaration 为 null，因此不能只创建一个 SubagentDeclaration 对象就假定所有字段生效。各字段落实位置如下：

| 冻结字段 | 首期实际落实位置 |
| --- | --- |
| 模型、指令、workspace、steps、skills | 薄子构建的公开 Builder 配置 |
| ISOLATED | 独立子定义根、原生子 Session 与显式子文件后端；验证无父对话自动复制 |
| tools | 子静态 Toolkit + 只读模型视图 + acting 执行拒绝规则 |
| persistSession=false | 该自定义注册路线的原生默认行为；契约探针固化每次新子 Session |
| exposeToUser=false | 可信 RuntimeContext 中 CTX_EXPOSE_TO_USER=false |
| 强制同步 | CTX_FORCE_SYNC=true、CTX_FORCE_SYNC_TIMEOUT_SECONDS=批准值 |
| 继承父权限上限 | 原生 DENY 传播 + 子 Scope 中间件进一步收窄；实际权限探针 |

如果需要持久子会话或声明中的远程/路由语义，后续再验证公开 SubagentEntry/SubagentsMiddleware 的注册组合；首期不把未接上的声明字段呈现为已生效功能。

### 8.3 完整只读工具集

| 工具类别 | 本次根执行 | 委派专家（CHILD） |
| --- | --- | --- |
| 原生技能加载、批准定义的读取/搜索 | 允许本次根角色范围 | 允许成员版本批准范围 |
| 原生 Plan 工具 | 协调者允许；直接只读专家关闭 | 关闭 |
| 固定/通用/生成角色 agent_spawn | TEAM_READONLY 按根角色和发布策略允许，动态路径见 §8.6 | 关闭 |
| agent_send | C 多轮协作探针通过后，根对本 Run 已受理专家允许；预算和身份重查 | 关闭 |
| 自治 team 工具、后台 task、动态角色管理 | 仅自治 profile 的内部 Team 实例按 §8.7 开放批准动作；后台提升与活 Team 动态成员管理关闭 | 自治 Team 成员按 §8.7 的动作白名单；普通 spawn/send 专家不注册 team |
| 受授权外部 TOOL/MCP | 协调者沿用父 Run 外部路径；直接只读专家关闭 | 不注册，拒绝调用 |
| 文件写、Shell、长期记忆、技能修改 | 协调者仅允许受控产物/Plan 写；直接专家只读；其余关闭 | 全部关闭 |
| 未识别的新原生工具 | profile 未明确批准时拒绝 | 拒绝 |

当前 CapabilityViewMiddleware 对“不在外部目录”的工具一律放行，不能沿用这个策略开放团队。新 profile 要同时维护原生工具类别白名单和外部工具视图，并在 acting 边界再检查真实工具调用。

原生 general-purpose 在子 Agent 功能开启时有内置工厂。获准的根角色通过 §8.6 的 generalPurposeEnabled 策略开放这条原生路径；未获准 profile 从模型可见说明中排除并在委派边界拒绝。Skill 文本和模型传入 agent_id 不构成角色授权。

### 8.4 上下文与控制传播

原生 DefaultAgentManager 会传播父 RuntimeContext 属性并替换为子 sessionId。保留可信 userId、根业务 Session/Run、attempt/fence；通过固定角色 Scope 增加 CHILD 标识、成员版本和只读限制，不改变根业务 Run 的所有者。本次用户选中的专家是 ROOT；只有其委派的调用为 CHILD，不按是否名为 coordinator 分类。

子调用的工具视图只能收窄。子执行不读取/消耗父 Run 的 RunGuidance；取消可以在父子各自的原生安全检查点观察。观测为同一 Run 下的子 span，子完成不能关闭主 Run 根 span。

模板中的中间件不保存某个用户的动态状态；权限、执行关联和预算放在本次 RuntimeContext 或平台仓储。两个用户并发复用模板时必须保持这些作用域独立。

### 8.5 同步、超时与最终交付

原生 agent_spawn 在默认超时下可能转为后台任务。首期由可信上下文强制同步，超时中断子订阅，不向后台提升；模型要求 timeout=0 或 expose_to_user=true 不能覆盖该设置。

委派专家正常结果回到本次根 Agent，由它汇总；用户直接选中的专家则直接产生该 Run 的根答案。委派失败或超时记录独立状态，框架将结果/错误返回根 Agent；根 Agent 明确说明分析缺失。若用户任务要求全部专家结果且未取得，不能给出“已全部完成”的交付描述。

AgentEnd 表示该次调用收尾，不能自动标为成功。无结果而结束记为 INCOMPLETE；超时、取消、故障以明确观察到的原因标注。同一专家上下文可以有多个 follow-up 调用，各次结果独立记录；业务 Run 最终成功只接受本次根执行的有效结果并通过平台结算。

### 8.6 动态专家创建（用户补充确认的需求）

用户确认在“发布定义 → 注册工厂 → 按需创建实例”的基础上加入动态创建，包含 **general-purpose 按任务创建通用实例**与**运行时生成新的专家定义**。本节调整前文仅允许固定角色的范围：获准的根角色可使用批准的动态路径；LEGACY_STABLE、未获准根角色和委派叶子的动态创建仍关闭。动态创建不改变已发布团队包、员工版本或用户业务权限。

#### 三种创建路径与选择顺序

| 路径 | 定义 / 工厂来源 | 运行时创建方式 | 适用情况 |
| --- | --- | --- | --- |
| 固定专家 | 已发布成员定义及受控工厂 | agent_spawn(固定 agent_id, task) | 有稳定岗位、专属技能或模型配置 |
| 通用任务实例 | 原生 general-purpose 内置工厂 | agent_spawn(general-purpose, task, label) | 职责随本次任务变化，现有批准能力足够 |
| 生成新专家定义 | 原生 agent_generate 生成声明，再由动态中间件注册工厂 | agent_generate → agent_spawn(新 agent_id, task) | 需要独立声明、配置或在本 Session 反复选择的专项角色 |

运行时先选择匹配的固定专家；任务可由现有批准能力完成时，优先用 general-purpose 直接创建实例；需要独立专家声明时才生成新定义。通用实例本身就是动态创建，不要求为每个临时职责新增发布版本或 Markdown 文件。三个路径的实例执行、跟进与推理均复用原生机制。

#### 原生 general-purpose 任务实例

已静态核对 2.0.3 的 HarnessAgentBuilderSupport 与 AgentSpawnTool：子功能开启时注册 general-purpose 工厂；每次 spawn 创建通用 Harness，采用原生叶子配置。默认无声明时 persistSession=false，生成独立 agent_key 与子 sessionId；后续 agent_send 通过已有 key 跟进同一实例，再次 spawn 创建另一个实例。

工具调用示意，参数名取自该版本原生签名：

~~~text
agent_spawn(agent_id="general-purpose", label="竞品分析", task="根据获准资料分析竞品，返回结论与依据")
agent_spawn(agent_id="general-purpose", label="风险复核", task="复核当前方案的风险，返回问题与依据")
~~~

这两个实例的 agent_id 都是 general-purpose，职责由 task 和批准资料确定。label 用于展示与跟进，不是授权依据；平台分别记录 delegationId、invocationId、原生 key/子会话及根 Run。不能按 general-purpose 名称或可能相同的 source 合并为一个专家执行，也不能将任务标签自动注册成正式数字员工。

原生通用工厂复制父模型、Toolkit、部分执行/记忆/计划配置、middlewares 与 hooks，并共享父 workspace/文件后端。新建子会话不代表获得独立文件权限，也不表示自动复制父完整对话状态。平台通过可信 CHILD 上下文、现有原生扩展点与执行边界校验收窄实际工具和文件范围；通用实例与固定专家遵守相同的首期只读、身份、预算、取消和安全输出规则。必须验证父 Plan 写入、业务 TOOL/MCP 等能力不会因 Toolkit 复制进入通用子实例的可执行面。

发布策略分别设置 generalPurposeEnabled 与 dynamicSubagentsEnabled：允许通用实例不要求同时开放声明生成。通用实例冻结父运行规格与批准能力，归属当前 Run；其任务结果可进入会话投影，不能据此宣称内存实例或 agent_key 支持跨 Run/重启恢复。若用户要长期选择该角色，走受控专家声明与稳定角色槽流程。

同一 Run 可有多个通用任务实例，并发上限仍服从统一预算。固定角色“同角色 1”的限制不能简单按 general-purpose 类型限制所有临时任务；通用任务改按 delegationId 限制同一实例的活跃调用。开放多个通用实例并行前，须先证明原生工具调用与子事件的完整关联；若仅能取得相同 source，暂不开放这项并发。

#### 原生生成、加载与执行链路

已静态核对本地 AgentScope Java 2.0.3：

| 原生组件 | 职责 / 实际行为 |
| --- | --- |
| SubagentSpecGenerator | 根据自然语言职责生成 Markdown/YAML 声明，用 AgentSpecLoader.parse 校验语法 |
| AgentGenerateTool / agent_generate | 检查名称和当前注册冲突；支持 dry_run；写 subagents/<name>.md；生成工具需要显式接线 |
| DynamicSubagentsMiddleware | 每个 reasoning step 读取声明并构造工厂、更新原生 AgentManager；动态声明默认可以覆盖同名静态成员 |
| AgentSpawnTool / agent_spawn、agent_send | 从已注册声明创建实例、执行任务与后续跟进；生成声明本身不等于已经启动专家 |

目标流程为：

~~~text
根 Agent 发现当前任务需要新专家
  → 原生 agent_generate 生成声明
  → 平台薄护栏校验职责配置、名称、权限、资产与预算
  → 写入原生隔离运行文件面
  → 下一 reasoning step 原生加载并注册工厂
  → agent_spawn 创建专家实例并执行
  → 必要时 agent_send 跟进，根 Agent 汇总结果
~~~

不另写声明生成器、动态注册器或子推理循环。动态中间件及生成工具显式接入；去掉 disableDynamicSubagents() 本身不能证明 agent_generate 已注册或权限已收窄。

#### 固定专家与动态专家共存

发布策略新增 generalPurposeEnabled、dynamicSubagentsEnabled、允许创建的根角色、实例/生成次数/定义数量上限与子迭代上限；旧包默认关闭。固定成员提供稳定岗位能力，通用实例承担本次任务职责，动态声明补充本 Session 的任务专项角色，例如“本次方案的竞品风险专家”。

动态名称使用受控 dyn- 前缀并保持原生 kebab-case 约束；同名生成竞争也需校验。禁止覆盖固定角色及 general-purpose 等保留名称；不能仅依赖生成提示词中的“不重名”，因为原生动态加载合并确实支持同名覆盖。

首期动态子专家继承获准的父模型和只读能力上限，只能引用已经批准的技能/知识。原生声明的 tools 为空可表示继承，平台仍须落实明确的实际工具白名单。拒绝任意 workspace.path、远程 agent URL、Shell、业务 TOOL/MCP、后台提升、用户暴露和递归动态创建；框架自身的状态保存继续允许。

声明校验在持久写入前执行，动态工厂在实例创建边界再次应用只读、身份、文件隔离和取消规则。原生语法校验不能代替业务策略校验；声明式子工厂的 StateStore/文件后端继承差异也必须纳入探针。

#### 范围、冻结与直接切换

动态声明归属于可信用户和当前业务 Session，底层原生文件命名空间与创建根角色运行槽关联。跨角色读取或用户直接选择动态专家时，服务器通过受控定义引用解析所属槽与声明，不能接受客户端任意文件路径或原生 Session ID。

生成时记录定义来源 RUNTIME_GENERATED、创建者、业务 Session、创建 Run、声明哈希及批准策略。调用实例固定该声明哈希；初期修改产生新声明身份，已有实例继续原版本。动态专家不自动拥有数字员工 employeeId，也不自动加入全局员工目录。

动态专家经策略校验后可进入本 Session 的临时专家列表。用户直接选择它时按 §3 的平台 Run/独立运行槽受理；任务委派仍使用独立子会话。若要升级为可供其他 Session 使用的正式专家，走管理员校验与员工发布流程。

动态注册集属于运行范围。原生 DynamicSubagentsMiddleware 会更新其 AgentManager，因此动态开启的构建先采用独立调用实例/管理器；全局缓存只复用不可变基础定义和工厂描述。两个用户并发复用一个含可变动态注册集的 Harness，必须经隔离探针证明安全后才能采用。

#### C 阶段追加验收

- general-purpose 不生成声明也能实际 spawn；同类不同任务得到不同实例，agent_send 继续原实例；关闭生成仍可按独立策略允许通用实例。
- 核对通用实例继承的真实 Toolkit、Plan、文件/状态后端、middleware 和身份；父能力不突破子只读约束。验证同类实例的工具与子事件关联后再开放并行。
- 生成后在下一 reasoning step 注册并实际执行，dry_run 不写入；正常 follow-up 保留同任务专家上下文。
- 动态专家能与固定专家串行、并行和复核协作；其事件有独立声明来源、执行位置与调用身份。
- 同名覆盖、非法字段、超额、越权工具、跨用户/Session/角色槽寻址被拒；生成与跟进分别计入批准预算。
- 动态定义可持久恢复不等于活执行可恢复；重启后的声明加载、原生子状态、取消与 Run 结算分别验收。
- 两个用户并发生成和调用不混注册集；直接切换动态专家继续原槽与原声明版本。

上述为设计补充，未执行通用实例、生成、MySQL、模型或并发恢复探针。固定版本源码入口：[HarnessAgentBuilderSupport](https://github.com/agentscope-ai/agentscope-java/blob/1b8e3dcd2338550ae5198bdb2a7bae56df5bf2e0/agentscope-harness/src/main/java/io/agentscope/harness/agent/HarnessAgentBuilderSupport.java)、[AgentSpawnTool](https://github.com/agentscope-ai/agentscope-java/blob/1b8e3dcd2338550ae5198bdb2a7bae56df5bf2e0/agentscope-harness/src/main/java/io/agentscope/harness/agent/tool/AgentSpawnTool.java)、[AgentGenerateTool](https://github.com/agentscope-ai/agentscope-java/blob/1b8e3dcd2338550ae5198bdb2a7bae56df5bf2e0/agentscope-harness/src/main/java/io/agentscope/harness/agent/tool/AgentGenerateTool.java)、[SubagentSpecGenerator](https://github.com/agentscope-ai/agentscope-java/blob/1b8e3dcd2338550ae5198bdb2a7bae56df5bf2e0/agentscope-harness/src/main/java/io/agentscope/harness/agent/subagent/SubagentSpecGenerator.java)、[DynamicSubagentsMiddleware](https://github.com/agentscope-ai/agentscope-java/blob/1b8e3dcd2338550ae5198bdb2a7bae56df5bf2e0/agentscope-harness/src/main/java/io/agentscope/harness/agent/middleware/DynamicSubagentsMiddleware.java)。

### 8.7 原生自治 Team 的详细设计

#### 8.7.1 具体场景与执行归属

例如用户请求“研究客户、编写方案并复核”。Team lead 使用原生任务板拆分工作，researcher 认领研究，reviewer 可直接向 researcher 索取依据；成员完成任务后通知 lead，lead 收敛方案。任务依赖和认领使用原生 TeamClient，成员之间不必让用户发消息或逐次由业务根转发。

一次自治 Team 是一个业务 Run 内部的协作过程。它有多个 Agent 轮次，不能把每轮 AgentResult 当作业务 Run 完成。设计采用以下组合：

~~~mermaid
flowchart TD
    U[用户请求与稳定角色槽] --> R[业务根 Harness]
    R --> E[run_readonly_team<br/>薄接线入口，等待本次 Team 收尾]
    E --> L[原生 Team lead<br/>本次 Team 的独立会话]
    L <--> T[原生 TeamClient / 持久任务板与消息]
    M1[researcher 原生 Harness] <--> T
    M2[reviewer 原生 Harness] <--> T
    T --> B[原生 TeamWakeups / MessageBus]
    B --> D[原生 WakeupDispatcher]
    D --> W[可信 WakeupTarget + 原生成员 TurnGate]
    W --> L
    W --> M1
    W --> M2
    L --> F[Team 收尾校验与安全完整结果]
    F --> R
    R --> O[唯一业务根结果与平台结算]
~~~

run_readonly_team 是**拟新增的薄工具入口**，不是 AgentScope 已有工具。它只接收 objective 和批准资料引用；服务端解析冻结角色、实例与所有权，组装并调用原生组件、等待结果、取消和释放资源。任务分解、依赖/认领、成员消息和 Agent 推理仍由框架完成；它不保存另一套任务板或重新实现协作调度算法。

业务根保留原先用户对话，Team lead 和成员使用本次 Team 的内部会话。Team lead 可经过多次唤醒轮次；这些调用和 worker 调用相对业务 Run 都是 CHILD。只有最外层业务根的最终结果能调用平台 complete。这样 Team lead 暂时结束一轮不会释放业务 Session 活动槽，也不会把内部工作消息写入用户直接对话状态。

#### 8.7.2 原生组件与平台接线

| 原生组件 / 行为 | 复用方式与本项目必须补的接线 |
| --- | --- |
| LocalTeamClient(BaseStore) | 同一个活跃 Team 的 lead/成员共用**同一个 client 实例**；BaseStore 接原生 JdbcStore；不为每个成员新建写入同命名空间的 client |
| createTeam / TeamCreateSpec | 用冻结成员构造原生任务板元数据；该方法不等于已启动成员进程 |
| HarnessAgent.Builder.teamsMode(client, context, sessionId) | 逐成员接入原生 TeamTool/TeamsMiddleware 并绑定独立原生 Session；builder.messageBus 接入共享总线与原生 inbox |
| WorkspaceMessageBus | 活 Team 共用一个 bus；使用隔离的受保护 busRoot 和已验证的原生文件后端；模型不能直接写队列文件 |
| WakeupDispatcher / WakeupTarget | 使用公开激活扩展点；薄 target 在当前父 Run 内调用已绑定成员 Harness，不启动第二套 Gateway 用户会话入口 |
| SessionTurnGate | 原生 gate 只互斥同一 Team 成员的内部轮次；业务 Session 的 Run 队列仍由平台唯一管理 |
| TeamContext.RecoveryContext | 恢复时注入已完成任务和受控历史资料；它是上下文输入，不是自动恢复引擎 |

TeamContext、TeamsMiddleware 和注册集含具体 Team/成员状态。只缓存不可变模型、定义和构建配置；含团队上下文的 Harness/中间件是调用范围对象，不放入全局 HarnessTemplateCache。所有内部调用重新构造可信 RuntimeContext，保留 user/业务 Session/Run/attempt/fence 和已冻结的权限。[N01]、[N09]、[N12]、[N14]、[N15]

#### 8.7.3 身份、实例与持久关联

| 标识 / 数据 | 设计约束 |
| --- | --- |
| teamExecutionId | 平台生成 UUID，标识本次自治过程；每 Run 首期最多 1 个 |
| teamName | 全局唯一，如 hb-{teamExecutionId}-g{generation}；不能仅用员工名、Session 内短名称或 tenant 局部名称 |
| namespace | 服务端按可信用户、业务 Session/Run 和 Team 身份生成并持久保存；拒绝缺失值及原生 default 回退 |
| memberName | lead 与固定批准成员的原生名称；维护它到业务 roleId/冻结版本的显式映射 |
| nativeSessionId | 每个 Team 实例、成员各自独立；与稳定直接对话槽、其他 Run 和已生成子任务会话分开 |
| teamRoundId / invocationId | 每次启动或唤醒各生成一条调用关联，带 attempt；同一成员不同轮次的事件/结果不能互相覆盖 |
| native message / task 引用 | 消息以 teamExecutionId + generation + nativeMessageId 关联；任务以 Team 身份 + taskId + version 关联 |

TeamsMiddleware 的成员注册键只包含 teamName 与 memberName，不包含 tenant/namespace；TeamWakeups 是进程级静态 hook。全局唯一 teamName 与逐成员绑定是隔离的必要条件。沿用原生 hook，不安装会覆盖其他团队的自定义全局唤醒 hook；在 Team 完整退出后撤销其原生 Session 注册。[N09]、[N13]

拟增加 platform_run_team_execution，记录 Run/attempt/fence、teamName/namespace、ownerWorkerId、generation、冻结策略哈希、native 数据引用及运行展示状态。拟增加 platform_run_team_member_binding，记录 memberName/roleId/成员版本/nativeSessionId 和调用关联；Team 展示状态可为 PREPARING/ACTIVE/DRAINING/SETTLED/FAILED/CANCELLED/RECOVERY_REQUIRED，不能替代原生 Task 状态。

**只有原生任务板负责 pending/in_progress/completed/failed 和依赖版本。** 平台表不保存可由另一个 Worker 认领的成员待执行队列。预算和有效 attempt 仍由父 Run 约束，记录仅支持可信寻址、生命周期与展示恢复。

#### 8.7.4 组建、消息与唤醒时序

1. 冻结本次 Team 成员、模型/资产、允许动作、任务与消息预算、时限；验证当前根角色有自治权限。记录 PREPARING 与可信成员绑定。
2. 创建原生 Team，构建 lead/所有批准成员的调用范围 Harness，绑定原生 Session，共享 client/bus，注册可信 target。创建失败明确关闭本次 Team，不能留下可被唤醒的半团队。
3. 启动原生 dispatcher，调用 lead 初始轮次，再转 ACTIVE。lead 用原生工具创建/分配任务；worker 被原生消息通知后读取 inbox/任务板并认领可执行任务，依赖关系由原生任务板判断。
4. sendMessage 先调用原生 BaseStore 写 TeamMessage，再经 TeamWakeups → inboxPush → enqueueWakeup → dispatcher 激活。对正在运行的成员，通知先进入 inbox；闲置成员启动新轮次。
5. worker 在完成工具中提交任务结果；原生 completeTask/failTask 保存状态并尝试通知 lead。lead 再读取任务板和批准结果，必要时重分解或提出新复核任务。
6. lead 申请 completeTeam 时进入 §8.7.6 的收尾检查；薄入口取得完整安全结果后返回业务根，业务根汇总正式答案，按 §12 完成唯一业务结算。

消息已持久化不等于对方已经执行；任务状态已改变也不等于 lead 已被唤醒。LocalTeamClient 的任务通知调用会捕获部分通知异常；结果以成功读取的原生任务板为准。平台将“消息发出、成员轮次开始、任务终态、Team 收尾、Run 完成”分别关联，不把其中一个直接推断成其他状态。[N09]、[N10]

WakeupTarget 不信任消息携带的 userId、agentId 或模型内容。2.0.3 TeamsMiddleware 的 enqueueWakeup 实际传入空 userId；target 必须从受信 member binding 查到真实属主/版本和有效父 Run，两个 runWakeup 重载都禁止匿名状态寻址。目标不属于当前活 Team、已失效 fence 或已关闭的调用，一律不执行。[N09]、[N12]

原生 dispatcher 的“检查闲置 → 调用”不是原子互斥，target 仍须 acquire 原生成员 gate。dispatcher 会跳过正在运行的目标；若消息在该轮最后一次读取 inbox 后到达，队列中的通知可能已经被移除。因此成员轮次释放 gate 后检查原生 inboxHasMessages，必要时合并并补发一次原生 wakeup；循环次数和总轮次受预算约束。消息驱动的再次调用仍走原生 dispatcher，不能另加一个平台规划循环。此竞态及队列 drain 后进程失效按 §17.5 做故障探针。

对任务通知失败，受管 worker 轮次收尾还需成功读取本轮新出现的 task/version 终态并合并一次给 lead 的原生提示，以观察到的任务版本去重。这里只补事实变化的唤醒提示，不替 lead 分配/重试任务；没有新事实时不持续启动空轮次。原生板读取失败时进入明确故障流程，不以异常降级的“无任务”结束。

#### 8.7.5 动作授权与规模约束

TeamTool 的 availableActions 为空时允许全部动作，不能把空列表当作禁用。每个成员提供明确且非空的名单，并在 acting/作用域 TeamClient 边界再次验证角色、namespace、目标、任务 owner、当前 attempt/fence 和预算。[N11]

| 角色 | 首期允许的原生动作 |
| --- | --- |
| lead | listTasks/listMembers/listMessages/createTask/assignTask/sendMessage/broadcastMessage/completeTeam |
| worker | listTasks/listMembers/listMessages/claimTask/completeTask/failTask/sendMessage |
| 所有角色禁止 | spawnMember/shutdownMember/submitPlan/approvePlan/rejectPlan；Shell、业务 TOOL/MCP、长期记忆写、后台提升、递归委派 |

claimTask 的 owner 固定为本成员，不能靠模型参数代别人认领；completeTask/failTask 限定自己的任务。2.0.3 的动作别名规则会随 claimTask 允许 listClaimableTasks/unclaimTask，薄边界也必须校验这些调用和实际归属。成员可向批准的其他成员/lead 发消息，不能向别的 Team 或任意会话发送。

LocalTeamClient 的 spawnMember/shutdownMember 和上述计划审批动作明确抛出“不支持，需要控制面”的异常；不能暴露工具后再假定框架会部署成员。首期预构建固定名单，平台不补另一套控制面。已认领任务不允许被 lead 改归属；所有状态转换继续走原生 CAS，任务 owner 检查与转换并发行为仍需探针，未通过不开放跨成员操作。

建议冻结默认：worker 最多 2 个，最多创建 6 个任务，模型主动消息/广播最多 20 次，Team 总 Agent 轮次最多 12 次、同时运行 worker 最多 2 个，每轮最多 4 次迭代，Team 时限 180 秒，自动重启次数 0。任务/消息总额跨父 Run attempt 保留，不能通过重建团队刷新额度；截止时间不因一次唤醒重置。

发布配置新增 autonomousTeamPolicy：enabled、allowedRootRoleIds、固定 roster 引用、allowedActionsByRole、peerMessageEdges、maxTeamExecutionsPerRun、maxTasks、maxMessageRecipients、maxRounds、maxParallelWorkers、maxIterationsPerRound、timeoutSeconds 和 autoRestartLimit。编译器检查这些值与只读工具/角色策略一致，将名单、预算及实际工具策略固定进 policy_json/RunSpec 和策略哈希。maxMessageRecipients 是实际主动投递收件人数上限；模型不能提交新的名单、实例地址或修改预算。direct/collaborative 模式不注册自治入口，autonomous 只注册已批准的入口，不通过用户请求 mode 扩权。

20 次统计模型发起的消息操作，原生任务通知由 6 个任务上限限制，通知数量另做观测；不能声称 sendMessage 外层预算能覆盖原生内部通知自调用。broadcast 按实际收件人数占用主动消息预算。超限在原生调用前拒绝，Team 明确失败/缺项收尾，不不断唤醒自循环。

#### 8.7.6 结束一轮、任务成功与最终结算

| 观察到的行为 | 可确认的含义 / 收尾规则 |
| --- | --- |
| lead AgentResult/AgentEnd | 该轮结束；若仍有工作，Team 保持 ACTIVE，父入口继续有界等待 |
| worker AgentResult | 该轮输出；任务成功要求明确的原生 completeTask，不能靠输出文字推断 |
| worker 正常轮次结束且自有任务仍 in_progress | 原生 TeamsMiddleware 会尝试 failTask；取消/异常路径须核查是否执行该收尾 |
| native completeTeam | 原生元数据标记；不是“所有任务已经成功且无活调用”的原子屏障 |
| 任务板读取出错 | 状态 UNKNOWN，停止成功结算并进入故障处置；不能接受原生 hasOutstandingTeamWork 的错误降级 false 作为完成证据 |
| 达到时限或任务失败 | 返回明确缺失项/错误；只有发布策略允许部分结果且业务根接受时，才形成有缺项说明的正式答案 |

lead 的 completeTeam 调用先经护栏禁止未结束任务，随后原生执行。父入口再进入 DRAINING，暂停新任务/成员轮次受理，等待正在运行的调用完整结束，并成功重读任务板、取得 lead 的安全完整汇总，核验必需任务成功或批准的部分交付规则、父租约/预算/时限。通过后 SETTLED；任何一步不确定都不提交 Run 成功。

原生完成标记与平台 Team/Run 投影不是同一个数据库事务；也不能声称 native completeTeam 是团队级 CAS barrier。原生板记录是事实来源，平台投影按 Team/task/version 幂等补齐。保存平台 Team 收尾、结果引用及其 Run 事件/Session 投影的操作在同一平台事务内；最外层业务根的结果与最终意图仍按 §12 唯一事务结算。

任务结果取原生完整 result 或独立完整结果引用；lead 的任务板 prompt digest 会截短展示内容，不能拿摘要当最终交付。成员原始互发文本默认 INTERNAL，用户仅看到批准的任务/进度摘要与安全结果，不逐条公开邮箱或内部推理。

#### 8.7.7 取消、租约丢失与生命周期

用户取消父 Run、总时限到达、预算耗尽或租约丢失时，先拒绝新消息动作和新成员轮次，关闭 dispatcher，再中断 lead/worker/父入口订阅。gate 等待必须可取消且不阻塞事件线程，已取得的 lease 在 finally 释放；只有确定调用已退出才清理原生会话注册和占位。

平台 Team 投影标记对应 CANCELLED/FAILED 或 RECOVERY_REQUIRED，保存仍未确定的任务和调用引用；不靠手工改 BaseStore 批量伪造原生 completed。迟到结果和失效回调不改变当前 attempt，也不创建消息投递。若尚无法证明旧调用停止，继续占用业务 Session 槽，按 §13.5 核查。

这部分已规定目标流程、组件接线、数据关联、授权、完成屏障和故障处理；**本轮仍只完成静态源码核对与设计，消息/唤醒/取消/恢复探针尚未运行**。

本次自治 Team 的任务实例、内部 lead 和随父 Run 收尾规则，遵守 §3.7 的兼容性约束；其私有工作邮箱不直接定义为未来群聊消息流。

### 8.8 父子任务契约、依赖与完整协作流程

本节是用户确认后补充的目标协议。所有业务字段、校验器和拒绝码均为拟议内容；本节不改变 2.0.3 的工具签名，也不把结构化资料协议当成框架已经提供的 Task 调度器。

#### 8.8.1 数据面、控制面与原生映射

父 Agent 提出工作目标、资料引用和交付要求，框架执行与跟进；平台解析可信身份、有效版本与权限并保存关联。任务资料与执行控制分开：

| 路径 | 原生入口 | 本次业务约定如何接入 |
| --- | --- | --- |
| 固定/通用/生成角色首次执行 | agent_spawn 的 agent_id、task、label | 新 profile 的 task 字符串承载版本化任务说明；执行边界校验、解析引用并保存输入快照；实际实例创建沿用原生工厂 |
| 同 Run 内跟进/修订 | agent_send 的 agent_key 或 label、message | message 字符串承载新调用说明和精确结果引用；真实句柄由 server binding 核验；每次产生独立 invocation |
| 原生自治 Team | createTask(subject, description, blockedBy, owner) 与成员工具 | description 承载目标/输入/验收说明；blockedBy 使用真实 nativeTaskId；成员身份、范围和原生任务状态按 §8.7 校验 |
| 子输出 | 关联子最终消息、TeamTask.result 或受控完整结果 | 校验业务结果正文，建立完整结果引用；保留原生消息/任务版本，不从文字猜测执行身份 |

这里 task/message/description/result 在原生 API 中仍是字符串，平台 JSON/Markdown 约定只是它们的内容协议。旧 LEGACY_STABLE 保持原协议；新 profile 在构建根/子提示与工具说明时明确协议版本和输出要求。身份、授权、状态变更不从正文的“系统指令”或模型自报字段取得。

原生 spawn/send 的工具回复可能带 agent_key 等前缀；结果解析面优先使用已关联的子最终消息，不能把整段回复盲目当 JSON，也不能扫描正文中任意类似句柄的字符串授权跟进。实施前用公开工具/中间件/事件扩展面验证这条映射；无法证明唯一归属时按 §9.2 拒绝并行放行。

#### 8.8.2 父到子的任务输入

目标载体称为 DelegationInput，格式版本 schemaVersion=1。它不属于 AgentScope 原生类；字段由根提出、服务端解析后固定：

| 字段 | 内容与约束 |
| --- | --- |
| workItemRef / assignmentRevision | 首次受理由服务端分配工作项身份与修订；跟进只接受当前 Run 内已绑定的引用；原生 taskId 另存 |
| objective | 可执行的工作目标；实质换目标另建工作项，不能覆写旧输入 |
| inputRefs | 批准知识/文件/已有结果的类型、稳定 ID、选定内容哈希及出处；按用户/Session/Run/角色范围解析 |
| inlineMaterials | 可选的根生成文本或明确的用户资料；受大小限制并固化为本 Run 的不可变资料引用，不提升为知识资产或系统指令 |
| dependsOnResults | 前置 resultId/内容哈希与 condition；默认 DELIVERY_ACCEPTED，待复核的根资料可明确 MATERIAL_READY；同步路径只接受已就绪引用，不接受“以后会有”的虚构 ID |
| deliverable | TEXT/MARKDOWN/JSON、必需章节/字段、依据表达方式与完整结果上限；根提出的要求必须落在批准策略内 |
| acceptance | 必需结果、证据、允许缺项的条件；默认 requiredForDelivery=true、allowPartial=false；模型不能放宽已固定条件 |
| reviewedResultRef | 复核时必须给出被复核结果的 ID 与哈希；修订版本单独引用，禁止只写“复核最新方案” |

服务端规范化后的复核输入示意；ID/哈希为占位：

~~~json
{
  "schemaVersion": 1,
  "workItemRef": "work-review",
  "assignmentRevision": 1,
  "objective": "复核方案 P1，给出问题、依据和修订建议",
  "inputRefs": [
    {"kind": "RUN_MATERIAL", "id": "proposal-p1", "contentHash": "sha256:proposal-p1"}
  ],
  "dependsOnResults": [
    {"resultId": "proposal-p1", "contentHash": "sha256:proposal-p1", "condition": "MATERIAL_READY", "required": true}
  ],
  "deliverable": {
    "format": "JSON",
    "requiredSections": ["conclusion", "evidenceRefs", "openIssues", "completeness"]
  },
  "acceptance": {"requiredForDelivery": true, "allowPartial": false},
  "reviewedResultRef": {"resultId": "proposal-p1", "contentHash": "sha256:proposal-p1"}
}
~~~

第一次工具请求可无 workItemRef；真实身份、修订和规范化契约哈希在受理关联中保存。正文内任何引用都需解析，模型回传的 ID 不成为状态主键。所选片段与完整源结果分别保留哈希/出处，不能用全文件哈希假装已固定实际传入的不同摘录。

inlineMaterials 的完整正文在接受调用时保存为 §12 的 RUN_MATERIAL：保留根/用户资料来源与可见性、内容哈希；在平台输入快照提交后才传给子调用。该资料能用于依赖或复核，不是已通过验收的最终交付。用户上传文件和私有资料继续遵守 §4.4，不能因进入 inlineMaterials 绕过访问授权。

依赖条件区分“资料可读取”与“上游交付已接受”：MATERIAL_READY 只表示批准的完整根资料已保存、可读且哈希一致；DELIVERY_ACCEPTED 还要求相应输入修订的结果检查与根接受事实。风险复核必须能够接收尚未通过风险验收的 P1，因此上例用前者；竞品/需求等必需分析结果用后者。模型不能将失败的子交付改包装成根资料，借此消除原有必需工作项的检查；来源与根 completion gate 一并核验。

#### 8.8.3 可信执行上下文与权限交集

ExecutionScope 由服务器创建，包含可信 tenant/user、业务 Session/Run、根运行槽、attempt/fence、ROOT/CHILD、delegation/invocation、有效规格引用、实际工具/资料视图、剩余预算、deadline 与取消信号。子原生 sessionId 创建后关联到该 Scope；仅传任务文本不能满足这一控制契约。

每个子调用使用自己的 Scope，不能在共享 RuntimeContext/中间件成员变量里修改“当前子角色”来服务并行调用。原生父属性传播之后仍核验 CHILD 标记和可信映射；复制 Toolkit 不证明子策略已经落实。

有效子权限不得超出：

~~~text
当前用户授权 ∩ 父 Run 批准范围 ∩ 子角色/通用实例策略 ∩ 目标资源授权
~~~

- 创建、跟进、技能/文件读取和真正工具执行各自校验；可见工具列表不是最终执行授权。
- 资料引用核对同属主/允许 Session、角色可见范围、内容版本；结果 ID 或 label 不授予权限。
- 原生 ALLOW/ASK/DENY/BYPASS 不替代海卓业务授权；确认不能补足缺失授权。
- 固定专家、general-purpose 与生成角色首期同样只读；Shell、业务 TOOL/MCP、递归委派和未批准文件写不能随父配置继承。
- 静态规格固定，用户撤权/成员停用/资源禁用在真正执行前重查；拒绝后明确收尾，不切到另一个成员规避。

普通用户可见结果与可供模型共享的结果分别审核范围。子思考链、内部邮箱、凭据和原始敏感参数不进入父任务资料或 USER 投影。Child 作为资料返回的文字不能扩展 root 的指令与授权。

#### 8.8.4 子到父的结果与交付检查

目标正文称为 DelegationResult。新 profile 按输入要求输出完整 TEXT/MARKDOWN 或受控 JSON；以下 JSON 字段是业务协议，身份仍来自关联 Scope：

| 内容 | 规则 |
| --- | --- |
| conclusion / deliverables | 完整结论或有权读取的交付物引用；不能用展示摘要替代正文 |
| evidenceRefs | 对批准资料/结果的引用及定位；核验出处和版本，不能仅凭模型编造 ID |
| missingInputs / openIssues | 缺失资料与未解决问题；允许空列表，不能因字段存在就断言已完成 |
| completeness | COMPLETE/PARTIAL，是模型声明；平台的格式/引用检查与根的交付判断分别记录 |
| reviewedResultRef | 复核时须匹配本次输入的目标哈希；模型指向另一版本时拒绝用于本次验收 |
| server provenance | resultId、完整正文哈希、workItemRef/输入修订/契约哈希、来源 invocation 与有效规格；由服务器补齐 |

子返回示意；这里格式有效，但交付声明为 PARTIAL，不满足上例 allowPartial=false：

~~~json
{
  "conclusion": "方案 P1 的实施成本尚无依据，当前不能确认预算风险",
  "evidenceRefs": [
    {"id": "proposal-p1", "contentHash": "sha256:proposal-p1", "locator": "预算章节"}
  ],
  "missingInputs": ["实施成本估算及来源"],
  "openIssues": ["取得成本资料后重新复核预算"],
  "completeness": "PARTIAL",
  "reviewedResultRef": {"resultId": "proposal-p1", "contentHash": "sha256:proposal-p1"}
}
~~~

格式检查记录 FORMAT_VALID/FORMAT_INVALID/UNVERIFIED；根的交付判断记录 ACCEPTED/REVISE_REQUIRED/REJECTED 及原因、验收规则与使用结果引用。平台检查结构、授权、引用、版本与必需项；内容正确性通过根/复核角色及质量验收判断，不承诺仅靠 JSON 校验证明事实正确。

这类检查是结果事实，保存在调用/结果元数据并形成安全投影，不成为可被另一 Worker 认领的 Task 状态。必须区分：

| 观察到的事实 | 可以推断什么 |
| --- | --- |
| 子 invocation 正常结束并返回结果 | 本次执行结束；内容可仍为 PARTIAL 或需修订 |
| 原生 TeamTask.state=completed | 框架任务已按原生接口完成；不能代替平台资料检查和根交付验收 |
| 必需结果通过本次输入版本的交付检查 | 可以作为后续汇总的已接受资料；不能直接结束根 Run |
| 根完整结果及平台完成事务提交 | 本次 Run 正式交付；仍不等于渠道已送达 |

格式非法、缺必需结果或只返回摘要时保留受控诊断，不伪造 COMPLETE。根可在有效预算内原生 send 要求修订；各次新结果独立保存。同一个工具执行被幂等重入不能触发第二次模型修订。

Team 的 completeTask 在执行边界核验 owner、格式、批准引用和该工作项允许的完整性；真实状态转换仍调用原生 API。结果标记 completed 后若需要新的语义复核/修订，创建新原生任务，旧版本保留。成员轮次结束没有 completeTask 的情况继续按 §8.7.6 处理。

#### 8.8.5 依赖、并发、重试与收尾规则

| 情况 | 原生执行与薄边界规则 |
| --- | --- |
| 互不依赖的任务 | 根可同轮调用多个 agent_spawn；总次数/并行占位按 §9 一次受理；每个实例、输入和结果分别关联 |
| 同步路径有前置结果 | 根按 MATERIAL_READY/DELIVERY_ACCEPTED 取得并检查精确结果后再发起下游；依赖未就绪/哈希不匹配在本次调用前拒绝，不进入平台等待队列 |
| Team 的任务依赖 | 原生 blockedBy/claimable/claimTask/CAS 判断任务是否可认领；平台只校验真实同 Team 引用、输入资料/版本与授权，不另写拓扑调度 |
| 前置任务 failed 或资料不可用 | 原生 failed 不满足 completed 依赖；lead/root 在时限内决定明确补做、允许的降级或失败收尾；无人工将 failed 改成 completed |
| 可选结果缺失 | 只有已批准的部分交付策略允许，根才能输出有缺项说明的结果；不得把必需项改成 optional 清除失败 |
| 重试/修订 | 每次显式新调用有新 invocation/输入修订并消耗剩余额度；同 toolUseId 重入只返回同受理记录；不自动刷新次数或截止时间 |
| 取消、超时、租约失效 | 先关闭新调用/跟进受理，再取消全部活跃子调用；待确实收尾后释放占位，未知执行按 §13.6 核查 |

普通同步协作不维护另一个平台 DAG：dependsOnResults 是本次输入的就绪/版本校验，根循环选择顺序。Team 依赖边写原生板，平台校验不创建队列、不主动扫描派发。createTask 的引用须真实同 Team，拒绝自引用和无效任务；不宣称框架会验证所有业务依赖与内容验收。

同一实例同时最多一个调用，避免 follow-up 与前轮写同一状态。多个 general-purpose 实例并行必须有不同的 delegation/native child session 和完整事件关联；类型名、label 或 source 不充当主键。批量受理须在一致事务中检查总预算并占位，数据库事务提交后才执行原生调用；不在锁内等待模型。

同一 Run 内的根最终答案须引用已固定的必需工作项结果/检查事实，平台 completion gate 校验缺项、输入版本、有效 attempt/fence 和部分交付策略，再按 §12 结算。这个 gate 不替根作任务分配或计算内容真假；它阻止已有必需项尚未处理就写成功。方案质量仍需实际模型与业务验收。

#### 8.8.6 general-purpose 的完整案例

业务 Session S 固定团队版本 V；用户向协调者提交“根据竞品和客户需求形成方案，并复核风险”，创建根 Run R。所有 T1–T4 都是 R 内的工作项，不创建新的业务 Run。

~~~mermaid
flowchart LR
    R[根 Run R：冻结规格 V] --> T1[T1：general-purpose<br/>竞品分析]
    R --> T2[T2：general-purpose<br/>需求分析]
    T1 --> P[T3：根形成方案 P1<br/>不可变资料引用与哈希]
    T2 --> P
    P --> T4[T4：general-purpose<br/>复核 P1 风险]
    T4 --> F[根修订、必要时再复核<br/>完整结果与 Run 结算]
~~~

1. T1/T2 各自固化输入和只读规格，原生创建 D1/D2、子 S1/S2、调用 I1/I2；通过同类并行关联验收后才同时执行。
2. 两项结果各自保存正文/引用与检查事实。根取得必需结果后形成 P1；作为 inlineMaterials 受理快照保存完整资料与哈希，不能只在 SSE 中存在。
3. T4 调用 D3/I3，reviewedResultRef 精确指向 P1。若根输入还没有完整方案，不能从一开始把 T4 当作与 T1/T2 无依赖的任务。
4. 根采纳复核形成 P2。P1 的复核不能冒充已复核 P2；需要复核 P2 时，对 D3 使用原生 agent_send(message=新输入说明)，产生 I4 与新输入修订，保留原子上下文。
5. 当前建议预算为 4 次 spawn/send；上述 3 次 spawn + 1 次 send 已用满。继续互评会被预算拒绝，根按完整/部分交付策略收尾，不能默默增加第五次。
6. 唯一根最终结果在有效所有权下结算，关闭 R 的全部子寻址。用户后续选择固定专家产生新 Run，明确引用 P2；不把 D3 的临时句柄自动变成稳定专家槽。

T3 是根自己的工作，可没有 delegation/nativeTaskId；它的资料引用记录根 Run 来源。换成 Team 模式时使用预构建批准成员和真实 native Task 引用，沿用同样的输入/结果版本约定；普通 general-purpose 工厂实例不会自动进入活 Team 成员表。

本节源机制已静态核对 [AgentSpawnTool](https://github.com/agentscope-ai/agentscope-java/blob/1b8e3dcd2338550ae5198bdb2a7bae56df5bf2e0/agentscope-harness/src/main/java/io/agentscope/harness/agent/tool/AgentSpawnTool.java)、[TeamTask](https://github.com/agentscope-ai/agentscope-java/blob/1b8e3dcd2338550ae5198bdb2a7bae56df5bf2e0/agentscope-harness/src/main/java/io/agentscope/harness/agent/team/TeamTask.java)、[LocalTeamClient](https://github.com/agentscope-ai/agentscope-java/blob/1b8e3dcd2338550ae5198bdb2a7bae56df5bf2e0/agentscope-harness/src/main/java/io/agentscope/harness/agent/team/LocalTeamClient.java)。数据协议、归一化接线、并发关联、格式检查与 completion gate 都尚未实施；按 §17 的 C15/C16 验收。

## 9. 委派预算与执行关联

### 9.1 预算是调用护栏

新增薄 DelegationPolicyMiddleware，使用公开 `MiddlewareBase.onActing(ActingInput.toolCalls)` 在原生工具执行前校验角色、同租户、成员状态、允许工具与预算。执行和等待继续调用框架的 next，不自建子推理循环、任务队列或轮询等待器。

执行目标按来源解析：固定专家从冻结成员清单取得；BUILTIN_GENERAL_PURPOSE 从 generalPurposeEnabled 与获准根策略取得；RUNTIME_GENERATED 从当前 Session 的批准声明/哈希取得。合法通用实例没有独立成员发布版本；生成角色也不能只因某个文件存在就得到授权。目标别名、label、模型自报员工 ID 和原生 agent_key 都需可信映射，不作为全局角色授权依据。

拟新增 `platform_run_delegation_budget` 与 `platform_run_delegation_reservation`：

| 内容 | 规则 |
| --- | --- |
| Run 总次数 | 每个 agent_spawn/agent_send 受理时递增；绑定 Run，重试与工具恢复不重置 |
| 并行数 | 每次 invocation 受理时占位，该次原生生命周期收尾/取消时释放 |
| 同角色限制 | 固定角色在同一个 Run/attempt 最多一个活跃调用；general-purpose 按 delegationId 限制同一实例单个活跃调用，同类并行须通过 §8.6 的事件关联验收 |
| 幂等键 | runId + attemptId + native toolUseId；新 follow-up 是新调用，同一边界重入不重复占位 |
| 所有权 | 占位/释放都校验当前 attempt/fence 与状态；旧 Worker 不释放新尝试额度 |
| 不确定恢复 | 不把“进程没了”当作计算已安全结束；先撤销旧执行所有权，再关闭旧占位 |

预算行记录批准上限、totalAcceptedInvocations、计数版本和审计。reservation 记录 delegationId、invocationId、roleId、attemptId、toolUseId、占位/关闭状态及原因。平台接受 follow-up 前验证原生 agent_key 与本 Run/根槽的可信关联，不能调用先前其他 Run/用户生成的专家句柄。它们负责限额与关联，不代替 TaskRepository 的原生任务状态。

非法角色、未发布成员、超额或不允许的工具在执行前产生受控策略失败。首期整批 acting 预检通过后才交给原生执行；预检失败时本批不执行，并以明确业务码结束当前根调用，不返回看似已完成的专家结果。框架有可复用的原生拒绝反馈面时由 A0 验证后接入；平台不伪造一套工具结果继续调度。

### 9.2 delegationId 与原生身份

首次 spawn 受理生成稳定 delegationId，表示本业务 Run 生成的专家上下文；spawn 和每次 agent_send 另生成 invocationId，关联 native toolUseId、roleId、成员版本和当前 attempt。工作项另以 §3.6 的 workItemRef 关联，不能用 delegationId 代替所有工作项身份。原生开始/结果/结束补充对应调用的 childSessionId/source/replyId；native taskId 只有框架确实给出时才保存。原生 agent_key 作为内部寻址引用保存，不转成普通用户可用的直聊授权。

source 标识来源路径，可能在同一角色重复调用时相同；不能单独当执行主键。原生工具开始/结果与子生命周期是否一一对应，需要探针验证。固定角色首期禁止同角色同时活跃；general-purpose 的多个任务实例按 §8.6 的关联验收开放并行，缺少完整关联时仍串行执行，避免把两个调用混在一起。

合成的子开始事件与子内部消息 replyId 可能不同，探针必须记录这两类 ID 的真实关系。消息身份按它自身的 replyId/blockId 保存；delegationId 作为外部关联，不改写原生 ID。

无法可靠关联的事件保留管理诊断并拒绝进入主答案，不能猜测员工或把它转成根完成。若公开扩展点不足以关联，再增加只包裹原生委派调用的薄关联适配；这个结果决定 C 阶段是否可放行。

### 9.3 平台子执行投影

拟新增 `platform_run_delegation` 保存 delegationId、根 Run、成员版本、原生子 Session/agent_key 引用及专家上下文关联；platform_run_delegation_invocation 保存 invocationId、delegationId、attempt、toolUseId、来源、结果及收尾原因。卡片展示专家以及其每轮调用，各 invocation 状态为：

~~~text
ACCEPTED → RUNNING → SUCCEEDED / FAILED / CANCELLED / TIMED_OUT / INCOMPLETE
~~~

首次结果成功不代表此专家上下文永远结束。delegation 的会话状态按 ACCEPTED → AVAILABLE（可继续跟进）→ CLOSED/CANCELLED/INVALID 记录；是否正活跃由 invocation 判断。根 Run 收尾后关闭所有 delegation 寻址，后续用户直聊走角色运行槽；不自动沿用任务内 childSessionId。

这些状态仅是展示和审计投影。同步只读路径不假定一定产生原生 TaskRepository 的 taskId；只有原生后台任务阶段才把 TaskRepository 作为任务持久事实源。平台不会根据投影再启动一个专家 Worker。

### 9.4 工作项、规格、调用与结果的关联

沿用拟新增 delegation/invocation 与结果表，增加工作项/输入修订、契约与执行规格引用/哈希、资料与依赖引用、检查事实。字段可采用明确索引列 + 版本化 JSON；实施时在 M5/M4 分组定稿，不增加任务队列或活动工作项调度表。

| 关联 | 约束 |
| --- | --- |
| workItemRef + assignmentRevision | 同一个 Run 内稳定的输入修订；同一身份/修订不能对应不同契约哈希 |
| delegationId | 本 Run 的实例上下文；一项工作可由多个实例协作，一个实例在本 Run 内也可承接受控新工作项 |
| invocationId | 关联一个明确的输入修订与执行规格；一次 Team 轮次可处理多个任务，以显式关联引用记录，不能只放一个 taskId 丢弃其他任务 |
| native refs | nativeTaskId/version、childSessionId、toolUseId、replyId/blockId；Team 引用同时包含 teamExecutionId/generation/memberName/teamRoundId |
| resultId + 内容哈希 | 对应工作项/输入修订/产生调用；复核另外记录 reviewedResultRef；原生 Task 版本不代替结果哈希 |
| 检查事实 | 输入哈希、结果哈希、规则哈希、FORMAT_* 与根交付判断、检查者/原因；由受控流程产生，不能照抄模型自报成功 |

新调用受理在同一平台事务内完成：校验当前 Run/attempt/fence、句柄与资料归属 → 固定工作项输入及规格 → 预算占位 → invocation/DELEGATE_ACCEPTED/Session 投影。正文存储与哈希写入失败则回滚，不执行对应原生调用；事务提交后才进入框架，不持锁等模型。

同一 runId + attemptId + native toolUseId 重入且输入摘要一致时复用同一次受理；摘要不同是幂等冲突。新 toolUseId 不自动意味着允许重复工作：根须明确它是补做、修订还是新工作项，服务端检查旧结果/修订引用与预算。失效尝试的未确认实例不能在新 attempt 下直接复用。

子安全结果正文、平台 invocation 结果/检查事实、Run 事件与 Session 投影在一次平台事务保存。同步路径必须在可验证的公开完成扩展面确认持久结果，再将受控结果交给根消费；若现有扩展面不能保证该顺序，先明确窗口并采用失败/核查处置，不能以事件订阅“通常很快”证明同步。原生任务终态与平台事务的差异按 §13.6 补读，不能重跑模型来补投影。

## 10. 执行事件契约：保留原生身份

### 10.1 BrainAgentEvent 的新边界

保留 runtime-api 与 AgentScope 的依赖边界，继续使用 BrainAgentEvent 作为平台端口。改造重点是给业务事件附上原生描述，并保留用户界面真正需要的来源与消息标识；不把框架全部事件种类重新命名一次。

拟新增不可变 RuntimeEventDescriptor，包含 nativeEventId/nativeType/nativeCreatedAt/source/replyId/blockId/toolCallId、原生 childSessionId/taskId（可空）与服务端确认的 ROOT/CHILD 归属。另有业务关联 runId/attemptId、executorRoleId/runtimeSlotId、实际 employeeId/definitionVersionId、delegationId/invocationId，以及固定团队版本引用。

自治 Team 另附 teamExecutionId/generation/memberName/teamRoundId 和可信执行种类 TEAM_LEAD/TEAM_MEMBER；其每轮 invocationId 独立，delegationId 可空。内部 Harness 的 source 即使为空，仍按受信 Team Scope 判为 CHILD，不可套用“source 为空就是业务根”的判断。Team 工具消息不是新用户请求，不创建另一个 Run 或改用匿名 userId。

原生类型名按框架原值保留。平台只定义少量业务结果：主文本/最终结果/挂起/取消/失败、计划快照、专家展示与生命周期投影。BrainAgentEvent 本身是内存契约，不自动表示已持久化。

原生异常或平台校验失败可能没有 nativeEventId；使用独立平台事件 ID，并标注 PLATFORM 来源，不能伪造框架 ID。runtime-api 不直接依赖或序列化 `io.agentscope.core.event.AgentEvent`。

### 10.2 主与子的分类规则

| 原生事件 | ROOT | CHILD |
| --- | --- | --- |
| AgentStartEvent | 绑定根调用身份 | 绑定 delegation 或 Team/成员轮次与原生子 Session |
| TextBlockDeltaEvent | 主消息增量，保留 replyId/blockId | 专家增量，独立消息/卡片 |
| AgentResultEvent | 主运行时完成候选 | 专家或 Team 成员该轮结果；不能创建 AgentRunCompletedEvent，也不等于任务板已完成 |
| RequestStopEvent | 主取消候选 | 子停止，不直接结束父 Run |
| RequireExternalExecutionEvent | 沿用主业务工具挂起路径 | 首期禁止；受控策略失败，不把结果送父会话恢复 |
| Plan 工具事件 | 主 Plan 投影 | 只读专家关闭；异常事件不改主计划 |
| AgentEndEvent | 调用收尾，不证明成功 | 专家生命周期结束，不证明取得结果 |
| 思考事件、敏感工具参数 | 内部诊断按需保留引用 | 不进入普通用户与渠道输出 |

直接 Harness 流的 source=null 根事件规则在 2.0.3 探针中固化，同时用可信执行 Scope 和开始关联验证；未知 source 不默认为根执行。若未来换成 Gateway/远程传输，必须重新验证来源规则。

AgentScopeRuntime 的 suspended 标记仅响应根挂起，终态过滤与 observer.onCompleted 同样只针对根，包括用户直接选择的专家根调用。Translator 的清理绑定本次调用：计划缓冲键至少含 runId + attemptId + source + invocationId + toolCallId；子结果只清理所属子范围。

每次 execute 的事件缓冲由调用作用域管理，完成、失败和取消通过最终清理释放。共享 Translator 不保存缺少 attempt 的跨调用缓冲，避免同一 Run 的两次尝试相互覆盖。

### 10.3 对外 V2 信封

沿用现有 StreamEvent 的 `schemaVersion` 命名，不另外引入 protocolVersion。保留 sessionCursor/runSequence/streamOffset 与现有 USER/INTERNAL 可见性；“专家进度”使用展示类型，不能成为新的绕过授权的可见性。

### 10.4 消息归并与重试

根消息与委派专家消息分别按 runId + attemptId + runtimeSlotId + delegationId/invocationId + native replyId + blockId 归并；Team 内部事件另外绑定 teamExecutionId/generation/memberName/teamRoundId，并按可见性过滤。相同 source 的两次 spawn 为不同专家上下文；同 delegation 的 follow-up 在同专家卡片内形成不同轮次，不覆盖上一轮。不同 block 不拼成同一正文，切换角色也不把其答案合并到旧角色气泡。

新的执行尝试出现后，旧 attempt 的 delta 不再修改当前答案；历史已提交事件保留原尝试标识。前端发现瞬时 streamOffset 跳跃时显示同步中，等待持久结果整体校准。

每个根 Run 只有一个业务最终答案，其 resultId 与消息身份及实际回答角色关联。用户直接选择专家的根结果也构成该轮正式回答；委派 invocation 结果只校准对应专家轮次。SSE id 只绑定已提交的持久序号，不给 delta 设置可回放 ID。

## 11. Run 持久事件与会话投影

### 11.1 保存什么

| 内容 | 保存方式 |
| --- | --- |
| Run 受理、开始、等待、完成、失败、取消、恢复待核查 | Run 事实 + 同事务会话投影 |
| 主完整最终结果 | 独立结果正文；事件保存摘要、resultId、原生引用 |
| 专家上下文、各轮受理/开始/结束及安全结果 | Run 事实 + delegation/invocation 读取投影 + 会话投影 |
| 工作项输入修订、有效子规格、资料/依赖引用、交付检查 | §9.4 的不可变关联与完整结果元数据；对应业务变更与 Run/Session 事件同平台事务；不是第二份原生任务状态 |
| 根中间方案与委派 inlineMaterials | 保存完整 RUN_MATERIAL 和内容哈希；用户可见性按来源与批准策略过滤，不自动成为根最终答案 |
| 自治 Team 关键状态、成员轮次、任务安全摘要和结果引用 | 原生板为任务事实源；平台 Team 读取投影与对应 Run/Session 事件在同一平台事务写入；原生与平台之间可幂等核对补齐 |
| 主计划更新 | 原生计划文件为执行存储；用户可见快照与引用作为事件 |
| 文本 delta | 瞬时流，最终结果补读校准 |
| 思考过程、原始敏感工具参数 | 不进入普通用户展示事件 |

新增事件类型建议使用既有大写业务类型：DELEGATE_ACCEPTED/STARTED/COMPLETED/FAILED/CANCELLED/TIMED_OUT/INCOMPLETE、RUN_RECOVERY_REQUIRED。流式展示类型保留 message.text.delta 等命名。不为每个原生事件建立一张表。

DELEGATE_* 携带 invocationId，描述该次执行；新增 DELEGATION_CLOSED 描述任务专家上下文关闭。用户选择其他角色时在对应 Run 受理/开始事件中记录固定目标，持久展示其实际回答身份，不把前端选中动作伪装成已执行切换。

关联 payload 增加 workItemRef、assignmentRevision、输入/结果/规格哈希及安全交付摘要；交付检查可使用 RESULT_CHECKED 事实，与 DELEGATE_COMPLETED 的执行结束含义分开。原始 task/message/description、可信 Scope 与私有资料不整体推送给用户。快照和最终状态从持久引用校准，不能只依靠一段子流式文字判断已验收。

自治 Team 采用 TEAM_ACCEPTED/STARTED/SETTLED/FAILED/CANCELLED、TEAM_ROUND_STARTED/ENDED 与 TEAM_TASK_UPDATED 的少量展示事实；任务更新附原生 taskId/version，普通用户只读批准摘要。原始互发消息默认 INTERNAL，只有经过结果策略的内容才形成 USER 投影。它们都不代表根 Run 已完成。

### 11.2 统一写入与事务

引入基础设施内部的 JdbcRunEventAppender 统一取号、写 Run 事实、分配会话游标、写 Session 投影。所有现有 Session、Run、工具执行和审批仓库调用该组件，并处于业务变更事务内。

事务语义为：

~~~text
校验属主 / 当前 attempt 与 fence
  → 业务状态或结果变更
  → RunEvent(runId, sequenceNo)
  → SessionEvent(sessionId, sessionCursor, runId, runSequence)
  → 必需的专家读取投影 / 交付意图
  → 一起提交或一起回滚
~~~

这里会话投影是为跨 Run 查询与 SSE 续传保存的读取表。同一 Session 的 Run A:seq1、A:seq2、B:seq1，分别取得 sessionCursor 1、2、3。AgentState 恢复不依赖这张表。

关键持久写入失败须让其业务事务失败；计划等可降级展示事件可在自己的事务失败后降级，但不能留下“Run 事件成功、会话投影缺失”的半次写入。

多个写入点采用一致锁顺序，候选为 Session → Run → attempt → runtimeSlot → tool/delegation/delivery。认领、审批和取消等路径需共同核对，不在持有数据库锁时等待模型或渠道网络。死锁后的有限事务重试须保持事件与意图幂等。

### 11.3 游标、保留与重建

当前 MAX(session_cursor)+1 可被投影裁剪/重建影响。新设计在 platform_agent_session 增加持久的 next_event_cursor，迁移从已有投影最大值初始化；分配时锁 Session 行，游标不因裁剪回退。

Run 事实新增可空 session_cursor 元数据。新事件同事务保存这个游标，投影重建可保留原 ID；已有事件从 V14 投影回填对应关系。历史工具/审批事件此前缺少投影，补入时分配新的高位游标并保留原 occurredAt，不重编号已发给客户端的事件。

原始时间描述发生时间，游标描述可补读的提交顺序，二者不能混同。历史补入在界面按事件标识去重，明确为历史记录。

保留窗口过期返回 cursorExpired，前端改从时间线/结果快照恢复后再订阅。若不得不改变历史游标，必须切换流 epoch 并强制客户端重新同步；禁止静默重排。

### 11.4 V1/V2 兼容

现有 event_type/content/created_at 保留，新增 schema_version、attempt_id、origin_kind、native_refs_json、payload_json/result_id 等可空字段；Session 读取投影同步承载所需字段。新用户读取按版本映射，旧行归一化为 V1。

V1 SSE 继续输出主员工文本与业务状态。V2 客户端通过显式事件格式参数请求包含专家信息的投影；单连接一次只输出一种格式。专家内容不混入 V1 主答案气泡。

V1 最终文本也应从完整结果取回或附受控结果读取入口，不能因为客户端旧协议就永久截断。后端和 Vue 的兼容变更须在开放新员工 profile 之前部署。

## 12. 完整结果与可靠交付

### 12.1 完整正文存储

拟新增 `platform_agent_result`：

| 字段 | 约束 / 用途 |
| --- | --- |
| result_id | UUID PK |
| run_id、attempt_id、delegation_id、invocation_id、executor_role_id | 根结果 delegation/invocation 为空；专家各轮结果关联其调用，实际角色独立记录 |
| result_key | 唯一业务键；根为 runId:final，专家各轮为 invocationId:final；不能用 delegationId:final 覆盖多轮结果 |
| media_type、body、body_sha256、byte_size | 首期 text/markdown，body 使用 LONGTEXT |
| employee_id、definition_version_id、native_refs_json | 结果来源与冻结版本；Team 结果附 teamExecutionId/generation/memberName/teamRoundId/native taskId/version |
| visibility、created_at | 平台赋值，与对应事件同事务保存 |

根最终结果、Run 终态、事件与结果引用一起提交。专家安全最终结果与专家事件一起提交，并校验当前 attempt/fence。事件 content 保存摘要，不能把截断摘要当完整交付。

Team 成员每轮结果用 invocationId:final；安全任务结果以 teamExecutionId:generation:taskId:version 关联；整体 Team 汇总以 teamExecutionId:generation:final 关联。结果附 Team/成员/轮次来源，只有随后业务根的 runId:final 构成正式交付。原生任务结果同步平台失败时可按 native task/version 补齐，不能为补结果重复执行任务。

结果记录增加 kind=ROOT_FINAL/DELEGATION_FINAL/TEAM_RESULT/RUN_MATERIAL、workItemRef/输入修订、输入/有效规格哈希、内容哈希及检查元数据。RUN_MATERIAL 使用独立的 runId:material:serverMaterialId 键，保留根/用户资料来源与可见性；不能抢占 runId:final，也不由中间方案保存触发 Run 完成。输入修订、结果与资料正文不可覆盖，新的方案产生新的引用；展示摘要与完整内容分别保存。

任意 resultId 的读取、作为输入共享与复核引用均核验属主、Session/Run 归属、角色范围和哈希。既有同 Session 结果可作为新 Run 的批准资料；它不成为新 Run 的已执行子实例或已完成任务。被撤销访问权的资料不能只凭旧 ID 再次读出。

建议首期正文上限 1 MiB；超限时明确失败或改受控文件交付，不静默截断。最少覆盖超过 4000 字符、中文、多段 Markdown 与 Unicode 字符的真实往返。

### 12.2 结算与出站意图同事务

扩展 RunExecutionStore.complete 的完成载荷，携带完整 RuntimeFinalResult、已消费工具结果 ID 和可空 ChannelReplyIntent；该端口成为根结果落定的唯一入口。

基础设施完成事务：

1. 锁定并校验 Run、当前 attempt、leaseToken/fenceToken、租约有效期及 RUNNING 状态。
2. 更新有效 attempt 和 Run；写完整结果、工具结果消费记录、RUN_COMPLETED 及会话投影。
3. 渠道 Run 在同一事务写入回复意图/outbox，引用刚写入的完整 resultId。
4. 返回 COMMITTED / STALE；STALE 时不写结果、不写事件、不入队，也不由旧 Worker 补写失败。

消息发送在提交后的 Delivery Worker 完成。不得把外部 send 放进上述事务；Run 成功和渠道已送达是两种状态。

回复路由从**该 Run 对应的入站消息**冻结 binding/provider/replyTarget，不以 Session 最新消息猜测旧 Run 的回复目标。Web 没有回复路由是正常情况。

### 12.3 Outbox、长度与失败

沿用既有 runId:reply 幂等意图与 Delivery Worker，扩展 resultId 引用/足够容量载荷。移除把最终正文静默截到 4000 字符的逻辑。

有文本长度限制的 provider 由适配层按已核对的能力分段，幂等键包含 intentId/partNo；或者发送受授权的结果入口。不能发送普通用户无法访问的裸内部路径。

明确失败可按 provider 规则重试；发送后结果不确定进入 UNCERTAIN 并核查，不盲目重发。进程在 SENDING 后崩溃也属于可能已发送，应按不确定结果回收，不能恢复为可重发。

本轮用模拟 provider 和真实数据库验收事务、长度与不确定分类；实际 IM 身份、长度规则和送达回执仍需对应 provider 联调。

## 13. 崩溃、取消与框架状态一致性

### 13.1 两个提交边界

~~~mermaid
sequenceDiagram
    participant W as Run Worker
    participant H as 原生 Harness / StateStore
    participant P as 平台 JDBC 事务
    participant D as Delivery Worker
    W->>H: streamEvents(冻结定义, 可信上下文)
    H->>H: 读取 / 保存 AgentState 与文件
    H-->>W: 根最终结果或挂起
    Note over H,P: 框架保存与平台结算之间存在故障窗口
    W->>P: 有效 lease/fence 下落定结果、事件、投递意图
    P-->>W: COMMITTED 或 STALE
    D->>P: 认领已提交意图
    D->>D: 调用渠道发送器
    D->>P: 保存已送达 / 失败 / 不确定
~~~

平台 complete 的事务不能自动覆盖此前原生 StateStore 的提交。工具结果 READY→DELIVERED 的平台标记也不能证明框架在崩溃前没有消费；“框架已保存、平台尚未标记”的窗口必须单独处理。

### 13.2 首期恢复决策

继续保留已存在的 RUNTIME_STATE_MISSING 保护。新 profile 建议增加 RECOVERY_REQUIRED 状态和 RUN_RECOVERY_REQUIRED 事件，避免不确定原生状态下自动重跑业务动作。

| 故障位置 | 首期处理 |
| --- | --- |
| 构建模板 / 物化前失败，尚未进入 Harness | 按明确失败或安全重试处理，不造空 AgentState |
| 外部结果恢复或续聊时缺少必须的状态 | RUNTIME_STATE_MISSING，停止执行 |
| 原生状态已保存，平台结算前进程失效，无法证明是否消费 | RECOVERY_REQUIRED；保留原状态与输入引用，禁止再次自动投递同一结果 |
| 租约丢失且旧执行是否已停止不明 | 中断本调用；新 profile 进入恢复核查，暂不自动启动竞争写入者 |
| complete 已提交，发送尚未开始 | outbox 正常消费，用户可从持久结果恢复 |
| 渠道可能发送但结果未知 | Delivery UNCERTAIN，保留已完成 Run，核查发送 |

RECOVERY_REQUIRED 占用 Session 执行槽，不能当 QUEUED 再认领；用户看见待核查和已有持久结果。管理员核查只允许明确终止或有证据的恢复，不接受手工改写原生 AgentState JSON。该状态须同步处理排队提升、取消、查询和前端状态。

现有 LEGACY_STABLE 的至少一次重试行为保留并说明风险；新 profile 在 A 阶段先采用上述保守恢复规则。改变自动恢复规则时再以故障验收证明安全。

### 13.3 框架状态写入与 fence

心跳返回 false 后立即停止本次原生流和子调用，禁止继续受理工具、写业务事件或入队。只在模型下一轮才发现租约丢失不足以覆盖长工具/专家调用，需持有调用级取消信号并验收原生取消传播。

原生 version/CAS 是状态并发原语，不等同于海卓租约所有权。实施阶段先核对公开 AgentStateStore 保存面和 JdbcAgentStateStore 的实际连接/事务行为，再决定是否能够以薄装饰在同一 MySQL 原子边界内校验租约并调用原生保存。

仅“先查租约、随后 delegate.save”仍有检查与写入竞态；只比较状态 version 也不能自动拒绝失效 Worker。必须用两个 Worker 的故障时序证明旧执行无法覆盖新执行。

如果无法在公开扩展点完成原子保护，首期保持新 profile 的恢复核查模式，要求旧进程已结束或旧调用已完整收尾后再恢复，暂缓自动跨 Worker 接续。不能把这一点写成已具备状态 fence 或精确一次。

### 13.4 必测故障时序

| 编号 | 场景 | 合格结果 |
| --- | --- | --- |
| R01 | 旧 attempt 完成返回后已被新 fence 取代 | STALE，零结果/事件/投递写入 |
| R02 | 结果落库后、outbox 插入前抛异常 | 同事务全部回滚；重试不会丢意图 |
| R03 | 完成事务提交后 Worker 失效 | 持久结果存在且恰有一份意图 |
| R04 | 原生消费 ToolResult 后、平台 DELIVERED 前失效 | 不重复自动恢复消费；明确核查或已验证恢复策略 |
| R05 | 专家结果先于父结果 | 只更新专家，Run 继续 |
| R06 | 子 RequestStop / 子外部工具挂起 | 不取消/挂起错误的父会话；首期策略拒绝违规工具 |
| R07 | force-sync 专家超时 / 用户取消 | 原生子订阅收尾，无后台提升，预算释放一次 |
| R08 | 心跳失败时模型仍在响应 | 业务写入与投递被拒；框架写入保护或阻塞恢复规则有证据 |
| R09 | 保存后重启到另一进程、另一物化目录 | 原状态与允许文件恢复；缺失状态不静默新建 |
| R10 | 前端断线、慢消费、旧 attempt 迟到 | 持久结果校准，无主子消息混合 |
| R11 | 审批/工具结果重复回调与事件投影故障 | 原工具幂等、Run/Session 投影同事务，没有重复消费承诺越界 |

### 13.5 自治 Team 的持久化与恢复设计

#### 已确认的固定版本限制

LocalTeamClient 用实例内 AtomicLong 分配消息 ID，再以该 ID 写 BaseStore；新 client 对同一 Team namespace 写入时序号从头开始，可能覆盖旧消息。它的广播与任务通知内部调用自己的 sendMessage，因此仅包装对外 sendMessage 不能修复所有路径。这是 2.0.3 的静态源码事实，探针要复现并检验规避方案，不能把它归为“原生自动恢复应该可以”。[N10]

原生 TeamsMiddleware 的成员映射与 TeamWakeups hook 属于当前进程；持久板记录不包含可恢复的 Java 活实例。WakeupDispatcher 从队列 drain 后订阅成员执行，未建立平台所需的消费确认事务；进程在两步之间退出，不能保证该条通知再次激活。[N09]、[N12]、[N13]

因此首期采用：**一个活 Team 由唯一 Worker 持有，同一代共用一个 LocalTeamClient；故障后旧 Team 保留，只读核查；需要重新建立执行时使用全新 teamName/namespace 和成员会话。** 不让多个 JVM 用不同 LocalTeamClient 写同一个活 Team。先查父租约再写原生板不等于原子 fence；沿用 §13.3，在旧执行是否停止未确定时禁止接续。

#### 首期可执行的处置

| 故障 / 恢复需求 | 状态与处理 | 恢复的内容与限制 |
| --- | --- | --- |
| 浏览器断线或服务页面重建 | Run 继续；snapshot + sessionCursor 补读 | 恢复用户可见的角色、任务/轮次和安全结果，不新建成员执行 |
| 活 owner 内通知缺失或运行中通知被跳过 | 在有效父 Run 内检查原生 inbox、任务板和已结束轮次，合并补发原生 wakeup；受总轮次和截止时间约束 | 唤醒是提示；成员按原生 CAS 读取/认领工作；不新增平台任务队列 |
| 原生任务已终态，平台事件写入失败 | 按 taskId/version 从板与完整结果幂等补投影 | 板转换与平台事务不同；补读不能重跑已经成功的任务 |
| 原生 Team 已标完成，业务根/平台未结算 | RECOVERY_REQUIRED，保留原生板与已提交结果 | 标记本身不能证明已交付或父工具已消费；按 A3/A4 核查，不直接再发送答案 |
| owner JVM/节点故障或租约失效 | RECOVERY_REQUIRED，占用 Session 槽；停止新认领、事件结算与唤醒 | 展示能恢复；活实例与待执行轮次不能从板自动还原 |
| 旧执行已完整结束，确认只需终止 | 管理员按 §14 的 terminate 入口审计关闭 | 原始 Team/成员 AgentState/消息/结果留存；不清库以“恢复” |
| 用户重新提交只读任务 | 旧 Run 先安全终止；父角色状态经过 A4 确认可继续时创建新 Run、新 Team 身份 | 明确任务与安全结果引用可传递；不复用旧 Team client 写入，不隐式复制内部记忆 |
| 父交互 AgentState 的工具消费仍不确定或缺失 | 保持保护性错误；结束核查后用新 Session 提交任务与明确资料 | 不能为了继续同 Session 手工改原生状态，或假装 private context 已完整恢复 |

活 owner 的补唤醒只修复消息到执行之间的遗漏。若读取板/inbox失败，不能推断已经空闲/全部完成；记录故障并收尾或转核查，不在无限重试中占用业务槽。

#### 后续有证据的人工续接契约

同一个旧 Run 的自动重启/人工续跑**首期不开放**。若 A4 和 Team 故障探针证明父工具消费边界、AgentState 与旧执行完整收尾，可按以下契约设计新的审计续接入口，再提交用户审阅：

1. 锁定 RECOVERY_REQUIRED 的父 Run，核对 expectedAttempt/fence、旧 owner 停止证据和恢复输入哈希；不能靠租约过期单独确认旧进程不会再写。
2. 读取旧原生板、已完成完整结果、待核查任务和允许的近期消息；成功完成的任务作为资料，不重新执行。失败/中断任务只有明确批准后才在新代创建。
3. 创建新的 Team generation、全局唯一 teamName/namespace、一个新 client 及新成员会话，通过原生 createTeam/createTask 建立新代板；不写旧消息命名空间，也不手工复制/修改任务记录。
4. 构造原生 TeamContext.RecoveryContext：previousSessionId、restartCount、completedTasks、interruptedTask 和受控 recentMessages；完整任务映射另以批准资料引用传入，因为原生 interruptedTask 只表达单项，不能据此丢弃多个中断任务。
5. 新旧任务/结果用恢复来源关联；继续使用原 Run 剩余额度/有效截止时间，旧代只读。新轮次以新 attempt/team generation 关联，迟到旧代事件只作历史核查。
6. 恢复根工具的输入/结果必须使用 A4 已证明的原生状态消费流程；不能直接再执行一次 run_readonly_team 来掩盖未确认的前次调用。无法证明时拒绝同 Run 续接，采用上表安全终止/新请求流程。

这种续接恢复的是已确认资料与尚未完成工作，不承诺复制成员的全部私有推理上下文。若业务要求原内部会话完全连续、自动跨节点接管或长时间后台存活，需要进一步证明原生持久消息序号/投递确认、成员重建、共享所有权与状态写 fence；优先升级或补齐原生扩展点，不增加与原生 Team 并行的第二套控制面。

### 13.6 父子数据、依赖与结果的故障处置

与 §13.2/§13.5 统一采用保守恢复边界，不根据工作项投影自动恢复执行：

| 故障 / 竞争时序 | 数据与执行处置 |
| --- | --- |
| 契约格式非法、越权引用、依赖尚未就绪 | 在受理边界拒绝；建议 DELEGATION_CONTRACT_INVALID/RESULT_REFERENCE_FORBIDDEN/DEPENDENCY_NOT_READY；不创建子调用或平台等待任务 |
| 引用内容/复核对象版本变化 | RESULT_VERSION_MISMATCH；重新明确输入修订后才接受新调用；不自动解析 latest |
| 子返回非法格式或缺必需资料 | DELEGATION_RESULT_INVALID/明确检查未通过；保存允许的诊断与已有结果，根可在预算内要求修订，不把正常结束等同于交付通过 |
| 输入快照/预算事务提交后、进入框架前进程失效 | 受理记录不证明框架未开始；只有实际调用日志/所有权证据证明未启动时才安全处理，无法证明进入 RECOVERY_REQUIRED |
| 原生已完成，平台结果或投影写入失败 | 从有证据的原生完整结果/任务与版本补平台事实；不能只凭 AgentEnd、摘要或 source 恢复成功；正文无法确认时核查，不重新执行已完成任务 |
| 部分并行调用失败，其他仍运行 | 停止受理受其依赖的下游；按 required/部分交付策略决定收尾，剩余调用取消或等待明确结束；预算不提前释放 |
| 结果保存后、根是否消费不明 | 按 A4 验证原生工具消费/状态提交边界；保存引用不代表可以再次送入根，不自动重放或伪造消费标记 |
| 父取消/超时/租约失效后有迟到结果 | 拒绝新受理，取消子；失效 Scope 不改变当前投影/结算，不产生出站意图；无法确认旧调用停止则占槽核查 |
| Run 已结算后浏览器重连 | snapshot + sessionCursor + 完整结果/检查引用重建展示；不重建临时 agent_key 的活执行 |
| 用户新请求引用旧结果 | 新 Run 的授权资料输入；新预算、调用与必要实例，旧原生 Task/实例不直接复活 |

上述业务拒绝码是设计命名。对新 profile 的 acting 拒绝沿用 §9.1 的整批预检规则；原生失败回馈的可用扩展面经 A0/C15 验证后才决定是否支持原循环内修正，当前不能承诺“拒绝一定会让模型自动重试”。

结果/检查事实可从持久存储恢复，活跃 general-purpose 实例和后续 agent_send 是否可重建必须另有原生契约证据。首期不把 parentState 中的一条 spawn 记录视为可安全恢复同一个模型调用。Team 仍按 §13.5 核查或在新请求中新建团队，不绕过消息序号与旧 owner 停止限制。

CreateRunRequest 增加可空 targetRoleId、referencedResultIds；缺省仍执行协调者/原单员工。mode=direct 表示指定角色直接回答，mode=collaborative 表示指定角色作为根组织受控协作，mode=autonomous 仅允许已验收的自治 profile/获准根角色；mode 不越过团队角色策略。服务端解析固定执行者与槽位，响应补充 executorRoleId/executorEmployeeId/executorDefinitionVersionId，不让客户端选择任意成员版本或 nativeSessionId。

自治模式不新增浏览器可调用的成员 wakeup/sendMessage/claimTask 入口；这些是父 Run 内的原生内部动作。团队查询读模式不参与调度。自动续接按钮保持关闭，恢复处置按 §13.5 和管理员 terminate 契约执行。

所有队列/渠道受理和提升均需保存目标及引用。Web 选择后的请求只影响它自己；渠道初期缺省目标为协调者，未来选专家需受授权的明确渠道动作，不能把消息文本中的任意“@名字”直接当可信角色。

### 14.2 请求兼容与错误契约

现有 DraftRequest 的 capabilities 为 @NotEmpty。V2 分组校验按 profile 允许零业务工具，assets/members 的约束仍由领域校验执行；旧请求缺少 configuration 时归一化为 LEGACY_STABLE。不要让空数组兼容处理隐式启用技能或专家。

validate 返回 valid、draftRevision、previewHash 与 issues[]。每个问题含 code、severity、fieldPath、message、可空 relatedId；fieldPath 精确到对应成员、文件或参数。

| code 示例 | 处理 |
| --- | --- |
| DRAFT_REVISION_CONFLICT | 保存/发布返回 409，要求用户重新读取与比较草稿 |
| ASSET_REVISION_UNAPPROVED、ASSET_HASH_MISMATCH | 拒绝发布或执行；标出资产和文件 |
| ASSET_PATH_INVALID、ASSET_PATH_COLLISION | 拒绝相对路径穿越、保留入口冲突及大小写冲突 |
| MEMBER_VERSION_INVALID、MEMBER_CYCLE | 拒绝未知版本、跨租户、自引用或递归依赖 |
| PROFILE_POLICY_UNSUPPORTED、DELEGATION_LIMIT_INVALID | 拒绝超出首期范围的记忆、后台、暴露或预算 |
| TEAM_ACTION_FORBIDDEN、TEAM_TARGET_INVALID、TEAM_LIMIT_REACHED | 拒绝未批准动作、跨 Team/任务归属与预算越界；不得启动对应成员轮次 |
| RUNTIME_DEPENDENCY_UNAVAILABLE | 已启用新 profile 但缺少原生 JDBC 文件面等必要组件时拒绝执行 |
| DELEGATION_LIMIT_REACHED、DELEGATION_ROLE_BUSY | 首期预检失败结束当前根调用；不启动本批/越限专家，不触发父 Run 成功 |
| RUNTIME_STATE_MISSING、RUN_RECOVERY_REQUIRED | 区分缺失状态与状态不确定；前端显示对应处置 |
| RESULT_SIZE_EXCEEDED | 按完整结果大小拒绝或引导文件交付，不能返回被截断的成功正文 |

沿用现有统一错误响应；实施前核对其 status/code 字段形状，再扩展以上业务码。请求正文大小在 API 和领域层一致限制；资产 hash/审核状态均由服务端计算，客户端不能自行声明“已审核”。

### 14.3 快照、增量与游标

snapshot 至少包含 session 固定版本、可选角色及安全槽位摘要、活动/近期 Run 的实际目标、根消息、计划、专家各轮关键状态、自治 Team/任务的安全展示和确定性标记、结果引用、snapshotCursor、cursorFloor。它是会话投影的读模型，不从原生内部记忆反推前端历史。

数据库同一一致性读边界取得内容和 snapshotCursor；不采用“先读内容、随后另查最大游标”的两次独立读取，否则两次读取间提交的事件可能被跳过。前端先应用快照，再从 snapshotCursor 接入持久事件和实时增量。

分页响应保留 cursorExpired/cursorFloor，并补充 nextCursor；nextCursor 对应扫描位置，不能因过滤 INTERNAL 事件而让客户端停在同一位置反复读。普通用户补读由服务器过滤，不只依赖页面隐藏。

format=v2 只调整载荷；它不改变游标编号、持久事件顺序或 Session 生命周期。Run 终态不关闭会话级流。瞬时增量可以在网络故障时丢失，完整持久结果用于校准；不要保证逐 token 重放。

沿用 DefinitionPanel.vue 与现有管理 API，增加“运行方式、技能、知识、协作成员、发布预览”区域：

4. 校验问题定位到字段；发布前展示相对上版的资产/成员/策略变化与冻结摘要。发布提交使用用户已经审阅的 draftRevision。

文件编辑只支持首期允许的 UTF-8 Markdown/文本与规范路径，预览内容做 HTML 清理；不提供执行脚本或打开主机任意文件的操作。普通业务界面不展示 framework flag、原生存储键或内部 AgentState。

### 15.2 用户 Session 页面

在 SessionView、useSessionStream 与 runEventPresenter 中引入 §10 的来源分组：

| 呈现项 | 数据来源 / 行为 |
| --- | --- |
| 主答案 | 根消息独立归并；完成后以 resultId 对应完整正文校准 |
| 专家选择 | 同一 Session 中列出固定团队角色；选项只作用于下一条请求，活动/排队 Run 各自显示已冻结的目标 |
| 回答身份 | 用户直接选专家时，根答案显示该专家；不能都标记成协调者 |
| 计划 | 主员工原生 Plan 事件的安全快照；按 Run/attempt/source 区分，不合并专家计划 |
| 专家卡片 | delegation 分组、invocation 多轮状态、成员名称/版本、耗时；允许时展开每轮安全结果 |
| 自治团队 | Team/成员/任务关键状态与已批准结果；区分一轮结束、任务完成、团队收尾、正式答案；原始互发邮箱和内部推理不展示 |
| 专家失败或超时 | 仅更新对应卡片；父员工按输入完整性决定最终答复 |
| 等待审批/工具 | 沿用现有父 Run 控件；子专家首期不出现审批面板 |
| 恢复核查 | 显示活动槽被占用及管理员核查状态；属主可请求取消，不能普通重试 |
| 渠道交付 | 单独显示待发送/已发送/失败/不确定；不把未送达显示成 Run 失败 |

主答案与专家结果由持久关键事件/结果引用恢复。思考链、原始工具参数和未授权内部文本不进普通页面；实时专家进度只展示允许的状态摘要，不逐段广播内部推理。

切换选择不清空页面历史，不把另一专家的旧答案重新命名。用户可明确把先前答案加入下一请求的引用；页面显示引用来源。需要中断活动任务时使用现有取消操作，与“选择下一条由谁回答”分开。

有委派权限的角色提供“直接问此专家 / 请组织协作”的请求方式，映射 direct/collaborative；自治 profile 另提供“专家自主协作”，映射 autonomous。权限来自固定包，页面不能打开未批准的模式。活动 Run 的引导和审批始终显示实际执行角色，不因下一请求选择改变目标。

会话流默认连接 format=v2，消息索引使用 runId/attemptId/delegationId/replyId/blockId，不复用现有唯一 runId-assistant 键承载全部来源。V1 旧客户端只接收兼容的主消息。

### 15.3 重连与错误

首次进入或游标失效：应用 snapshot → 以 snapshotCursor 连接会话流。正常断线：保留最后持久 cursor，退避重连；实时 streamOffset 只用于当前 attempt 的去重/诊断。

持久完成先到而瞬时 delta 后到时，忽略该结果的迟到增量。发现 attempt 变更时，不把旧 attempt 未完成正文合并到新正文；保留已有安全历史与状态。订阅结束/页面离开只关闭连接，不调用 Run cancel。

用超过 4000 字符的真实最终答案验收刷新与历史；不能仅验收接口返回而页面仍取摘要。

| M5 协作与恢复 | Session 身份模式/角色槽；RunSpec/Run 实际执行者与引用；预算、reservation、delegation/invocation；workItemRef/输入修订、契约与有效规格快照；RECOVERY_REQUIRED | 团队版本固定；只有根 Run 调度；输入修订/工具受理幂等；直接槽/任务子槽分开；无工作项 Worker 队列 |

字段长度、JSON/LONGTEXT 类型、索引长度、字符集、FK 删除策略和 check 约束以真实 MySQL 版本验证。若某约束在目标 MySQL 不支持，必须由领域层执行并在报告注明；H2 行为不足以证明兼容。

### 16.2 数据回填与保持游标

1. 备份并核对现有 Run/Session 数量、事件唯一键和最大的会话游标。
2. 从已存在 Session 投影回填 RunEvent.session_cursor，给 Session.next_event_cursor 设置不小于当前最大值的下一可分配位置。
3. 找出只存在 Run 表的历史工具/审批事件，按 §11 分配新的高位会话游标；保留原发生时间和历史补投影标识。先小批核查，确认不会曝光 INTERNAL 数据。
4. 旧运行包不重编译，旧 definitionVersionId/legacy_runtime/AgentState 物理键不变。不得把多版本旧状态合并到一个新 Session。
5. 为旧渠道 Run 路由只有可靠入站关联时才回填；缺少关联的历史 Run 保持无自动投递，不猜测接收人。
6. 启动新写入前验证游标分配器不会与存量重复；在线批次采用明确升级窗口或已验证并发方案，不让新旧分配器并行写入。

旧迁移 V13/V14/V19 不修改。新增 KV 数据不替换 AgentState；公开结果、会话投影和框架记忆各自保留既有归属。

### 16.3 上线顺序

1. 用户审阅本设计后，执行 A0 原生探针并校准有歧义的 API/字段，形成真实验证记录。
2. 新增向后兼容的数据库字段/表，部署可读 V1/V2 但仍关闭新 profile 的服务与前端。
3. 完成事件统一写入、完整结果/完成事务、恢复状态与原生 KV 门槛；校验现有 TOOL/MCP、审批、Web/渠道排队回归。
4. B 阶段仅给测试员工发布 SINGLE_SKILLED V2，新建 Session 验证技能、知识和文件恢复。
5. C 阶段发布 TEAM_READONLY V2，执行只读、预算、来源及取消验收，再允许普通用户新建此类会话。
   同阶段完成专家稳定运行槽、同 Session 切换、原生 follow-up、共同资料引用与多轮展示验收。已有单员工 Session 不在线重写成团队 Session；用户通过新团队 Session 获得完整能力。
   C9–C13 独立验证并发布 TEAM_AUTONOMOUS_READONLY，依次放行预构建团队、消息唤醒、完成/取消和故障处置；未通过不影响已经合格的受控协作，但不得标记自治模式已交付。
6. 保留 LEGACY_STABLE 和旧客户端读面；记录 MySQL/模型/provider/浏览器各层实际证据，不把模拟 provider 结果当真实渠道验证。

原生 KV schema、通用事件/完成事务和新的恢复规则是多节点共用变化，启用前确保所有活跃 Worker 支持。运行新 profile 时不能把任务路由给旧二进制；首期采用整体后端升级和关停旧 Worker，不新增复杂的版本路由调度器。

### 16.4 回退与清理

部署开关关闭新 profile 的新建受理，已有新 profile Session 保留查询与明确停止能力。回退到**已具备 V2 读取/安全拒绝能力的兼容版本**；旧二进制不能处理新的 RECOVERY_REQUIRED、资产或专家事件，不直接把它上线认领新 Run。

不通过删除资产、清空 AgentState 或删投影回退。只读发布修订、完整结果、outbox 与原生 KV 保留到引用关系和业务留存策略允许清理；优先修复前向兼容问题。已提交交付意图照其状态核查，不因回退重新产生一次发送。

管理员发现发布资产需紧急停用时，以服务端可用性检查拒绝新委派/Run；固定版本记录仍保留供审计。暂停受理和执行终止分别记录，不能把停用某成员自动映射为换用新版。

| DelegationResultPersistenceFailureProbe | 输入提交后未明启动、子结果持久化失败、根消费不明、晚到失效结果；平台回滚/补事实与 RECOVERY_REQUIRED，不能因补读重跑模型 |
| MultiAgentDeliveryAcceptanceTest | 完整 §8.8.6 案例；P1/P2 与复核引用；必需失败/部分交付、撤权、A→B→A、刷新与完整结果取回 |

框架接入探针优先采用可控模型/工具，以确定运行协议；质量验收再调用实际已授权模型。执行 MySQL 场景需真实数据库及明确迁移版本，不能用已有 target/surefire-reports 当作本轮跑过的结果。

自治 Team 专项故障与契约场景：

| 编号 | 探针 / 故障注入 | 合格结果 |
| --- | --- | --- |
| T01 | 共用一个 client 与两个新 client 写同一板；保存消息后重建 client | 明确复现实例序号冲突；共用 client + 唯一 Team 身份无覆盖；故障后新代不写旧消息 namespace |
| T02 | 相同 teamName/memberName，不同 namespace/用户并发；Team 退出后回调 | 复现注册键只含 Team 名的限制；平台全局名称与可信绑定修复串话；关闭后不激活旧目标 |
| T03 | 原生 Team 通知携带空 userId，唤醒已存在成员状态 | target 从 server binding 重建真实 user/版本/Run；继续正确状态，陌生 sid 与伪造载荷拒绝 |
| T04 | 最后一次 inbox drain 后、gate 释放前到消息；同时两条 wakeup | 原生 gate 保持单成员互斥，收尾合并补醒；不丢待处理 inbox、不无限空调用；等待和 acquire 可取消 |
| T05 | availableActions 空列表、动作别名、伪造 claim owner、完成别人的任务 | 观察原生宽放行行为；实际非空名单与 acting/作用域校验拒绝越权，原生任务 owner/CAS 并发证据明确 |
| T06 | 调用动态成员部署/计划审批；构造成员但不显式接线 | 记录 LocalTeamClient 的 unsupported 分支；不开放动作；仅 createTeam 不被误认为已启动 worker |
| T07 | lead 一轮结果先到、completeTeam 时有 pending、必需任务失败、listTasks 抛错 | 不产生根完成；冻结受理/等待活动调用/成功板读取后才结算；读取异常不是“全部完成” |
| T08 | worker 输出答案但没有 completeTask；正常结束与 error/cancel | 观察原生 settleOwnedTasks 的真实路径；任务无明确成功不能自动成功，异常/取消保留可核查状态 |
| T09 | 任务状态提交后通知失败；原生 completed 后平台投影失败 | task/version 核对补投影/lead 提示；不重复执行已完成任务；Run/Session 平台事件仍同提交 |
| T10 | queue drain 后启动前退出 JVM；原生 Team 完成后父工具消费/结算前退出 | 重启能查原生板和平台结果，但不自动重建同 Team writer；RECOVERY_REQUIRED 占槽；按 A4 证明或拒绝续接 |
| T11 | 并行 worker 执行中用户取消、总时限到达或父心跳失效 | dispatcher 停止、订阅/gate/注册收尾可证；迟到业务写/意图为零；停止未证实时不启动新 owner |
| T12 | 同 Session A→B→A 与自治任务交替，两用户/版本并发；长结果断线补读 | 稳定直接角色槽不混入自治内部记忆；成员/代/轮次来源正确；完整结果恢复、INTERNAL 严格过滤 |

本轮 GitNexus 仅提供有限的调用关系辅助，覆盖限制见 §20；上述业务风险不能由它的 LOW/MEDIUM 类级结论自动降级。
