## 对象与原生映射

Session 是产品会话，Run 是根执行；workItem 是业务资料/验收对象，delegation 是子实例关联，invocation 是某一轮调用。原生 taskId/agent_key/toolUseId 都分别保留，不能互相顶替。任务执行/认领复用原生仓储和 Team 任务板，平台不建工作项派发 Worker。

## 输入与有效规格

- 根建立 workItemRef 和不可变输入修订：目标、交付契约、required、授权资料引用/哈希、依赖、检查策略、固定/来源角色、剩余预算与截止时间。
- effectiveChildSpec 冻结父允许能力与子配置的交集；子不得扩大权限、换模型/版本或修改父截止时间。
- 把结构化契约编码为原生 spawn/send 的受控任务内容，关联到服务端 Scope；文本不是可信身份或权限声明。
- 复核对象显式指定 resultId/contentHash/contractVersion；不读取 latest。依赖未成功/错版在受理边界拒绝，不创建平台等待队列。
- 同 workItem/输入修订的幂等及预算占位同事务；记录实际原生接受/启动证据，不把输入提交等同未启动。

### 受理重入与取消校验（2026-10-08 校准）

- 幂等键为 `runId + attemptId + native toolUseId`；完整请求（操作、身份、版本摘要、原生定位参数和输入）摘要一致时复用原 invocation 与原输入修订，不新增预算、事件或 Session 游标。同键不同摘要拒绝受理。
- V32 新增 `request_sha256` 和原生入参快照 `accepted_payload`。重入直接返回已冻结入参，不随代码升级重新物化。旧回执缺少可重建的完整请求，字段保持空；此类重入须核查，不以输入正文摘要推断身份/操作一致，也不重新启动子 Agent。
- 原生启动仍使用 AgentScope 的 reservation/调用链；原子 `ACCEPTED → ACTIVE` 防止同回执启动两次。重入回执未取得启动权时，其清理不能改变原调用状态。
- 启动与结果提交均重新检查父 Run 为 `RUNNING`、profile、当前 attempt/fence 和有效租约。父 Run 已取消或进入恢复核查时，迟到结果不能写事实或投影。
- MySQL 默认 `REPEATABLE READ` 下，初始身份定位查询可能在等待 Session 锁前建立旧快照。预算、回执、角色占用及根必需项检查使用锁定当前读取；事件幂等和序号也读取当前行，不能用旧快照 `COUNT/MAX` 计算下一次写入。
- 定向事务回归 23 项通过。新增真实 MySQL 场景覆盖重入/修订、预算并发、并发事件序号/游标、并发同键回执、取消迟到、投影失败回滚和结果写入失败后的恢复占槽；实际执行结果见[阶段验收报告](../../07-测试报告/数字员工协作实施阶段验收报告.md)，不能把这些仓储场景等同于完整原生 P1/P2 编排。

## 输出与检查

### 同角色实例与完整消息边界（实施切片，2026-10-08）

原生契约探针确认：两个 `general-purpose` label 拥有不同的原生 Session；`agent_send` 保留对应 label 的 Session。它们的父流 source 相同，且父流不转发子 `AgentResultEvent`。因此不能以角色/source 排队关联，也不能把增量拼接当作最终正文。

本切片使用已冻结的 `accepted_payload` 精确匹配子调用，取得唯一 invocation、workItem 和输入修订。AgentScope 继续负责实例、上下文和调度。子 `onAgent` 中间件在实际 `AgentResultEvent` 边界调用平台结果端口，提交完整 Msg、实际子 Session 和原生引用；平台按 invocation 校验当前 Run/attempt/fence、受理输入和执行身份，并在同一事务保存结果、工作项状态、Run 事件和 Session 投影。结果提交成功后原生工具才能返回，便于根下一轮读取结果。

同角色的通用/动态实例允许多个工作项；固定已发布专家仍保留每角色一个实例的产品规则。跟进调用必须指向本 Run 的服务端工作项 label；未经持久验证的 `agent_key` 不能通过解析角色名定位任意实例。提交失败记录在 Run Scope，原生工具即使把异常包装成错误回复，根事件流也必须向平台抛出，进入 `RECOVERY_REQUIRED`。旧父流结果收集器不再从进度生成持久结果。

验收覆盖同角色两个实例与准确结果绑定、跟进上下文、未受理输入拒绝、固定角色重复拒绝、完整最终消息与增量不同、事务故障后的恢复占槽。该切片不替代下述 P1/P2 资料/复核协议和 Team 故障矩阵。

- 子实际最终消息完整保存为 TEXT/JSON 等批准契约，带产物/资料引用、哈希、限制与检查结果；原生正常结束不等于资料合格。
- 原生 spawn 回复可能含前缀/封装；以实际最终消息与批准映射读取，不将任意回复字符串冒充结构化正文。
- 平台格式/引用检查与原生任务 completed/failed 分开记录。根决定验收/修订/部分交付，ROOT_FINAL 独立保存。
- 必需失败阻止其依赖下游；允许部分交付也需明确列出缺失与已接受范围，不自动变全部成功。
- 结果已保存但父消费不明进入 SPEC-04 核查；平台补投影不重新执行已完成子任务。

## 验收

覆盖详细设计 §8.8.6 完整案例：P1/P2 并行 → 合成 → 复核精确版本 → 修订 → 根交付。检查 TEXT/JSON、缺必需项、非法/越权引用、哈希错版、重复修订、依赖未就绪及部分失败。

故障注入输入提交后未明启动、原生完成后结果写失败、根消费不明、取消后晚到。正确结果为幂等补事实或 RECOVERY_REQUIRED，不能靠重跑模型掩盖不确定状态。
