## 1. 核心结论和阅读边界

工具配置要统一，但执行权不能混为一谈：**本地 Tool 与 MCP 子工具共用能力目录、修订、员工绑定和 Run 工具视图；本地业务资源由平台判权，可信 MCP 的业务资源由 MCP Server 基于终端用户身份在每次调用时最终判权。** AgentScope 的工具许可只控制框架层允许、询问或拒绝，不能代替这两种业务授权。

把整个过程看作五个不同问题：平台登记了什么连接和工具；哪个工具修订经过批准；员工发布版本装配了哪些修订；当前用户在本次 Run 中可向模型展示哪些工具；模型提出的这次具体调用是否可以落地。前一个问题的肯定答案不会自动回答后一个问题。

本文优先规定可信 MCP 接入。未经验证能按终端用户隔离 `tools/list`、逐次判权 `tools/call` 的服务，不能仅凭“支持 MCP 协议”按此信任边界上线；如需使用，必须另行设计受控适配与平台判权，不默认降级成服务账号代用户调用。

## 2. 当前代码和框架证据

以下是截至本文日期的代码现状，不是 MCP 已交付声明：

| 已有事实 | 证据与限制 |
| --- | --- |
| 根 `pom.xml` 锁定 AgentScope Java `2.0.3`；能力目录已保存修订、工具名、Schema、实现键、业务动作和确认要求 | `CapabilityCatalogEntry`、Flyway V2/V9；当前目录与管理页面主要服务本地能力 |
| 数字员工草稿、发布能力包和 Run 工具视图已有主干 | `AgentDefinitionManagementService` 与 `DefaultHarnessDefinitionBundleCompiler` 当前只接受 `TOOL`；`HarnessRunSpecFactory` 用平台用户能力授权筛选工具，不是 MCP 逐用户列表 |
| 外部工具在 Harness 中以仅 Schema 形式装配，实际调用交回平台 | `ExternalToolSchemaAssembler` 不携带 MCP 地址或凭证；`DefaultToolExecutionGatewayService` 目前按本地工具逻辑执行平台资源策略，执行异常会归为通用错误，尚不满足本文的 MCP 错误分类 |
| `CapabilityBinding.CapabilityType.MCP` 是预留类型 | 尚无 MCP 连接管理、逐用户发现、子工具批准和真实 MCP 调用闭环；不能把枚举值当作已接通 |

AgentScope 2.0.3 已有 MCP 客户端、Toolkit 注册和子工具筛选，也提供每次 HTTP 请求的 `httpRequestCustomizer`。但其直接注册会在初始化/装配阶段发现工具；原生 `McpTool` 的上下文传递与错误转换也不能直接证明共享客户端的逐用户身份隔离及写操作结果分类。首版应优先复用原生 MCP 协议客户端，保留平台控制的外部工具执行边界；只有经过双用户并发、逐用户发现和失败分类验证，才考虑把 MCP 客户端直接注册进共享 Harness 模板。不得重写一套 MCP 协议栈。

## 3. 三层职责与两种执行权

| 层 | 必须负责 | 不负责 |
| --- | --- | --- |
| AgentScope 工具许可层 | Agent 循环、Tool Schema/分发、框架 `ALLOW/ASK/DENY/BYPASS`、MCP 协议能力与执行事件 | 平台 Role、业务资源 ACL、终端用户凭证归属；`BYPASS` 不扩大业务权限 |
| 平台用户与工具治理层 | 可信用户身份、账号/员工可用性、MCP 连接和工具目录、已批准修订、Run 可见集合、必要确认、执行路由、审计及结果核查 | 对可信 MCP 复制一套 Role/资源 ACL，或替 MCP 对目标资源作最终授权 |
| 数字员工功能装配层 | 草稿选择具体工具修订、发布不可变版本、提供面向业务的能力组合 | 给用户授权；绑定工具不意味着任何用户都能调用它 |

两类工具共用治理外壳，但在执行前分支：

- **本地 Tool**：平台的用户能力、`Resource + Action`、资源归属与确认规则继续参与实际判权；白名单实现键指向受控执行器。
- **可信 MCP 子工具**：平台只检查用户/员工/Run、已批准子工具、启停、必要确认和调用一致性；同一终端用户的 `tools/list` 控制潜在可见性，MCP Server 在每次 `tools/call` 按真实目标资源最终判权。平台可保存业务动作标签用于说明和审计，但不把标签发展为平行的 MCP 资源授权系统。默认不为每个 MCP 工具再复制一份平台用户能力 Grant；如未来需要灰度开关，应明确它只是平台发布门禁，不是 MCP 业务授权。

用户确认是对一次已经受控的具体调用增加操作门槛，不是授权提升。子 Agent 的工具集合必须是父 Run 已冻结集合的子集。模型参数、渠道消息和自报用户 ID 均不能成为认证事实。

## 4. 统一配置对象与字段归属

关系为：**MCP 连接 → 发现候选 → 已批准工具修订 → 员工发布绑定 → 本次 Run 工具视图**。只有“已批准工具修订”是员工可选择的对象；Server 连接和发现候选都不能整包绑定员工。

| 对象 | 最小职责与边界 |
| --- | --- |
| MCP 连接 | 平台/租户范围的稳定 Server 身份、连接目标、传输方式、信任与启停、配置修订及观测到的健康状态。连接配置不存用户 Token；“连接正常”不表示任何用户有业务权限。 |
| 发现候选 | 某次受控发现所见的远端工具名、标题/说明、输入/输出 Schema、注解、发现时间和差异。它是观察结果，不是全体用户工具全集，也不自动可执行；管理侧发现使用何种身份留待对接。 |
| 统一工具修订 | 平台稳定工具 ID、不可变修订 ID、来源 `LOCAL/MCP`、唯一模型工具名、经审核的模型说明与 Schema、读写影响、确认规则及启停状态。本地来源还要关联受控实现和平台资源判权映射；MCP 来源要关联连接修订、远端工具名和经审核的接口快照。 |
| 员工绑定/发布 | 草稿选择具体工具修订；发布包固定模型可见契约与来源引用。Server 新增工具或目录出现新修订，不会改变已发布员工。 |
| Run 工具视图 | 按当前用户与已发布版本生成并持久化模型可见名称集合；执行期间只可收窄，不可新增名称或改用较新修订。 |

远端 `name`、`inputSchema` 和存在时的 `outputSchema` 来自 MCP，平台保存经审核的快照，不在界面直接手改协议参数。需要参数裁剪、固定参数或改名调用时，应形成明确的受控适配修订，而不是让展示 Schema 与实际调用不一致。管理员可维护仅供后台展示的名称；若要调整模型可见说明，须审核并生成新工具修订。工具名应带稳定命名空间，避免不同 Server 或本地工具碰撞；具体编码留给详细设计。

平台明确判定工具的读写影响、确认与写结果核查要求。MCP 的 `readOnlyHint` 等注解仅是发现元信息，不自动成为业务许可或产品确认策略。影响无法判断的通用命令、任意 HTTP、文件或网络工具，不能以单个宽泛名称进入普通用户能力目录。MCP 规范定义工具名称、Schema、注解和分页发现，但不规定平台的逐用户授权规则；这些必须成为可信 Server 的接入契约。[MCP Tool 规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)。

## 5. 管理、发布与变更流程

1. 管理员登记连接并完成可信 Server 准入验证：同一终端用户身份可用于列表与调用；`tools/list` 按用户过滤；`tools/call` 每次按用户和资源判权；跨用户、跨租户与伪造身份测试通过。连接测试与逐用户授权测试分开记录。
2. 受控发现产生候选及差异。`listChanged` 可触发重新发现，但不能自动批准；它是协议中的条件性通知，不是可靠的发布事实。发现分页必须完整处理，不能把一页结果当成全部工具。
3. 管理员逐个选择子工具，确认模型说明、接口、读写影响、确认要求和错误/副作用契约。写工具若缺少可执行的幂等或结果查询/人工核查路径，不批准为普通用户的生产写能力。
4. 员工草稿只选择已批准且启用的工具修订；发布预览列出来源、模型可见名称、影响、确认及与上版差异。发布包和连接/工具修订的引用必须可追溯；凭证值不进入发布物。
5. 服务端新增工具只留在候选；远端名称、输入/输出 Schema、影响模型使用的说明或行为契约发生实质变化，须审核新修订。后台展示措辞或密钥值轮换不构成工具修订；连接目标、服务身份、传输或授权边界变化须作为连接配置实质变更重新验证。紧急停用立即阻止尚未发出的调用。

同一个远端工具名对已获准用户应保持一致的调用 Schema；首版不支持“同名工具按用户返回不同参数结构”。更重要的是，**Schema 摘要只能发现部分漂移，不能证明业务语义不变**。可信 Server 必须承诺不兼容变更使用新工具身份/版本，或提供可核实的兼容性与变更通知。旧 Run 所需的原修订无法继续安全执行时应明确失败，不能静默切到新 Server 或新工具。

## 6. 一次 Run 的可见性与调用

新 Run 创建时，平台将“员工已发布修订 ∩ 当前全局启用状态 ∩ 用户对此 Server 的 `tools/list` 结果 ∩ 其他已确认的渠道/Run 约束”投影为模型可见工具集合。列表与调用必须对应同一可信终端用户及租户；不能以服务账号的全量清单替代用户清单，也不能跨用户缓存列表。对于已入集合的工具，未知目标资源保留到 `tools/call` 时由 MCP 最终判权。未入集合的工具，即使用户后来获得权限，也不进入旧 Run；新获得的资源权限可作用于旧 Run 已可见工具的后续调用。撤权、账号停用和工具停用只会收窄未发出的调用。

逐用户发现不要求在数据库事务中发网络请求。详细设计应安排受控预检，再在 Run 创建事务中原子固定所选发布版本、工具视图和对应证据；预检之后的撤权由真正调用时的 MCP 判权兜底。预检失败不能被解释为“用户正常地没有工具”。

模型提出调用后，平台校验 `RunId + toolUseId + 已冻结工具修订 + 当前用户 + 参数/确认状态`，检查 Server 与工具启停，保留幂等与审计事实，然后才送 MCP。MCP 拒绝时平台保留拒绝来源；框架许可、员工绑定、平台确认均不能推翻它。原生 Harness 模板可跨用户复用，但用户身份、Token、`tools/list` 结果和实时权限不能保存在共享模板、Prompt、AgentState 或 Workspace 正式定义层。

在目前的外部 Schema 执行边界下，平台负责把上述检查接到真正的 MCP 调用前；AgentScope 负责 Agent 循环、Schema 和协议客户端，不承担平台的发布/授权事实。详细设计须用最小探针验证 AgentScope 2.0.3 原生客户端在目标传输上的用户隔离、工具发现、并发、取消及异常映射，再决定是否保留平台桥接或采用更直接的注册方式。

## 7. 异常、写操作与审计契约

MCP 对接必须把下面几类结果分开，不把所有异常折叠为“工具失败”：

| 分类 | 平台处理原则 |
| --- | --- |
| 认证失效 | 只有 MCP 能证明在执行前拒绝的 401 才可认定业务未执行；同一用户凭证如何取得、续期，以及 `tools/list` 在新 Run 遇到此类错误如何处理，**待实际对接确定**。不得回退服务账号，也不得把列表失败伪装为空列表。 |
| 无权限 | MCP 逐次资源判权的拒绝不能由平台确认或框架 `ALLOW/BYPASS` 覆盖；不自动提权或重试。 |
| 调用前不可用 | 明确记录连接、工具或版本不可用；不替换为最新工具、不谎称用户无权限。 |
| 请求发出后写结果未知 | 超时、连接中断、5xx 或 `isError=true` 本身不证明副作用未发生。保存原操作键，先查询/核对结果；未查明前不盲目重发。 |

可信 Server 的写工具要提供可区分认证/授权、业务错误、暂不可用与副作用确定性的错误契约，以及原操作标识、幂等或结果查询/人工核查路径。平台对普通用户只给安全文案；有权限的排障视图保留 `UserId`、Run、员工版本、工具/连接修订、调用标识、判定来源、效果状态和必要的脱敏证据。Token、原始敏感参数和隐藏工具目录不进入模型流、普通用户流或普通日志。用户确认绑定单次操作及其规范化参数；已发出的写请求不因 Run 取消、权限撤销或确认失效而被虚构为回滚。

MCP 规范区分 JSON-RPC 协议错误与 `isError` 工具执行错误，但没有替本平台定义写副作用是否发生；上述细分属于接入方必须补齐的业务契约。[MCP Tool 错误规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)。

## 8. 详细设计与编码阶段的必交付项

详细设计必须在动工前明确以下内容；实现时按可验证的纵向切片推进，不以接口骨架宣称打通：

1. **对象与迁移**：连接、发现记录、工具修订、绑定/发布引用和停用事实的最小持久模型；已有 `capability_revision`、RunSpec、ToolExecution 如何演进；只新增 Flyway 迁移，不改已执行脚本。
2. **管理契约**：连接登记/测试、候选差异、逐工具批准、启停、员工发布预览的 API 与页面；管理侧发现身份和可见范围按目标 Server 对接确认，不推定管理员列表是所有用户的全集。
3. **运行契约**：逐用户 `tools/list` 的完整分页、Run 创建原子冻结、同名 Schema 一致性、模型工具名冲突、子 Agent 继承、调用前收窄、错误与幂等/恢复状态。`tools/list` 认证失效的新 Run 行为仍为待定项，不得在代码中偷偷选定默认值。
4. **执行适配**：本地 Tool 与可信 MCP 的判权分支；在同一受控外部执行入口复用 AgentScope/MCP SDK 的协议能力，不复制 MCP 服务端 ACL；保留发送前/发送后边界和写操作结果核查。
5. **验证门槛**：至少覆盖双用户/双租户列表隔离、伪造身份、已绑定但用户列表不可见、列表可见但资源调用被拒、旧 Run 撤权、服务器新增工具或 Schema 漂移、连接停用、401/403/不可用/未知写结果、并发共享 Harness 模板、恢复去重和真实 Server 的协议兼容。静态检查或 Mock 通过不等于真实 MCP Server 已验收。

建议先以一个可信只读子工具贯通“登记—发现—批准—绑定—发布—逐用户可见—调用—拒绝审计”，再加入有结果核查契约的写工具；不在首个切片中开发通用 MCP 资源/知识库、跨 Server 自动同步或新的平台资源 ACL 引擎。

## 9. 明确保留的对接空位

- 终端用户 MCP 凭证由谁签发/取得、怎样续期、平台登录凭证与 MCP 受众如何映射；统一认证不等于同一 Bearer Token 可在各服务通用。协议要求 HTTP 请求逐次携带面向 MCP Server 的凭证并校验受众，具体接法待目标身份系统确定。[MCP 授权规范](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)。
- 新 Run 的 `tools/list` 遇到登录凭证失效时，是否允许同用户自动恢复、是否终止 Run、怎样向用户提示；此处不预设产品状态或自动续期流程。安全底线是不得跨用户、不得回退服务账号、不得当作正常空列表。
- 管理侧发现使用的可信身份、目标 Server 的版本/兼容性和写结果查询接口，在具体 MCP Server 接入时签订并验证；缺少契约的能力不得以“先接上再说”为由放宽上述边界。

本文若与较早的通用能力/权限文档中“平台对所有 MCP 业务资源自行作最终判权”的表述不同，**可信终端用户 MCP 的工具权限与执行边界以本文为准**；本地 Tool 和非可信来源仍按原有平台授权设计或另行评审。
